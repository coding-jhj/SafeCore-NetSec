## 1. 왜 하는가

### 해결하는 문제

- 2일차까지는 부서별 네트워크 대역(VLAN 번호와 IP 대역)을 설계만 해둔 상태였다. 스위치에는 VLAN이 실제로 입력되어 있지 않았고(커밋 기록 "스위치 VLAN 미입력 확인"), 본사와 지사 사이에는 서로 가는 길이 없었다.
- PC는 자기 대역 밖으로 나가려면 게이트웨이(라우터 주소)가 필요하다. 게이트웨이가 없으면 부서 안에서만 통신되고, 다른 부서나 지사로는 한 패킷도 나가지 못한다.
- 라우터는 자기가 모르는 대역으로 가는 패킷을 버린다. 본사 라우터는 지사 대역(192.168.60.0/24)을, 지사 라우터는 본사 대역 5개를 처음에는 모른다. 그래서 정적 경로로 알려줘야 한다.
- 장비에 아무나 접속해 설정을 바꿀 수 있으면 네트워크 전체가 위험해진다. 그래서 비밀번호, 관리 IP, 미사용 포트 차단도 같이 넣었다.

## 2. 핵심 개념

### VLAN

- 물리적으로 같은 스위치에 꽂혀 있어도 논리적으로 네트워크를 나누는 기술이다. VLAN마다 브로드캐스트 도메인이 따로 생긴다.
- 서로 다른 VLAN끼리는 L3 장비(라우터)를 거쳐야만 통신한다. 그래서 라우터가 부서 간 통신의 통제 지점이 되고, 나중에 ACL을 걸 자리가 된다.
- 2960 스위치에서는 `switchport access vlan X`를 입력할 때 그 VLAN이 없으면 자동으로 만들어진다. 로그 8번 섹션에 이 동작을 이용했다고 적혀 있다.

### 액세스 포트와 트렁크 포트

- 액세스 포트는 VLAN 하나에만 속하는 포트다. PC가 꽂히는 포트이고, 프레임에 VLAN 태그가 붙지 않는다.
- 트렁크 포트는 여러 VLAN의 프레임을 한 선으로 나르는 포트다. IEEE 802.1Q 태그(VLAN ID 12비트, 1부터 4094)를 붙여서 어느 VLAN의 프레임인지 구분한다.
- 네이티브 VLAN은 트렁크에서 태그 없이 지나가는 VLAN이다. 기본값은 VLAN 1이다. 양쪽 설정이 어긋나면 문제가 생기고, VLAN 호핑 공격과도 관련된다(후속 하드닝 항목).
- Catalyst 2960은 802.1Q만 지원한다. 그래서 캡슐화 방식을 고르는 `switchport trunk encapsulation dot1q` 명령 자체가 없다(4번 섹션 실수 2).

### VLAN 사이 통신(Inter-VLAN routing)을 만드는 세 가지 방식

| 방식 | 구조 | 장점 | 단점 |
|------|------|------|------|
| 전용 포트 | 부서마다 라우터 포트 하나씩 | 단순하고 한 선에 트래픽이 몰리지 않는다 | 부서 수만큼 라우터 포트가 필요하다 |
| Router-on-a-Stick | 라우터 포트 하나를 트렁크로 받고 서브인터페이스로 나눈다 | 라우터 포트를 아낀다 | 모든 부서 간 트래픽이 한 선에 몰린다 |
| SVI(L3 스위치) | 스위치 안의 가상 인터페이스에 IP를 준다 | 라우팅을 스위치 내부에서 처리한다 | L3 스위치가 필요하다 |

- SafeCore 본사 라우터(SC-HQ-R1, ISR4331)는 실제 토폴로지가 부서별 전용 포트 구조였다. 그래서 원래 계획(Router-on-a-Stick)을 바꿔 전용 포트 방식으로 갔다(작업계획서 "업데이트" 단락).
- 온보드 포트(Gi0/0/0 연구개발, Gi0/0/1 QA)는 일반 라우티드 포트라서 포트에 바로 IP를 준다.
- NIM-ES2-4 모듈 포트(Gi0/1/0부터 Gi0/1/3)는 스위치 포트 성격이다. 포트에 바로 IP를 줄 수 없어서, 포트를 VLAN에 넣고 그 VLAN의 SVI(`interface vlan X`)에 IP를 줬다. 이 경우 라우터 안에서 SVI가 그 부서의 게이트웨이 역할을 한다.
- SVI는 일반적으로 해당 VLAN에 up 상태인 포트가 하나 이상 있어야 up/up이 된다. 스위치가 꺼져 있거나 선이 빠지면 SVI도 down으로 보인다.

### VTP

- VLAN 정보를 스위치끼리 트렁크를 통해 자동으로 전파하는 시스코 프로토콜이다. 같은 도메인 이름 안에서만 동작한다.
- 모드는 세 가지다.

| 모드 | VLAN 생성과 삭제 | 받은 정보를 따르나 | 받은 정보를 다른 스위치에 넘기나 |
|------|------------------|---------------------|----------------------------------|
| server | 가능 | 따른다 | 넘긴다 |
| client | 불가능 | 따른다 | 넘긴다 |
| transparent | 가능(자기 것만) | 따르지 않는다 | 넘긴다(VTP 버전에 따라 다르다, 확인 필요) |

- 편리하지만 위험이 있다. configuration revision 번호가 더 높은 스위치가 같은 도메인으로 연결되면, 그 스위치의 VLAN 정보로 도메인 전체가 덮어써질 수 있다. 실수로 VLAN이 전부 사라지는 운영 사고가 된다.

### 정적 라우팅

- 관리자가 "이 목적지 대역은 이 next-hop으로 보내라"를 직접 적는 방식이다. 형식은 `ip route <목적지 대역> <마스크> <next-hop>`이다.
- 장점은 단순하고, 라우터 부하가 거의 없고, 동작을 예측하기 쉽다는 점이다.
- 단점은 대역이 늘 때마다 사람이 양쪽 라우터에 추가해야 하고, 경로 너머의 장애를 스스로 감지하지 못한다는 점이다. 5일차에 RIPv2로 이 단점을 다룬다.
- 통신은 갈 때와 올 때가 모두 있어야 성립한다. 본사에서 지사로 가는 경로만 있고 지사에서 본사로 돌아오는 경로가 없으면 ping은 실패한다.
- 라우팅 테이블에서 `C`는 직접 연결된 대역, `L`은 라우터 자신의 인터페이스 주소(/32), `S`는 정적 경로다.

### CDP

- 시스코 장비끼리 직접 연결된 이웃의 이름, 기종, 포트 정보를 주고받는 L2 프로토콜이다.
- 3일차에는 실제로 어느 포트에 선이 꽂혔는지 확인하는 데 썼다. 설계와 실제 배선이 달랐던 것을 CDP로 찾았다(단계 3).
- 이웃에게 장비 정보를 알려주므로 정보 노출 위험이 있다. 외부와 닿는 포트에서는 끄는 것이 보통이다.

### ARP와 첫 ping 유실

- ARP는 IP 주소로 MAC 주소를 알아내는 프로토콜이다. 같은 대역 안에서 프레임을 보내려면 상대(또는 게이트웨이)의 MAC 주소가 필요하다.
- 처음 보내는 ping의 앞쪽 패킷이 유실되는 경우가 있는데, ARP 학습을 기다리는 동안 생기는 경우가 많다.

### 장비 관리 접속과 비밀번호

- 텔넷은 원격으로 장비 CLI에 접속하는 방법이다. 평문으로 전송되어 비밀번호가 그대로 보일 수 있다. 실무에서는 SSH를 쓴다. 학습 단계라 텔넷으로 구성했고 SSH 전환은 후속 하드닝 항목이다.
- `enable secret`은 해시로 저장된다. line의 `password`는 설정 파일에 평문으로 보인다.
- 스위치는 L2 장비지만 관리용으로 SVI 하나에 IP를 받을 수 있다. 이 IP로 텔넷에 접속한다.

## 3. 단계별 실습

### 단계 1. 본사 라우터(SC-HQ-R1) 부서 VLAN과 SVI 설정 (로그 1번)

**(a) 목적**

기술지원팀(본사), 경영지원팀, 서버팜이 연결된 NIM-ES2-4 모듈 포트는 포트에 바로 IP를 받지 못한다. 그래서 포트를 부서 VLAN의 액세스 포트로 만들고, 그 VLAN의 SVI에 게이트웨이 IP를 준다.

연구개발(Gi0/0/0, 192.168.10.1)과 QA(Gi0/0/1, 192.168.20.1)는 온보드 포트라서 포트에 직접 IP가 들어가 있다. 그런데 이 두 포트에 IP를 처음 넣은 명령은 3일차 로그에 없다. 로그 1번 섹션에는 확인 결과(.10과 .20이 up/up)만 있다. 3일차 이전에 입력했거나 기록에서 빠진 것이다(확인 필요). 같은 형식의 명령은 단계 15(원복)에 기록되어 있다.

**(b) 명령어**

**SC-HQ-R1** (기술지원팀 본사, VLAN 30)
```
interface GigabitEthernet0/1/0
switchport mode access
switchport access vlan 30
exit
interface vlan 30
ip address 192.168.30.1 255.255.255.0
no shutdown
exit
```

**SC-HQ-R1** (경영지원팀, VLAN 40)
```
interface GigabitEthernet0/1/1
switchport mode access
switchport access vlan 40
exit
interface vlan 40
ip address 192.168.40.1 255.255.255.0
no shutdown
exit
```

**SC-HQ-R1** (서버팜, VLAN 50)
```
interface GigabitEthernet0/1/2
switchport mode access
switchport access vlan 50
exit
interface vlan 50
ip address 192.168.50.1 255.255.255.0
no shutdown
exit
```

**(c) 명령어 설명**

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |
|--------|-----|----------------------------------|
| `interface GigabitEthernet0/1/0` | 해당 모듈 포트의 설정 모드로 들어간다 | 이후 명령이 이 포트에 적용되게 한다. 다른 포트에서 입력하면 엉뚱한 부서가 바뀐다 |
| `switchport mode access` | 이 포트를 VLAN 하나에만 속하는 액세스 포트로 고정한다 | 고정하지 않으면 포트가 DTP로 상대와 트렁크를 협상할 여지가 남는다. 부서 스위치 하나만 연결되는 포트이므로 액세스로 못 박아 두는 것이 의도가 분명하다 |
| `switchport access vlan 30` | 이 포트를 VLAN 30에 넣는다 | 빠지면 포트가 기본 VLAN 1에 남는다. 그러면 VLAN 30의 SVI와 이 포트가 연결되지 않아 기술지원팀 PC가 게이트웨이에 닿지 못한다 |
| `exit` | 인터페이스 설정 모드에서 빠져나온다 | 다음 인터페이스로 넘어가기 위한 정리 동작이다 |
| `interface vlan 30` | VLAN 30의 가상 인터페이스(SVI)를 만들고 설정 모드로 들어간다 | 모듈 포트에는 IP를 줄 수 없으므로 IP를 받을 자리가 이 SVI다. 빠지면 VLAN 30에는 게이트웨이가 없다 |
| `ip address 192.168.30.1 255.255.255.0` | SVI에 게이트웨이 주소를 준다 | 기술지원팀 PC들의 기본 게이트웨이 주소다. 빠지거나 틀리면 PC가 자기 대역 밖으로 나가지 못한다 |
| `no shutdown` | 인터페이스를 켠다 | 라우터의 인터페이스와 새로 만든 SVI는 기본이 꺼진 상태다. 빠지면 administratively down으로 남고 통신이 안 된다 |

VLAN 40과 VLAN 50 블록도 번호와 주소만 다르고 같은 이유로 들어간다.

로그에는 라우터에서 `vlan 30` 같은 VLAN 생성 명령이 따로 없다. `switchport access vlan 30` 입력 시 VLAN이 자동 생성되었다고 보는 것이 자연스럽지만, 라우터 쪽에서 실제로 자동 생성되었는지는 기록이 없다(확인 필요).

**(d) 확인**

**SC-HQ-R1**
```
show ip interface brief
```

- 읽는 법: Interface, IP-Address, Status, Protocol 열을 본다. Status와 Protocol이 둘 다 up이면 정상이다. Status가 administratively down이면 `no shutdown`이 빠진 것이다. up/down이면 물리 연결은 되었지만 상위 계층 문제가 있는 것이고, SVI라면 그 VLAN에 활성 포트가 없는 경우가 많다.
- 실제 결과(로그): 연구개발(.10), QA(.20), 기술지원본사(.30), 경영지원(.40), 서버팜(.50) 인터페이스가 모두 up/up으로 확인되었다.

### 단계 2. 장비 호스트네임 설정 (로그 2번)

**(b) 명령어**

**SC-SW-RND** (연구개발팀 스위치)


**SC-SW-TS** (기술지원팀 본사 스위치)

**SC-SW-ADM** (경영지원팀 스위치)

**(c) 명령어 설명**

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |

| `hostname SC-BR-R1` | 장비 이름을 정한다. 프롬프트가 `SC-BR-R1(config)#`처럼 바뀐다 | 기본 이름(Router, Switch)이 그대로면 8대가 구분되지 않는다. 엉뚱한 장비에 명령을 넣는 실수가 생기고, CDP 결과(단계 7)에서도 이웃이 어느 장비인지 알 수 없다 |

**(d) 확인**

### 단계 3. 본사와 지사 사이 WAN 링크, VLAN 70 (로그 3번)

**(a) 목적**

본사 라우터와 지사 라우터를 이더넷으로 연결하고, 그 구간에 192.168.70.0/24 대역을 준다. 이 링크가 정적 경로의 next-hop이 된다.

설계상으로는 SC-HQ-R1의 Gi0/0/2와 SC-BR-R1의 Gi0/1을 연결하려 했다. 그런데 `show cdp neighbors`로 확인해 보니 실제로는 SC-HQ-R1의 Gi0/1/3(NIM 모듈 포트)에 연결되어 있었다. 모듈 포트이므로 단계 1과 같은 VLAN과 SVI 방식으로 설정했다. 대역은 기존 부서 대역 체계와 맞추려고 VLAN 70, /24로 정했다.

**(b) 명령어**

**SC-HQ-R1**
```
interface GigabitEthernet0/1/3
switchport mode access
switchport access vlan 70
exit
interface vlan 70
ip address 192.168.70.1 255.255.255.0
no shutdown
exit
```

**SC-BR-R1**
```
interface GigabitEthernet0/1
ip address 192.168.70.2 255.255.255.0
no shutdown
exit
```

**(c) 명령어 설명**

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |
|--------|-----|----------------------------------|
| `interface GigabitEthernet0/1/3` | 실제로 지사와 연결된 모듈 포트를 고른다 | 설계에 적힌 Gi0/0/2에 설정했다면 선이 없는 포트에 IP가 들어가고 WAN은 끊긴 채로 남는다. CDP로 확인한 실제 포트에 넣어야 한다 |
| `switchport mode access` | 액세스 포트로 고정한다 | WAN 구간은 VLAN 하나만 쓰므로 트렁크 협상 여지를 없앤다 |
| `switchport access vlan 70` | 포트를 WAN 전용 VLAN 70에 넣는다 | 빠지면 포트가 VLAN 1에 남아 SVI 70과 연결되지 않는다 |
| `interface vlan 70` | WAN용 SVI를 만든다 | 모듈 포트 대신 IP를 받을 자리다 |
| `ip address 192.168.70.1 255.255.255.0` | 본사 쪽 WAN 주소 | 지사 라우터가 본사로 보낼 때 쓰는 next-hop 주소가 된다(단계 5). 빠지면 지사의 정적 경로가 갈 곳이 없다 |
| `no shutdown` | SVI를 켠다 | 빠지면 WAN 전체가 down이다 |
| `interface GigabitEthernet0/1` (SC-BR-R1) | 지사 라우터의 WAN 포트를 고른다 | 2901의 이 포트는 일반 라우티드 포트라서 VLAN 없이 바로 IP를 줄 수 있다 |
| `ip address 192.168.70.2 255.255.255.0` | 지사 쪽 WAN 주소 | 본사 라우터가 지사로 보낼 때 쓰는 next-hop 주소다. 본사와 같은 대역이어야 서로 직접 연결된 이웃이 된다 |
| `no shutdown` (SC-BR-R1) | 포트를 켠다 | 라우터 포트는 기본이 꺼져 있다. 빠지면 링크가 올라오지 않는다 |

**(d) 확인**

**SC-HQ-R1** 또는 **SC-BR-R1**
```
show cdp neighbors
```

- 읽는 법: Device ID는 상대 장비 이름, Local Intrfce는 내 쪽 포트, Port ID는 상대 쪽 포트다. 설계 문서의 포트가 아니라 이 결과가 실제 배선이다.
- 실제 결과(로그): SC-HQ-R1 Gig0/1/3과 SC-BR-R1 Gig0/1이 연결된 것이 확인되었다.
- 로그에는 WAN 구간만 따로 ping한 기록(예: SC-HQ-R1에서 192.168.70.2로 ping)은 없다. 단계 5의 ping 성공이 이 구간이 살아 있다는 간접 증거다.

### 단계 4. 지사 라우터(SC-BR-R1) 내부 LAN 게이트웨이 (로그 4번)

**(a) 목적**

지사 기술지원팀(VLAN 60, 192.168.60.0/24) PC들의 게이트웨이를 만든다. SC-BR-R1의 Gi0/0은 일반 라우티드 포트라서 바로 IP를 준다.

**(b) 명령어**

**SC-BR-R1**
```
interface GigabitEthernet0/0
ip address 192.168.60.1 255.255.255.0
no shutdown
exit
```

**(c) 명령어 설명**

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |
|--------|-----|----------------------------------|
| `interface GigabitEthernet0/0` | 지사 스위치(SC-SW-TSBR)와 연결된 포트를 고른다 | 지사 LAN의 출입구가 이 포트다 |
| `ip address 192.168.60.1 255.255.255.0` | 지사 기술지원팀의 게이트웨이 주소 | 빠지면 지사 PC가 본사로 나갈 수 없다. 또 이 대역이 SC-BR-R1의 연결된 대역(C)으로 잡히지 않는다 |
| `no shutdown` | 포트를 켠다 | 빠지면 지사 LAN 전체가 고립된다 |
| `exit` | 인터페이스 설정 모드를 빠져나온다 | 다음 설정을 위한 정리 동작이다 |

라우터 포트에 직접 IP를 주는 방식이므로 VLAN 60은 라우터 설정에 나타나지 않는다. VLAN 60은 지사 스위치 안에서만 의미가 있다(단계 8).

**(d) 확인**

- 로그에는 이 단계만의 확인 기록이 따로 없다. 단계 10의 관리 IP 설정과 단계 5 이후 통신으로 간접 확인된다.
- 확인하려면 SC-BR-R1에서 `show ip interface brief`를 실행해 Gi0/0이 192.168.60.1로 up/up인지 본다.

### 단계 5. 정적 라우팅 (로그 5번)

**(a) 목적**

라우터는 자기에게 직접 연결된 대역만 안다. 본사 라우터는 지사 LAN(60 대역)을, 지사 라우터는 본사 LAN 5개(10, 20, 30, 40, 50 대역)를 모른다. 양쪽에 상대 대역으로 가는 길을 적어 준다.

본사 쪽은 경로가 1줄이고 지사 쪽은 5줄인 이유는, 각 라우터가 모르는 대역 수가 다르기 때문이다. 본사 라우터 입장에서 본사 5개 부서는 모두 직접 연결된 대역이고 모르는 것은 지사 1개뿐이다.

**(b) 명령어**

**SC-HQ-R1** (지사 네트워크로 가는 길)
```
ip route 192.168.60.0 255.255.255.0 192.168.70.2
```

**SC-BR-R1** (본사 5개 네트워크로 가는 길)
```
ip route 192.168.10.0 255.255.255.0 192.168.70.1
ip route 192.168.20.0 255.255.255.0 192.168.70.1
ip route 192.168.30.0 255.255.255.0 192.168.70.1
ip route 192.168.40.0 255.255.255.0 192.168.70.1
ip route 192.168.50.0 255.255.255.0 192.168.70.1
```

**(c) 명령어 설명**

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |
|--------|-----|----------------------------------|
| `ip route 192.168.60.0 255.255.255.0 192.168.70.2` | 60 대역으로 가는 패킷은 지사 라우터의 WAN 주소로 넘기라는 정적 경로 | 빠지면 본사 라우터는 지사로 가는 패킷을 버린다. 지사 PC가 본사로 보낸 요청이 본사에 도착해도 응답이 지사로 돌아가지 못한다 |
| `ip route 192.168.10.0 255.255.255.0 192.168.70.1` | 연구개발 대역은 본사 라우터로 넘기라는 경로 | 빠지면 지사에서 연구개발 대역으로 갈 수 없다 |
| `ip route 192.168.20.0 255.255.255.0 192.168.70.1` | QA 대역으로 가는 경로 | 빠지면 지사에서 QA 대역으로 갈 수 없다 |
| `ip route 192.168.30.0 255.255.255.0 192.168.70.1` | 기술지원팀 본사 대역으로 가는 경로 | 빠지면 본사와 지사 기술지원팀끼리 통신할 수 없다 |
| `ip route 192.168.40.0 255.255.255.0 192.168.70.1` | 경영지원 대역으로 가는 경로 | 빠지면 지사에서 경영지원 대역으로 갈 수 없다 |
| `ip route 192.168.50.0 255.255.255.0 192.168.70.1` | 서버팜 대역으로 가는 경로 | 요구사항의 핵심이다. 지사 기술지원팀이 쓰는 티켓 시스템과 파일 서버가 서버팜에 있다. 빠지면 요구사항을 충족하지 못한다 |

연구개발 대역(10)과 경영지원 대역(40)으로 가는 경로는 요구사항상 지사가 쓸 일이 없는 경로다. 3일차는 "먼저 전체를 연결하고 나중에 ACL로 막는다"는 계획이라 모두 넣었다. 6번 섹션에서 다시 다룬다.

next-hop을 상대 라우터의 WAN 주소로 지정했다. 출구 인터페이스만 적는 방식(`ip route ... GigabitEthernet0/1`)도 있지만, 이더넷 구간에서는 next-hop 주소를 적는 쪽이 ARP 동작이 명확하다.

**(d) 확인**

**SC-BR-R1**
```
ping 192.168.10.1
```

- 읽는 법: 라우터 ping은 `!`가 성공, `.`가 시간 초과다. 5개 중 몇 개가 돌아왔는지와 성공률이 마지막 줄에 나온다.
- 실제 결과(로그): 성공. 지사 라우터에서 본사 연구개발 게이트웨이까지 경로가 열렸다.
- 이 ping은 지사 라우터 자신이 출발점이라 출발 주소가 192.168.70.2다. 본사 라우터는 70 대역을 직접 알고 있으므로, 이 ping의 성공만으로는 본사 쪽 정적 경로(60 대역)까지 검증되지 않는다. 지사 PC(60 대역)에서 본사로 ping해야 양방향 경로가 모두 검증된다.
- 작업계획서에는 `show ip route`로 라우팅 테이블을 확인한다고 계획되어 있지만, 로그에는 그 실행 결과가 기록되어 있지 않다(확인 필요). 실행한다면 SC-BR-R1에 `S 192.168.10.0/24 [1/0] via 192.168.70.1` 형태의 줄이 5개, SC-HQ-R1에 60 대역 줄이 1개 보여야 한다. 대괄호 안의 1은 정적 경로의 기본 AD 값이다.
- 작업계획서 결과 섹션에는 "본사 5개 부서와 지사 1개 부서 간 전체 조합 ping 테스트 성공"이라고 적혀 있지만, 로그에는 조합별 결과가 기록되어 있지 않다(확인 필요).

### 단계 6. no ip domain-lookup (로그 6번)

**(a) 목적**

CLI에서 명령어를 잘못 입력하면 IOS는 그 단어를 호스트 이름으로 보고 DNS 조회를 시도한다. 조회가 끝날 때까지 콘솔이 멈춘 것처럼 기다리게 된다. 이 기다림을 없앤다.

로그에는 "전 장비(SC-HQ-R1, SC-BR-R1, 스위치 6개)에 적용 요청함"이라고만 적혀 있다. 8대에 실제로 적용되었는지 확인한 기록은 없다(확인 필요).

**(b) 명령어**

**SC-HQ-R1**
```
no ip domain-lookup
```

**SC-BR-R1**
```
no ip domain-lookup
```

**SC-SW-RND**
```
no ip domain-lookup
```

**SC-SW-QA**
```
no ip domain-lookup
```

**SC-SW-TS**
```
no ip domain-lookup
```

**SC-SW-ADM**
```
no ip domain-lookup
```

**SC-SW-SRV**
```
no ip domain-lookup
```

**SC-SW-TSBR**
```
no ip domain-lookup
```

**(c) 명령어 설명**

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |
|--------|-----|----------------------------------|
| `no ip domain-lookup` | 이름을 DNS로 조회하는 기능을 끈다 | 빠지면 오타 하나마다 수십 초씩 기다려야 한다. 통신이 깨지지는 않지만 작업 시간이 늘고, 장애 대응 중에는 그 지연이 곧 복구 지연이 된다. 사내에 DNS 서버가 없는 실습 환경에서는 조회가 성공할 일도 없다 |

**(d) 확인**

- 각 장비에서 일부러 없는 단어를 입력해 본다. 바로 에러가 나오고 기다림이 없으면 적용된 것이다.
- 설정으로 보려면 `show running-config`에서 `no ip domain-lookup` 줄을 찾는다. 장비와 IOS 버전에 따라 `no ip domain lookup`으로 표시될 수 있다(확인 필요).

### 단계 7. 스위치 6대의 라우터 업링크 포트 확인, CDP (로그 7번)

**(a) 목적**

스위치마다 어느 포트가 라우터로 올라가는 업링크인지 확인한다. 다음 단계에서 포트를 VLAN에 넣을 때 업링크 포트까지 같은 VLAN에 넣어야 PC가 게이트웨이에 닿는다. 설계 문서가 아니라 실제 배선을 기준으로 해야 한다는 것을 단계 3에서 이미 겪었다.

**(b) 명령어**

**SC-SW-RND**
```
show cdp neighbors
```

**(c) 명령어 설명**

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |
|--------|-----|----------------------------------|
| `interface range fastEthernet 0/1-15` | 여러 포트를 한 번에 설정 모드로 연다 | 포트 15개를 하나씩 입력하면 빠뜨리는 포트가 생긴다. 한 포트라도 빠지면 그 PC만 VLAN 1에 남아 고립된다 |
| `switchport mode access` | 포트를 액세스 포트로 고정한다 | 2960 포트 기본값은 동적 협상 모드다. 고정하지 않으면 누군가 스위치를 꽂았을 때 트렁크가 맺혀 여러 VLAN이 노출될 여지가 생긴다 |
| `switchport access vlan 10` | 포트를 VLAN 10에 넣고, VLAN 10이 없으면 만든다 | 빠지면 모든 포트가 VLAN 1에 남는다. 부서 분리가 안 되고, 라우터 쪽 SVI와 VLAN 번호가 의미를 잃는다 |
| `no switchport access vlan` | 포트의 VLAN 지정을 지워 기본 VLAN 1로 되돌린다 | 잘못 넣은 미사용 포트(Fa0/8부터 Fa0/17)를 QA VLAN에서 빼기 위해서다. 남겨두면 쓰지 않는 포트가 QA 대역에 붙어 있게 되고, 단계 12의 shutdown 전까지 그 포트에 꽂으면 바로 QA 망에 들어온다 |

스위치 자체에서 업링크 포트가 VLAN 10이고 라우터 Gi0/0/0이 라우티드 포트인 구조다. 라우터 포트에는 VLAN 개념이 없고 태그 없는 프레임만 받는다. 스위치 업링크가 액세스 포트라서 태그 없이 내보내므로 두 장비가 맞물린다.

| `line console 0` | 콘솔 포트 설정 모드로 들어간다 | 장비 앞에서 케이블로 접속하는 경로를 보호하기 위해서다 |
| `password <실습용 비밀번호>` (console) | 콘솔 접속 비밀번호를 정한다 | 빠지면 장비에 물리적으로 다가간 사람은 비밀번호 없이 사용자 모드에 들어온다 |
| `login` (console) | 이 라인에 접속할 때 위 비밀번호를 검사하라고 지시한다 | 빠지면 비밀번호를 정해 두어도 검사하지 않는다. `password`와 `login`은 짝으로 들어가야 의미가 있다 |
| `line vty 0 15` | 원격 접속용 가상 라인 16개(0번부터 15번)를 한 번에 설정한다 | 0번부터 4번만 설정하면 나머지 라인이 다른 설정으로 남을 수 있다. 전체 라인에 같은 규칙을 걸어 빈틈을 없앤다 |
| `password <실습용 비밀번호>` (vty) | 텔넷 접속 비밀번호를 정한다 | 빠지면 IOS는 비밀번호 없는 vty 접속을 거부한다. 즉 텔넷 관리가 아예 안 된다 |
| `login` (vty) | vty 접속 때 비밀번호를 검사한다 | 비밀번호 검사를 명시적으로 켠다. IOS 기본 설정에 vty `login`이 이미 들어 있는 경우가 많지만, 명시해 두면 의도가 설정 파일에 분명히 남는다(Packet Tracer 2960의 기본값은 확인 필요) |
| `interface vlan 10` | 스위치의 관리용 SVI를 VLAN 10에 만든다 | 2960은 L2 스위치라 포트에 IP를 줄 수 없다. 원격 접속을 받을 IP를 둘 자리가 SVI다. 부서 VLAN에 만들어야 같은 VLAN의 PC가 닿는다 |
| `ip address 192.168.10.254 255.255.255.0` | 관리 IP를 준다 | 텔넷으로 접속할 목적지 주소다. .254를 쓴 이유는 PC 주소(.11 등)와 게이트웨이(.1)와 겹치지 않는 끝 번호로 규칙을 정해 두려는 것이다 |
| `no shutdown` | 관리 SVI를 켠다 | 새로 만든 SVI는 꺼져 있다. 빠지면 관리 IP에 ping도 텔넷도 안 된다 |
| `ip default-gateway 192.168.10.1` | 스위치 자신이 다른 대역과 통신할 때 쓸 게이트웨이를 정한다 | 빠지면 같은 VLAN의 PC에서는 텔넷이 되지만, 다른 대역(예: 다른 부서나 지사)에서 접속하면 스위치가 응답을 돌려보낼 길을 모른다. 스위치는 라우팅을 하지 않으므로 `ip route`가 아니라 이 명령을 쓴다 |

**(d) 확인**

- 읽는 법: 접속되면 비밀번호를 묻고, 맞게 입력하면 `SC-SW-RND>` 프롬프트가 나온다. 이어서 `enable`을 입력하고 enable secret을 넣어 `SC-SW-RND#`이 나오면 원격 관리까지 확인된 것이다.
- 실제 결과(로그): 연구개발팀 PC에서 `telnet 192.168.10.254` 접속에 성공했다. 나머지 5대는 설정만 하고 개별 테스트는 생략했다. 그래서 QA, TS, ADM, SRV, TSBR의 텔넷 동작은 검증되지 않았다(확인 필요).
- 접속 후 `enable` 단계까지 확인했는지는 로그에 없다(확인 필요).

### 단계 12. 안 쓰는 포트 shutdown (로그 12번)

**(a) 목적**

각 스위치의 connected 범위 밖 포트(안 쓰는 FastEthernet 포트)와 기가비트 포트 Gi0/1, Gi0/2를 모두 끈다. 누군가 빈 포트에 장비를 몰래 꽂아도 통신이 되지 않게 하려는 것이다.

로그 12번 섹션의 제목은 "안 쓰는 포트/VLAN shutdown"이지만, 기록된 명령은 포트 shutdown뿐이다. VLAN을 끄거나 지운 명령은 없다.

**(b) 명령어**

**SC-SW-RND**
```
interface range fastEthernet 0/16-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown
```

**SC-SW-QA**
```
interface range fastEthernet 0/8-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown
```

**SC-SW-TS**
```
interface range fastEthernet 0/8-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown
```

**SC-SW-ADM**
```
interface range fastEthernet 0/10-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown
```

**SC-SW-SRV**
```
interface range fastEthernet 0/6-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown
```

**SC-SW-TSBR**
```
interface range fastEthernet 0/10-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown
```

**SC-SW-SRV** (실수 수정. TSBR용 범위 0/10-24를 넣어서 빠진 Fa0/6부터 Fa0/9를 추가로 끔)
```
interface range fastEthernet 0/6-9
shutdown
```

적용 후 장비마다 `copy running-config startup-config`로 다시 저장했다. 로그는 대상을 "8대"라고 적었는데, 이 단계에서 변경한 장비는 스위치 6대이고 라우터 2대의 저장 여부는 로그에 없다(확인 필요). 스위치 6대에서 입력한 저장 명령은 다음과 같다.

```
(SC-SW-RND) copy running-config startup-config
(SC-SW-QA) copy running-config startup-config
(SC-SW-TS) copy running-config startup-config
(SC-SW-ADM) copy running-config startup-config
(SC-SW-SRV) copy running-config startup-config
(SC-SW-TSBR) copy running-config startup-config
```

**(c) 명령어 설명**

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |
|--------|-----|----------------------------------|
| `interface range fastEthernet 0/16-24` | connected 범위 다음 포트부터 마지막 포트까지 고른다 | 범위의 시작은 반드시 connected 범위 바로 다음이어야 한다. 시작을 하나 앞으로 당기면 사용 중인 PC나 업링크가 꺼진다 |
| `shutdown` | 고른 포트를 관리자 권한으로 끈다 | 빠지면 빈 포트에 노트북이나 무선 공유기를 꽂는 순간 바로 네트워크에 들어온다. 미사용 포트는 기본 VLAN 1에 있으므로, 같은 스위치의 관리 정보나 VLAN 1 트래픽에 접근할 통로가 된다 |
| `interface range gigabitEthernet 0/1-2` | 업링크용 기가비트 포트 2개를 고른다 | 이 실습에서는 기가비트 포트를 쓰지 않는다. 속도가 빠른 포트라 다른 스위치를 연결하기 좋은 자리여서 더 막아둘 이유가 있다 |

**(d) 확인**

- `show ip interface brief`(스위치에서도 동작한다) 또는 `show interfaces status`로 해당 포트가 administratively down(또는 disabled)인지 본다.
- 로그에는 이 단계의 확인 출력이 따로 기록되어 있지 않다. SRV의 범위 실수는 확인 과정에서 발견된 것으로 보이지만, 어떤 명령으로 발견했는지는 기록이 없다(확인 필요).

### 단계 13. 수업 과제: 체인 트렁크, 라우터 서브인터페이스, VTP 구성 (로그 13번)

**(a) 목적**

메인 포트폴리오와 별개인 수업 과제다. 본사 라우터는 SC-SW-RND에만 연결을 남기고, 나머지 스위치 4대는 라우터 연결을 끊은 뒤 RND부터 체인(사슬)으로 이었다: RND, QA, TS, ADM, SRV 순서다. 라우터는 포트 하나(Gi0/0/0)로 5개 부서를 모두 받는 Router-on-a-Stick 구조가 되고, 스위치 사이 연결은 모두 트렁크가 된다. VLAN 정보는 VTP로 RND(서버)에서 나머지(클라이언트)로 전파한다.

체인 구조에서 VTP가 필요한 이유가 있다. 예를 들어 서버팜 PC의 프레임은 SRV, ADM, TS, QA, RND를 거쳐 라우터로 간다. 중간 스위치(ADM, TS, QA, RND)는 자기 부서가 아닌 VLAN 50의 프레임도 트렁크로 넘겨야 한다. 스위치는 자기 VLAN 데이터베이스에 없는 VLAN의 프레임은 트렁크로 넘기지 않으므로, 모든 스위치가 VLAN 10부터 50까지 전부 알아야 한다. VTP가 이것을 자동으로 맞춰 준다.

물리 연결(로그, `show cdp neighbors`로 확인):

| 연결 | 포트 |
|---|---|
| SC-HQ-R1 Gi0/0/0 와 SC-SW-RND | Fa0/1 |
| SC-SW-RND 와 SC-SW-QA | Fa0/16 과 Fa0/1 |
| SC-SW-QA 와 SC-SW-TS | Fa0/8 과 Fa0/4 |
| SC-SW-TS 와 SC-SW-ADM | Fa0/8 과 Fa0/4 |
| SC-SW-ADM 와 SC-SW-SRV | Fa0/10 과 Fa0/5 |

새로 쓰게 된 RND Fa0/16, QA Fa0/8, TS Fa0/8, ADM Fa0/10은 단계 12에서 shutdown한 포트다. 로그에는 이 포트들에 `no shutdown`을 입력한 기록이 없다. 단계 14에서 이 포트들이 trunking 상태로 확인되었으므로 다시 켜진 것은 확실하지만, 입력한 명령은 기록에서 누락되어 있다.

**(b) 명령어**

**SC-HQ-R1** (Router-on-a-Stick 서브인터페이스로 전환)
```
interface GigabitEthernet0/0/0
no ip address
no shutdown
exit
interface GigabitEthernet0/0/1
no ip address
shutdown
exit
no interface Vlan30
no interface Vlan40
no interface Vlan50
interface GigabitEthernet0/0/0.10
encapsulation dot1Q 10
ip address 192.168.10.1 255.255.255.0
exit
interface GigabitEthernet0/0/0.20
encapsulation dot1Q 20
ip address 192.168.20.1 255.255.255.0
exit
interface GigabitEthernet0/0/0.30
encapsulation dot1Q 30
ip address 192.168.30.1 255.255.255.0
exit
interface GigabitEthernet0/0/0.40
encapsulation dot1Q 40
ip address 192.168.40.1 255.255.255.0
exit
interface GigabitEthernet0/0/0.50
encapsulation dot1Q 50
ip address 192.168.50.1 255.255.255.0
exit
interface GigabitEthernet0/1/0
shutdown
exit
interface GigabitEthernet0/1/1
shutdown
exit
interface GigabitEthernet0/1/2
shutdown
end
```

**SC-SW-RND** (VTP 서버)
```
vtp domain SAFECORE
vtp mode server
vlan 20
name QA
exit
vlan 30
name TechSupport_HQ
exit
vlan 40
name Admin
exit
vlan 50
name ServerFarm
exit
interface fastEthernet 0/1
switchport mode trunk
exit
interface fastEthernet 0/16
switchport mode trunk
end
```

**SC-SW-QA** (VTP 클라이언트, 위로 RND Fa0/16, 아래로 TS Fa0/4)
```
vtp domain SAFECORE
vtp mode client
interface fastEthernet 0/1
switchport mode trunk
exit
interface fastEthernet 0/8
switchport mode trunk
end
```

**SC-SW-TS** (VTP 클라이언트, 위로 QA Fa0/8, 아래로 ADM Fa0/4)
```
vtp domain SAFECORE
vtp mode client
interface fastEthernet 0/4
switchport mode trunk
exit
interface fastEthernet 0/8
switchport mode trunk
end
```

**SC-SW-ADM** (VTP 클라이언트, 위로 TS Fa0/8, 아래로 SRV Fa0/5)
```
vtp domain SAFECORE
vtp mode client
interface fastEthernet 0/4
switchport mode trunk
exit
interface fastEthernet 0/10
switchport mode trunk
end
```

**SC-SW-SRV** (VTP 클라이언트, 체인의 끝이라 위로 ADM Fa0/10 연결 하나뿐)
```
vtp domain SAFECORE
vtp mode client
interface fastEthernet 0/5
switchport mode trunk
end
```

로그 원문은 클라이언트 4대를 `interface fastEthernet 0/X`, `0/Y` 틀 하나로 적었다. 위 블록은 로그에 적힌 장비별 포트(QA는 0/1과 0/8, TS는 0/4와 0/8, ADM은 0/4와 0/10, SRV는 0/5만)를 그대로 풀어 쓴 것이다.

**(c) 명령어 설명**

라우터 쪽:

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |
|--------|-----|----------------------------------|
| `interface GigabitEthernet0/0/0` 후 `no ip address` | 물리 포트에서 192.168.10.1을 지운다 | 같은 주소를 서브인터페이스 .10에 다시 줄 것이므로 먼저 비워야 한다. 남겨두면 "overlaps with" 에러가 난다(4번 섹션 실수 3). 트렁크를 받는 물리 포트는 주소 없이 서브인터페이스의 그릇 역할만 한다 |
| `no shutdown` (Gi0/0/0) | 물리 포트를 켜 둔다 | 서브인터페이스는 물리 포트가 켜져 있어야 동작한다. 물리 포트가 꺼지면 5개 부서 게이트웨이가 한꺼번에 down된다 |
| `interface GigabitEthernet0/0/1` 후 `no ip address` | QA 포트의 192.168.20.1을 지운다 | 같은 대역을 .20 서브인터페이스에 줄 것이므로 겹침을 없앤다. 빠지면 "overlaps with" 에러가 난다 |
| `shutdown` (Gi0/0/1) | QA 포트를 끈다 | 이 구조에서 QA 스위치는 라우터에 직접 연결되지 않는다. 쓰지 않는 포트를 끄는 원칙(단계 12)과 같다 |
| `no interface Vlan30`, `no interface Vlan40`, `no interface Vlan50` | 기존 SVI 3개를 지운다 | SVI에 있던 192.168.30.1, 40.1, 50.1을 서브인터페이스에 다시 줄 것이므로 먼저 지워야 한다. 빠지면 "overlaps with" 에러가 난다. Vlan70(WAN)은 지우지 않는다. 지우면 지사와의 연결이 끊긴다 |
| `interface GigabitEthernet0/0/0.10` | Gi0/0/0 아래에 논리 서브인터페이스 .10을 만든다 | 물리 포트 하나를 VLAN별 논리 포트로 나누는 것이 Router-on-a-Stick의 핵심이다. 번호(.10)는 VLAN 번호와 맞춰야 읽기 쉽지만, 실제 VLAN을 정하는 것은 다음 줄이다 |
| `encapsulation dot1Q 10` | 이 서브인터페이스는 VLAN 10 태그가 붙은 프레임을 처리한다고 정한다 | 빠지면 라우터가 어느 VLAN의 프레임을 이 서브인터페이스로 받을지 모른다. IOS는 캡슐화가 없는 서브인터페이스에 IP를 주는 것을 허용하지 않으므로 반드시 IP보다 먼저 넣는다 |
| `ip address 192.168.10.1 255.255.255.0` (서브인터페이스) | VLAN 10의 게이트웨이 주소를 서브인터페이스에 준다 | PC의 게이트웨이 설정은 그대로 두고 구조만 바꾸기 위해 같은 주소를 쓴다. 다른 주소를 주면 모든 PC의 게이트웨이를 바꿔야 한다 |
| `.20`부터 `.50`까지 같은 형식 | 나머지 4개 부서도 같은 방식 | 하나라도 빠지면 그 부서만 게이트웨이를 잃는다 |
| `interface GigabitEthernet0/1/0`, `0/1/1`, `0/1/2` 후 `shutdown` | 기존 모듈 포트 3개를 끈다 | 이 구조에서는 선이 연결되지 않는다. 미사용 포트 차단 원칙이다 |
| `end` | 설정 모드를 한 번에 빠져나와 특권 모드로 간다 | 이어서 `show` 명령으로 확인하기 위해서다 |

스위치 쪽:

| 명령어 | 뜻 | 왜 넣는가 (빠지면 무엇이 깨지나) |
|--------|-----|----------------------------------|
| `vtp domain SAFECORE` | VTP 도메인 이름을 정한다 | VTP는 도메인 이름이 같은 스위치끼리만 정보를 주고받는다. 한 대라도 이름이 다르거나 대소문자가 다르면 그 스위치는 VLAN을 받지 못한다 |
| `vtp mode server` (RND) | RND를 VLAN 정보의 원본으로 정한다 | 2960 기본값도 server다. 명시해서 의도를 분명히 한다. VLAN을 만들고 지우는 일은 이 스위치에서만 한다 |
| `vlan 20` 후 `name QA` 등 (RND) | 서버에 VLAN 20, 30, 40, 50을 이름까지 만든다 | 클라이언트는 서버의 VLAN 목록을 그대로 따른다. 서버에 VLAN 20이 없으면, QA가 클라이언트가 되는 순간 QA의 VLAN 20이 사라지고 QA 포트가 갈 곳을 잃는다. 이름까지 같이 넣는 이유는 클라이언트의 이름도 서버 것으로 바뀌기 때문이다. VLAN 10은 RND에 이미 있어서 넣지 않았다 |
| `vtp mode client` (QA, TS, ADM, SRV) | 서버의 VLAN 정보를 받아 따르는 모드로 바꾼다 | 빠지면 4대가 모두 server로 남는다. 그러면 각자 VLAN을 만들 수 있고, revision이 높은 쪽이 다른 쪽을 덮어쓰는 사고가 날 수 있다. 원본을 하나로 정해야 관리가 된다 |
| `interface fastEthernet 0/1` 후 `switchport mode trunk` (RND) | 라우터로 가는 포트를 트렁크로 바꾼다 | 라우터 Gi0/0/0이 5개 VLAN을 태그로 구분해 받으므로 스위치도 태그를 붙여 보내야 한다. 라우터는 DTP로 협상하지 않으므로 스위치 쪽을 반드시 고정 트렁크로 둬야 한다. 빠지면 액세스 포트로 남아 VLAN 10만 태그 없이 나가고 나머지 부서는 게이트웨이에 닿지 못한다 |
| `switchport mode trunk` (스위치 사이 포트) | 스위치 사이 링크를 트렁크로 고정한다 | 2960 포트 기본값(dynamic auto)끼리는 트렁크가 자동으로 맺히지 않는다. 양쪽 모두 고정해 두면 협상에 의존하지 않는다. 빠지면 체인 아래쪽 부서의 프레임이 라우터까지 올라가지 못한다 |
| `end` | 설정 모드를 빠져나온다 | 확인 명령을 이어서 입력하기 위해서다 |

2960에서 `switchport trunk encapsulation dot1q`는 입력하지 않는다. 2960은 802.1Q만 지원해서 이 명령이 없고, 입력하면 Invalid input 에러가 난다(4번 섹션 실수 2).

**(d) 확인**

단계 14에서 모아서 다룬다.

| `show ip interface brief` | 인터페이스별 주소와 상태 | 서브인터페이스 5개가 up/up이고, 끈 포트는 down이고, WAN은 그대로인지 한 번에 본다. 건너뛰면 WAN을 실수로 건드렸는지 알 수 없다 |
| `show vtp status` | VTP 도메인, 모드, revision, MD5 digest | 5대가 같은 도메인과 같은 데이터베이스를 가졌는지 확인한다. 건너뛰면 도메인 이름 오타 같은 문제를 ping 실패 후에야 알게 된다 |
| `show interfaces trunk` | 트렁크로 동작 중인 포트와 그 위를 지나는 VLAN | 트렁크가 실제로 맺혔는지, 어떤 VLAN이 허용되고 활성인지 본다 |
| `ping 192.168.10.11` (서버팜 PC에서) | 체인의 맨 끝(SRV)에서 맨 앞(RND) 부서 PC로 ping | 가장 긴 경로를 시험하면 중간 스위치 4대의 트렁크와 VLAN 전파, 라우터 서브인터페이스 2개(.50과 .10)를 한 번에 검증할 수 있다 |

**(d) 출력 읽는 법과 실제 결과**

- `show ip interface brief`: Gi0/0/0.10부터 .50까지 Status와 Protocol이 up/up이어야 한다. 실제 결과(로그): Gi0/0/0.10부터 .50까지 모두 up/up, Gi0/0/1과 Gi0/1/0, 0/1/1, 0/1/2는 administratively down, Gi0/1/3(WAN)과 Vlan70은 up/up 그대로 유지되었다.
- `show vtp status`: VTP Domain Name이 SAFECORE, VTP Operating Mode가 서버 1대와 클라이언트 4대, MD5 digest가 5대 모두 같아야 한다. MD5 digest가 같다는 것은 VLAN 데이터베이스 내용이 완전히 같다는 뜻이다. 실제 결과(로그): 5대 모두 MD5 digest가 완전히 일치해서 VTP 동기화가 정상이었다.
- `show interfaces trunk`: Port 열에 트렁크 포트가, Mode가 on, Encapsulation이 802.1q, Status가 trunking으로 나와야 한다. 아래쪽의 VLANs allowed and active 부분에 전파된 VLAN 번호가 보인다. 실제 결과(로그): RND는 Fa0/1과 Fa0/16, QA는 Fa0/1과 Fa0/8, TS는 Fa0/4와 Fa0/8, ADM은 Fa0/4와 Fa0/10, SRV는 Fa0/5가 모두 802.1q trunking 상태였다. VLAN 1, 10, 20, 30, 40, 50 전체가 전파된 것이 확인되었다.
- PC의 ping: Reply from 줄이 4개 나오고 통계에 손실률이 나온다. 실제 결과(로그): Reply 4/4 성공(0% loss). 체인 전체(RND, QA, TS, ADM, SRV)를 거친 통신이 정상이었다.

| `vtp mode transparent` | VTP로 받은 정보를 따르지 않고 자기 VLAN만 관리하는 모드로 바꾼다 | 원래 설계에서는 스위치끼리 연결이 없어 VTP가 필요 없다. 클라이언트 모드로 두면 나중에 같은 도메인에서 revision 번호가 더 높은 스위치가 연결될 때 VLAN 정보가 덮어써질 위험이 남는다 |
| `no vlan 20`, `no vlan 30`, `no vlan 40`, `no vlan 50` (RND) | RND에서 다른 부서 VLAN을 지운다 | RND는 VLAN 10만 쓴다. 쓰지 않는 VLAN을 남겨두면 실수로 포트를 다른 부서 VLAN에 넣을 여지가 생긴다 |
| `interface fastEthernet 0/1` 후 `switchport access vlan 20` 등 (QA, TS, ADM, SRV) | 각 업링크를 자기 부서 VLAN 액세스로 되돌린다 | 업링크가 다시 라우터에 직결되었으므로 단계 8의 상태로 돌린다 |
| `interface fastEthernet 0/8` 후 `switchport mode access`, `shutdown` (QA, TS), `0/10` (ADM) | 체인용 아래쪽 포트를 원래의 미사용 상태로 돌린다 | RND Fa0/16과 같은 이유다. SRV는 체인의 끝이라 아래쪽 포트가 없다 |

**순서가 중요한 부분**

- RND에서 `vtp mode transparent`를 VLAN 삭제보다 먼저 해야 한다. RND가 server인 상태에서 `no vlan 20`을 하면 그 삭제가 클라이언트로 전파되어 QA의 VLAN 20, TS의 VLAN 30 같은 자기 부서 VLAN까지 사라진다. 그러면 그 스위치의 PC 포트가 모두 갈 곳을 잃는다(로그 15번 주의 문구).
- 라우터에서는 서브인터페이스를 먼저 지우고 나서 물리 포트와 SVI에 주소를 다시 준다. 반대로 하면 "overlaps with" 에러가 난다.

## 4. 실제 결과와 실수

### 실수 1. NIM-ES2-4 모듈 포트에 IP를 바로 줄 수 없음

- 상황: 기술지원팀(본사), 경영지원팀, 서버팜이 연결된 Gi0/1/0, 0/1/1, 0/1/2에 온보드 포트처럼 IP를 주려고 했다.
- 증상: `% Incomplete command` 에러가 났다. 어떤 명령에서 이 에러가 났는지는 소스마다 다르게 적혀 있다. 작업계획서는 `ip address`를 바로 할당하려다 났다고 적었고, 개념정리는 `no switchport`가 안 되어서 났다고 적었다. 명령어 로그 1번 섹션은 "`ip address`를 바로 못 받아서"라고만 적었고 에러 문구는 없다(확인 필요). 원인은 확인하지 못했다. 에러 이후 포트에 직접 IP를 주지 않고 VLAN 인터페이스(SVI) 방식으로 해결했다.
- 원인: NIM-ES2-4는 라우터에 꽂는 스위치 모듈이다. 포트가 L2 스위치 포트로 동작해서 포트 자체에 L3 주소를 둘 수 없다. `no switchport`가 이 모듈에서 되지 않았다는 서술은 인수인계 파일에만 있고 명령어 로그에는 없다(확인 필요).
- 해결: 포트를 VLAN에 넣고 그 VLAN의 SVI(`interface vlan X`)에 IP를 줬다(단계 1). WAN 포트 Gi0/1/3도 같은 방식으로 처리했다(단계 3).
- 배운 점: 같은 라우터 안에서도 포트가 어느 하드웨어(온보드인지 모듈인지)에 속하느냐에 따라 설정 방식이 다르다. 설정 전에 포트 종류를 먼저 확인해야 한다.

### 실수 2. 2960에서 `switchport trunk encapsulation dot1q`가 Invalid input

- 상황: 수업 과제에서 스위치 포트를 트렁크로 만들 때, 캡슐화 방식을 먼저 지정하려고 `switchport trunk encapsulation dot1q`를 입력했다.
- 증상: `% Invalid input` 에러(작업계획서 기록).
- 원인: 이 명령은 802.1Q와 ISL 두 방식을 모두 지원하는 스위치(예: 3560 같은 L3 스위치)에서 하나를 고르는 명령이다. 2960은 802.1Q만 지원해서 고를 것이 없고, 그래서 명령 자체가 없다.
- 해결: `switchport mode trunk`만 입력했다(단계 13). 단계 14에서 Encapsulation이 802.1q로 표시되는 것으로 자동 적용이 확인되었다.
- 배운 점: 교재나 인터넷의 명령을 그대로 옮기기 전에 장비 기종이 그 명령을 지원하는지 봐야 한다.

### 실수 3. 서브인터페이스 설정 중 "overlaps with" 에러

- 상황: 수업 과제에서 SC-HQ-R1에 서브인터페이스 Gi0/0/0.20부터 .50을 만들고 192.168.20.1 같은 주소를 넣었다.
- 증상: "overlaps with" 에러가 났다. 로그와 작업계획서에는 `% overlaps with`까지만 적혀 있고 에러 전문(어느 인터페이스와 겹친다고 나왔는지)은 기록되어 있지 않다.
- 원인: 라우터는 한 장비 안에서 두 인터페이스가 같은 대역에 속하는 것을 허용하지 않는다. 그런데 그 시점에 Gi0/0/1에는 192.168.20.1/24가, Vlan30, Vlan40, Vlan50 SVI에는 30.1, 40.1, 50.1이 그대로 있었다.
- 해결: Gi0/0/1의 IP 제거(`no ip address`)와 SVI 3개 삭제(`no interface Vlan30` 등)를 서브인터페이스 설정보다 먼저 하는 순서로 바꿨다(단계 13 블록이 수정된 순서다). 원복할 때도 같은 규칙을 반대 방향으로 지켜 서브인터페이스를 먼저 지웠다(단계 15).
- 배운 점: 주소를 옮길 때는 "먼저 비우고 나중에 채운다". 순서만 바꿔도 에러가 사라진다.

### 실수 4. WAN 포트가 설계와 다름

- 상황: 설계상 본사 WAN 포트는 Gi0/0/2였다.
- 발견: `show cdp neighbors`로 보니 실제로는 Gi0/1/3(모듈 포트)에 연결되어 있었다.
- 해결: Gi0/1/3에 VLAN 70과 SVI 방식으로 설정했다(단계 3).
- 배운 점: 설정은 설계 문서가 아니라 실제 배선 기준으로 한다. CDP는 그 실제 배선을 가장 빠르게 보여준다.

### 실수 5. 스위치 포트 범위를 잘못 입력

- SC-SW-QA: VLAN 할당 범위를 0/1-7이 아니라 0/1-17로 넣었다. `interface range fastEthernet 0/8-17` 후 `no switchport access vlan`으로 되돌렸다(단계 8).
- SC-SW-SRV: shutdown 범위에 TSBR용 범위(0/10-24)를 넣어서 Fa0/6부터 Fa0/9가 켜진 채로 남았다. `interface range fastEthernet 0/6-9` 후 `shutdown`으로 추가했다(단계 12).
- 배운 점: 장비마다 범위가 다르면 복사해서 붙이는 과정에서 다른 장비의 값이 들어간다. 장비별 블록을 따로 만들고, 입력 후 `show` 명령으로 반드시 확인한다.

### 결과 6. 원복 후 첫 ping 50% 손실

- 상황: 원복 직후 연구개발팀 PC에서 서버팜 PC(192.168.50.11)로 ping했다.
- 결과: 1차는 4개 중 2개 timeout(50% loss), 2차는 4/4 성공(0% loss).
- 원인으로 본 것: 포트 설정을 바꾼 직후라 ARP를 새로 조회하는 시간과 STP가 포트를 포워딩 상태로 바꾸는 지연이 겹친 일시적 현상으로 판단했다. 이것은 로그에 "판단"으로 적힌 추정이고, 원인을 따로 측정해 확인하지는 않았다(확인 필요).
- 일반적인 설명: 스위치 포트가 새로 올라오면 STP는 루프가 없는지 확인하는 동안(listening, learning 단계) 포트가 데이터를 넘기지 않는다. 그동안 보낸 패킷은 유실된다. 또 PC와 라우터는 상대 MAC 주소를 ARP로 다시 배워야 해서 첫 패킷이 늦거나 유실될 수 있다.
- 배운 점: 구성 변경 직후 한 번의 실패를 바로 장애로 단정하지 않고 재시도로 확인한다. 반대로 재시도에서도 실패하면 그때는 설정을 의심한다.

## 5. 면접 질문과 답변 요지

**Q1. VLAN은 왜 쓰나요?**
같은 물리 스위치 위에서 네트워크를 논리적으로 나누기 위해서다. VLAN마다 브로드캐스트 도메인이 따로 생겨 불필요한 브로드캐스트가 줄고, 부서 간 통신은 반드시 라우터를 거치게 되어 그 지점에서 통제(ACL)를 걸 수 있다. SafeCore에서는 연구개발팀 소스코드와 경영지원팀 인사 자료를 다른 부서와 분리하는 기반으로 썼다.

**Q2. 액세스 포트와 트렁크 포트의 차이는?**
액세스 포트는 VLAN 하나에만 속하고 태그 없이 프레임을 보낸다. 트렁크 포트는 여러 VLAN의 프레임을 802.1Q 태그로 구분해서 한 선으로 보낸다. 메인 설계에서는 모든 스위치 포트가 액세스였고, 수업 과제의 체인 구조에서만 스위치 사이와 라우터 쪽 링크를 트렁크로 썼다.

**Q3. 같은 라우터인데 어떤 포트는 직접 IP를 주고 어떤 포트는 SVI를 썼나요?**
포트가 속한 하드웨어가 달라서다. ISR4331의 온보드 포트(Gi0/0/0, Gi0/0/1)는 라우티드 포트라서 바로 IP를 준다. NIM-ES2-4 모듈 포트(Gi0/1/0부터 0/1/3)는 스위치 포트라서 IP를 직접 받지 못한다. 실제로 IP를 주려다 에러가 났고, VLAN에 포트를 넣고 SVI에 IP를 주는 방식으로 해결했다.

**Q4. Router-on-a-Stick과 전용 포트 방식의 차이, 그리고 왜 전용 포트를 메인으로 했나요?**
Router-on-a-Stick은 라우터 포트 하나에 트렁크를 받고 서브인터페이스로 VLAN을 나눈다. 포트는 아끼지만 모든 부서 간 트래픽이 한 선에 몰리고, 그 포트 하나가 고장 나면 전 부서가 동시에 끊긴다. 전용 포트는 부서마다 라우터 포트를 쓴다. 실제 토폴로지가 이미 부서별 전용 포트였고, 병목과 단일 장애점이 없어서 메인으로 택했다. Router-on-a-Stick은 수업 과제로 구성하고 검증까지 한 뒤 되돌렸다.

**Q5. 서브인터페이스 설정에서 "overlaps with" 에러가 났을 때 어떻게 했나요?**
같은 라우터 안에서 두 인터페이스가 같은 대역을 가질 수 없어서 난 에러였다. QA 물리 포트와 SVI 3개에 같은 주소가 남아 있었다. 기존 주소를 먼저 지우고 서브인터페이스를 만드는 순서로 바꿔 해결했고, 원복할 때도 서브인터페이스를 먼저 지웠다.

**Q6. 2960에서 `switchport trunk encapsulation dot1q`가 안 되는 이유는?**
2960은 802.1Q만 지원하므로 캡슐화를 고르는 명령이 없다. ISL과 802.1Q를 둘 다 지원하는 스위치에서만 필요한 명령이다. `switchport mode trunk`만 넣으면 자동으로 802.1Q로 동작한다.

**Q7. 체인 구조에서 VTP는 왜 필요했나요?**
중간 스위치가 자기 부서가 아닌 VLAN의 프레임도 트렁크로 넘겨야 하기 때문이다. 스위치는 자기 VLAN 데이터베이스에 없는 VLAN은 트렁크로 넘기지 않는다. 그래서 5대 모두 VLAN 10부터 50까지 알아야 했고, VTP로 RND(서버)에서 나머지(클라이언트)로 전파했다. MD5 digest가 5대 모두 일치하는 것으로 동기화를 확인했다.

**Q8. VTP의 위험은?**
configuration revision이 더 높은 스위치가 같은 도메인에 연결되면 그 스위치의 VLAN 정보로 전체가 덮어써질 수 있다. 실수로 VLAN이 다 사라지면 전 부서가 끊긴다. 그래서 원복할 때 transparent로 바꿨고, RND에서는 transparent 전환을 VLAN 삭제보다 먼저 해서 삭제가 다른 스위치로 전파되지 않게 했다.

**Q9. 정적 경로를 본사에는 1줄, 지사에는 5줄 넣은 이유는?**
라우터는 직접 연결된 대역은 이미 안다. 본사 라우터에게 본사 5개 부서는 모두 직접 연결된 대역이고 모르는 것은 지사 1개다. 지사 라우터는 반대로 본사 5개를 모른다. 갈 길과 돌아올 길이 모두 있어야 통신이 되므로 양쪽에 다 넣었다.

**Q10. 정적 라우팅의 한계는?**
대역이 늘 때마다 양쪽에 사람이 추가해야 하고, next-hop 너머의 장애를 스스로 알지 못한다. 3일차에는 회선이 하나라서 WAN이 끊기면 본사와 지사가 완전히 끊긴다. 4일차에 백업 회선과 floating static route로, 5일차에 RIPv2로 이 한계를 다뤘다.

**Q11. 스위치에 관리 IP와 `ip default-gateway`를 넣은 이유는?**
L2 스위치는 포트에 IP가 없어서 원격 접속을 받을 주소를 SVI에 둔다. `ip default-gateway`가 없으면 같은 VLAN에서는 접속되지만 다른 대역에서 접속하면 스위치가 응답을 돌려보낼 길을 모른다. 스위치는 라우팅을 하지 않으므로 `ip route`가 아니라 이 명령을 쓴다.

**Q12. `enable secret`과 `enable password`의 차이, 그리고 텔넷의 문제는?**
`enable secret`은 해시로 저장되고 `enable password`는 평문으로 저장된다. 그래서 secret을 썼다. 텔넷은 접속 과정 전체가 평문이라 중간에서 비밀번호가 보인다. 실무에서는 SSH로 바꾸고, vty에 ACL을 걸어 관리 PC에서만 접속하게 해야 한다.

**Q13. 안 쓰는 포트를 왜 shutdown했나요?**
빈 포트에 누군가 장비를 꽂는 순간 내부망에 들어오는 것을 막기 위해서다. 특히 미사용 포트는 기본 VLAN 1에 있어서 관리 트래픽과 섞일 수 있다. 다만 shutdown만으로는 누가 `no shutdown`을 하면 다시 열리므로, 사용하지 않는 별도 VLAN으로 옮기는 것까지 하는 것이 더 안전하다.

**Q14. 원복 후 첫 ping이 50% 실패했는데 장애라고 보지 않은 이유는?**
포트 설정을 바꾼 직후에는 STP가 포트를 포워딩 상태로 바꾸는 시간과 ARP를 다시 배우는 시간이 있다. 그 사이의 유실로 판단하고 재시도했고, 2차에서 4/4가 성공했다. 다만 원인을 측정으로 확인한 것은 아니라서, 면접에서는 "추정했고 재시도로 검증했다"고 정확히 말한다.

**Q15. CDP는 어떻게 활용했고 위험은 무엇인가요?**
설계상 WAN 포트는 Gi0/0/2였는데 CDP로 실제는 Gi0/1/3이라는 것을 찾았다. 스위치마다 업링크 포트도 CDP로 확인했다. 하지만 CDP는 장비 이름, 기종, IOS 정보를 이웃에게 알려주므로 외부와 닿는 포트에서는 꺼야 한다.

## 6. 한계와 더 깊게 갈 방향

| 한계 | 왜 문제인가 | 더 깊게 갈 방향 |
|------|-------------|-----------------|
| 연구개발팀이 다른 부서와 통신 가능 | 요구사항(소스코드 유출 방지)과 어긋난다. 3일차는 의도적으로 열어둔 상태다 | SC-HQ-R1에 확장 ACL을 걸어 10 대역과 다른 부서 대역 사이를 막는다. 지사 쪽 정적 경로 중 10, 40 대역은 업무상 필요 없으므로 ACL로 막거나 경로 자체를 재검토한다 |
| 텔넷 평문 관리 | 비밀번호가 네트워크에 그대로 흐른다 | SSH(도메인 이름, RSA 키, 로컬 사용자, `transport input ssh`)로 전환한다 |
| 모든 장비에 같은 실습용 비밀번호 | 하나가 새면 전부 뚫린다. 누가 접속했는지 구분도 안 된다 | 장비별 비밀번호, `username` 기반 로컬 계정, 나중에는 AAA 서버를 검토한다 |
| line 비밀번호가 설정 파일에 평문 | `show running-config`를 본 사람은 비밀번호를 안다 | `service password-encryption`으로 가린다. 강한 암호화는 아니므로 SSH와 로컬 계정 방식이 근본 대책이다 |
| vty 접속 출발지 제한 없음 | 관리 IP에 닿는 모든 PC가 로그인을 시도할 수 있다 | vty에 `access-class`로 관리용 대역만 허용한다 |
| 관리 IP가 사용자 VLAN 안에 있음 | 일반 PC와 관리 트래픽이 같은 대역에 섞인다 | 별도 관리 VLAN을 두고 관리 PC만 그 VLAN에 접근하게 한다 |
| 미사용 포트가 VLAN 1에 있고 shutdown만 됨 | `no shutdown` 한 줄로 다시 열린다 | 미사용 포트를 사용하지 않는 별도 VLAN으로 옮기고, port-security로 MAC 수를 제한한다 |
| 액세스 포트의 DTP | `switchport mode access`로 고정했지만 협상 프레임 차단까지는 확인하지 않았다 | `switchport nonegotiate`를 검토한다(확인 필요) |
| CDP가 전 포트에서 켜져 있음 | 장비 정보가 이웃에게 노출된다 | 사용자 포트와 외부 포트에서 `no cdp enable`을 검토한다 |
| WAN 회선 1개 | 3일차 시점에는 이 회선이 끊기면 본사와 지사가 완전히 끊긴다 | 4일차에 시리얼 백업 회선과 AD 250 floating static route로 보완했다 |
| 정적 경로의 확장성 | 대역이 늘 때마다 양쪽에 수동 추가해야 한다. 지사 경로 5줄은 요약도 가능하다 | 5일차에 주 회선을 RIPv2로 전환했다(예비 경로는 정적 유지). 정적 경로를 유지한다면 요약 경로(본사 대역을 묶는 마스크)나 기본 경로를 검토한다 |
| 본사와 지사 사이 트래픽 암호화 없음 | 티켓 내용이 WAN에서 엿보이거나 바뀔 수 있다 | IPsec VPN을 검토한다(요구사항 4번 티켓 무결성) |
| 수업 과제 흔적 | 본사 스위치 5대에 VTP 도메인 이름 SAFECORE가 남아 있고(로그에 도메인 제거 명령이 없다), QA, TS, ADM, SRV에는 VTP로 받은 다른 부서 VLAN이 남아 있을 수 있다(확인 필요) | `show vlan brief`로 확인하고 불필요한 VLAN을 지운다 |
| 검증 범위 | 텔넷은 1대만, ping은 일부 조합만 로그에 남아 있다 | 6개 대역 전체 조합 ping과 스위치 6대 텔넷을 표로 기록한다. `show ip route`와 `show startup-config` 출력도 남긴다 |
| 첫 ping 유실의 원인 | 추정만 했다 | 포트 변경 직후 `show spanning-tree`로 포트 상태 변화를, `show arp`나 PC의 `arp -a`로 ARP 학습을 직접 관찰한다. PortFast를 사용자 포트에 거는 것도 검토한다 |

## 7. 보안 3요소(기밀성, 무결성, 가용성)와의 연결

`01_요구사항/프로젝트_계획서.md` 4번 표의 보호 대상과 연결해서 정리한다.

### 기밀성

| 3일차 설정 | 기여 | 남은 약점 |
|-----------|------|-----------|
| 부서별 VLAN 분리(단계 8) | 부서마다 브로드캐스트 도메인이 나뉘어, 다른 부서의 L2 트래픽이 보이지 않는다. 제품 소스코드(연구개발)와 인사 자료(경영지원)를 분리하는 기반이다 | 라우터에서 모든 부서 간 통신이 열려 있다. ACL이 들어가기 전까지는 연구개발 대역에 다른 부서가 닿을 수 있다 |
| enable secret, console과 vty 비밀번호(단계 10) | 장비 설정과 라우팅 정보를 아무나 볼 수 없게 한다 | 텔넷이 평문이라 비밀번호가 노출될 수 있다. line 비밀번호는 설정 파일에 평문이다 |
| 미사용 포트 shutdown(단계 12) | 빈 포트로 들어와 내부 트래픽을 엿보는 경로를 막는다 | shutdown만 되어 있고 VLAN 1에 남아 있다 |
| CDP 사용(단계 3, 7) | 기밀성에는 오히려 약점이다. 장비 정보가 이웃에게 노출된다 | 외부 포트에서 끄는 작업이 남아 있다 |

### 무결성

| 3일차 설정 | 기여 | 남은 약점 |
|-----------|------|-----------|
| 비밀번호와 enable secret(단계 10) | 요구사항의 "장비 설정: 아무나 라우터에 접속해 설정을 바꾼다"에 대한 1차 대책이다. 특권 모드 없이는 설정을 바꿀 수 없다 | 로그상 비밀번호 설정은 스위치 6대 기준이다. 라우터 2대에 적용되었는지는 3일차 로그에 없다(확인 필요). 같은 비밀번호를 공유해 누가 바꿨는지 추적할 수 없다 |
| 설정 저장(단계 11) | 재부팅 후에도 의도한 설정 그대로 올라온다. 저장하지 않으면 재부팅 때 비밀번호까지 사라진 무방비 상태로 켜진다 | 저장본을 장비 밖에 백업한 기록은 없다 |
| VTP를 transparent로 되돌림(단계 15) | revision이 높은 스위치가 연결되어 VLAN 정보가 덮어써지는 위험을 줄인다 | 도메인 이름이 남아 있다 |
| 원복 순서 지키기(단계 15) | VLAN 삭제가 다른 스위치로 전파되어 의도치 않게 설정이 바뀌는 것을 막았다 | 사람이 순서를 기억해야 한다. 변경 절차서로 남기는 것이 좋다 |
| 본사와 지사 사이 정적 경로(단계 5) | 티켓 시스템에 닿는 길을 열었다 | 전송 구간 암호화나 무결성 검증이 없다. 요구사항의 "티켓 내용이 엿보이거나 바뀐다"는 아직 대책이 없다 |

### 가용성

| 3일차 설정 | 기여 | 남은 약점 |
|-----------|------|-----------|
| 부서 게이트웨이(단계 1, 4)와 정적 경로(단계 5) | 지사 기술지원팀이 본사 티켓 시스템과 파일 서버(서버팜)를 쓸 수 있게 되었다. 요구사항을 충족하는 핵심이다 | WAN 회선이 1개뿐이라 끊기면 지사 업무가 멈춘다(4일차에 보완) |
| 전용 포트 방식 유지(단계 15) | Router-on-a-Stick처럼 포트 하나에 모든 부서가 몰리지 않는다. 포트 하나의 장애가 한 부서에만 영향을 준다 | 라우터 자체는 1대라서 라우터가 멈추면 본사 전체가 멈춘다 |
| 관리 IP와 텔넷(단계 10) | 장애 때 콘솔 케이블 없이 원격으로 들어가 빨리 조치할 수 있다 | 관리 경로가 사용자 망과 같아서, 사용자 망이 끊기면 관리 접속도 같이 끊긴다 |
| `no ip domain-lookup`(단계 6) | 장애 대응 중 오타로 인한 지연을 없앤다 | 적용 확인 기록이 없다 |
| 원복 후 재시도 검증(단계 15) | 원복한 뒤 같은 시험을 다시 해서 결과를 확인했다 | STP 수렴 지연 자체를 줄이는 설정(PortFast)은 아직 없다 |
