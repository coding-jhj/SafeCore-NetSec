## 2. 왜 하는가

- 2일차까지는 부서별 대역을 설계만 해 둔 상태였다. 스위치에는 VLAN이 입력되어 있지 않았고 본사와 지사 사이에는 가는 길이 없었다.
- PC는 자기 대역 밖으로 나가려면 게이트웨이(라우터 주소)가 필요하다. 게이트웨이가 없으면 부서 안에서만 통신되고 다른 부서나 지사로는 한 패킷도 나가지 못한다.
- 라우터는 자기가 모르는 대역으로 가는 패킷을 버린다. 본사 라우터는 지사 대역(192.168.60.0/24)을, 지사 라우터는 본사 대역 5개를 처음에는 모른다. 그래서 정적 경로로 알려줘야 한다.
- 장비에 아무나 접속해 설정을 바꿀 수 있으면 네트워크 전체가 위험하다. 그래서 비밀번호, 관리 IP, 미사용 포트 차단도 같이 넣었다.

| 요구사항 | 3일차에서 한 것 |
|----------|-----------------|
| 부서마다 네트워크를 나눈다 | 스위치 6대에 부서별 VLAN을 만들고 포트를 할당 |
| 지사 기술지원팀은 본사의 티켓 시스템과 파일 서버를 쓴다 | WAN(VLAN 70)을 연결하고 양쪽 라우터에 정적 경로를 넣어 지사에서 본사 서버팜(192.168.50.0/24)까지 길을 열었다 |
| 연구개발팀은 다른 부서와 통신할 일이 없다 | 일부러 막지 않았다. 먼저 전체 라우팅을 연결하고 차단(ACL)은 보안 작업 단계에서 한다 |
| 장비 설정 무결성: 아무나 라우터에 접속해 설정을 바꾼다 | enable secret, console과 vty 비밀번호, 미사용 포트 shutdown. 비밀번호 설정은 스위치 6대 기준으로 기록되어 있다 |

## 3. 핵심 개념

### 3-1. VLAN
- 물리적으로 같은 스위치에 꽂혀 있어도 논리적으로 네트워크를 나누는 기술이다. VLAN마다 브로드캐스트 도메인이 따로 생긴다.
- 서로 다른 VLAN끼리는 L3 장비(라우터)를 거쳐야 통신한다. 그래서 라우터가 부서 간 통신의 통제 지점이 되고 나중에 ACL을 걸 자리가 된다.
- 2960 스위치에서는 `switchport access vlan X`를 입력할 때 그 VLAN이 없으면 자동으로 만들어진다.

### 3-2. 액세스 포트와 트렁크 포트
- 액세스 포트는 VLAN 하나에만 속하는 포트이고 PC가 꽂힌다. 프레임에 VLAN 태그가 붙지 않는다.
- 트렁크 포트는 여러 VLAN의 프레임을 한 선으로 나른다. IEEE 802.1Q 태그(VLAN ID 12비트, 1 - 4094)를 붙여 구분한다.
- 네이티브 VLAN은 트렁크에서 태그 없이 지나가는 VLAN이다. 기본값은 VLAN 1이다. 양쪽 설정이 어긋나면 문제가 생기고 VLAN 호핑 공격과도 관련된다(후속 하드닝).
- Catalyst 2960은 802.1Q만 지원해서 캡슐화 방식을 고르는 `switchport trunk encapsulation dot1q` 명령 자체가 없다(실수 2).

### 3-3. VLAN 사이 통신(Inter-VLAN routing)의 세 가지 방식

| 방식 | 구조 | 장점 | 단점 |
|------|------|------|------|
| 전용 포트 | 부서마다 라우터 포트 하나씩 | 단순하고 한 선에 트래픽이 몰리지 않는다 | 부서 수만큼 라우터 포트 필요 |
| Router-on-a-Stick | 라우터 포트 하나를 트렁크로 받고 서브인터페이스로 나눈다 [2] | 라우터 포트를 아낀다 | 모든 부서 간 트래픽이 한 선에 몰린다 |
| SVI(L3 스위치) | 스위치 안의 가상 인터페이스에 IP를 준다 | 라우팅을 스위치 내부에서 처리 | L3 스위치 필요 |

- 본사 라우터(SC-HQ-R1, ISR4331)는 토폴로지가 이미 부서별 전용 포트 구조였다. 그래서 원래 계획(Router-on-a-Stick)을 바꿔 전용 포트 방식으로 갔다.
- 온보드 포트(Gi0/0/0 연구개발, Gi0/0/1 QA)는 일반 라우티드 포트라 포트에 바로 IP를 준다.
- NIM-ES2-4 모듈 포트(Gi0/1/0 - Gi0/1/3)는 스위치 포트 성격이라 포트에 IP를 직접 줄 수 없다. 포트를 VLAN에 넣고 그 VLAN의 SVI(`interface vlan X`)에 IP를 줬다. 라우터 안에서 SVI가 그 부서의 게이트웨이가 된다.
- SVI는 일반적으로 해당 VLAN에 up 상태인 포트가 하나 이상 있어야 up/up이 된다.

### 3-4. VTP
- VLAN 정보를 스위치끼리 트렁크로 자동 전파하는 시스코 프로토콜이다. 같은 도메인 이름 안에서만 동작한다.

| 모드 | VLAN 생성과 삭제 | 받은 정보를 따르나 | 받은 정보를 넘기나 |
|------|------------------|---------------------|---------------------|
| server | 가능 | 따른다 | 넘긴다 |
| client | 불가능 | 따른다 | 넘긴다 |
| transparent | 가능(자기 것만) | 따르지 않는다 | 넘긴다(VTP 버전에 따라 다르다) |

- 위험: configuration revision 번호가 더 높은 스위치가 같은 도메인에 연결되면 그 스위치의 VLAN 정보로 도메인 전체가 덮어써질 수 있다. VLAN이 전부 사라지는 운영 사고가 된다 [1].
- transparent 모드는 VTP를 끄고 자기 VLAN만 관리할 때 쓴다 [1].

### 3-5. 정적 라우팅
- 관리자가 "이 목적지 대역은 이 next-hop으로 보내라"를 직접 적는 방식이다. 형식은 `ip route <목적지 대역> <마스크> <next-hop>`.
- 장점은 단순하고 라우터 부하가 거의 없고 동작을 예측하기 쉽다는 점이다.
- 단점은 대역이 늘 때마다 양쪽에 수동으로 추가해야 하고, 경로 너머의 장애를 스스로 감지하지 못한다는 점이다. 5일차에 RIPv2로 이 단점을 다룬다.
- 통신은 갈 때와 올 때가 모두 있어야 성립한다. 한쪽에만 경로가 있으면 ping은 실패한다.
- 라우팅 테이블 표기: `C`는 직접 연결된 대역, `L`은 라우터 자신의 인터페이스 주소(/32), `S`는 정적 경로.

### 3-6. CDP
- 시스코 장비끼리 직접 연결된 이웃의 이름, 기종, 포트 정보를 주고받는 L2 프로토콜이다.
- 3일차에는 실제로 어느 포트에 선이 꽂혔는지 확인하는 데 썼다. 설계와 실제 배선이 달랐던 것을 CDP로 찾았다(단계 3).
- 이웃에게 장비 정보를 알려주므로 정보 노출 위험이 있어, 신뢰하지 않는 네트워크와 닿는 인터페이스에서는 끄도록 권고된다(`no cdp enable`) [3].

### 3-7. ARP와 첫 ping 유실
- ARP는 IP 주소로 MAC 주소를 알아내는 프로토콜이다 [6]. 같은 대역 안에서 프레임을 보내려면 상대(또는 게이트웨이)의 MAC이 필요하다.
- 처음 보내는 ping의 앞쪽 패킷이 유실되는 경우가 있는데 ARP 학습을 기다리는 동안 생기는 경우가 많다.

### 3-8. 장비 관리 접속과 비밀번호
- 텔넷은 원격으로 장비 CLI에 접속하는 방법이다. 평문으로 전송되어 비밀번호가 그대로 보일 수 있다. 실무에서는 SSH를 쓴다. 학습 단계라 텔넷으로 구성했고 SSH 전환은 후속 하드닝 항목이다.
- `enable secret`은 해시로 저장되고 `enable password`는 되돌릴 수 있는 약한 방식으로 저장된다. Cisco는 `enable secret` 사용을 권한다 [4]. line의 `password`는 설정 파일에 평문으로 보인다.
- 스위치는 L2 장비지만 관리용으로 SVI 하나에 IP를 받을 수 있다. 이 IP로 텔넷에 접속한다.

### 단계 1. 본사 라우터(SC-HQ-R1) 부서 VLAN과 SVI

**목적**: 기술지원팀(본사), 경영지원팀, 서버팜이 연결된 NIM-ES2-4 모듈 포트는 포트에 바로 IP를 받지 못한다. 포트를 부서 VLAN의 액세스 포트로 만들고 그 VLAN의 SVI에 게이트웨이 IP를 준다.

연구개발(Gi0/0/0, 192.168.10.1)과 QA(Gi0/0/1, 192.168.20.1)는 온보드 포트라 포트에 직접 IP가 들어가 있다. 이 두 포트에 IP를 처음 넣은 명령은 기록에 없다(6장). 같은 형식의 명령이 단계 15에 있다.

**SC-HQ-R1**
```
! 기술지원팀 본사, VLAN 30
interface GigabitEthernet0/1/0
switchport mode access
switchport access vlan 30
exit
interface vlan 30
ip address 192.168.30.1 255.255.255.0
no shutdown
exit

! 경영지원팀, VLAN 40
interface GigabitEthernet0/1/1
switchport mode access
switchport access vlan 40
exit
interface vlan 40
ip address 192.168.40.1 255.255.255.0
no shutdown
exit

! 서버팜, VLAN 50
interface GigabitEthernet0/1/2
switchport mode access
switchport access vlan 50
exit
interface vlan 50
ip address 192.168.50.1 255.255.255.0
no shutdown
exit
```

| 명령어 | 뜻 | 왜 넣는가 (빠지면 깨지는 것) |
|--------|-----|------------------------------|
| `interface GigabitEthernet0/1/0` | 해당 모듈 포트의 설정 모드 | 이후 명령이 이 포트에 적용된다. 다른 포트에서 입력하면 엉뚱한 부서가 바뀐다 |
| `switchport mode access` | 포트를 VLAN 하나에만 속하는 액세스 포트로 고정 | 고정하지 않으면 DTP로 트렁크를 협상할 여지가 남는다. 부서 스위치 하나만 연결되는 포트라 액세스로 못 박는다 |
| `switchport access vlan 30` | 포트를 VLAN 30에 넣는다 | 빠지면 포트가 VLAN 1에 남아 VLAN 30의 SVI와 연결되지 않아 PC가 게이트웨이에 닿지 못한다 |
| `exit` | 인터페이스 설정 모드에서 나온다 | 다음 인터페이스로 넘어가는 정리 동작 |
| `interface vlan 30` | VLAN 30의 가상 인터페이스(SVI) 생성과 진입 | 모듈 포트에는 IP를 줄 수 없어서 IP를 받을 자리가 SVI다 |
| `ip address 192.168.30.1 255.255.255.0` | SVI에 게이트웨이 주소 | 기술지원팀 PC의 기본 게이트웨이. 빠지거나 틀리면 PC가 대역 밖으로 나가지 못한다 |
| `no shutdown` | 인터페이스를 켠다 | 새로 만든 SVI는 기본이 꺼져 있다. 빠지면 administratively down |

VLAN 40, 50 블록도 번호와 주소만 다르고 같은 이유로 들어간다. 라우터에서 `vlan 30` 같은 생성 명령을 따로 입력한 기록은 없다.

**확인**: `show ip interface brief`
- Status와 Protocol이 둘 다 up이면 정상이다. administratively down이면 `no shutdown` 누락, up/down이면 상위 계층 문제이고 SVI라면 그 VLAN에 활성 포트가 없는 경우가 많다.
- 결과: 연구개발(.10), QA(.20), 기술지원 본사(.30), 경영지원(.40), 서버팜(.50) 인터페이스가 모두 up/up.

### 단계 2. 장비 호스트네임 설정

**목적**: 장비마다 이름을 붙여 프롬프트, CDP 이웃 정보, 설정 파일에서 어느 장비인지 바로 알 수 있게 한다. 본사 라우터의 `hostname SC-HQ-R1`은 3일차 이전에 설정된 것으로 보인다(6장).

```
! SC-BR-R1 (지사 라우터)
hostname SC-BR-R1
! SC-SW-RND (연구개발팀 스위치)
hostname SC-SW-RND
! SC-SW-QA (품질보증팀 스위치)
hostname SC-SW-QA
! SC-SW-TS (기술지원팀 본사 스위치)
hostname SC-SW-TS
! SC-SW-ADM (경영지원팀 스위치)
hostname SC-SW-ADM
! SC-SW-SRV (서버팜 스위치)
hostname SC-SW-SRV
! SC-SW-TSBR (기술지원팀 지사 스위치)
hostname SC-SW-TSBR
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `hostname SC-BR-R1` | 장비 이름 설정. 프롬프트가 `SC-BR-R1(config)#`로 바뀐다 | 기본 이름(Router, Switch)이면 8대가 구분되지 않아 엉뚱한 장비에 명령을 넣는 실수가 생기고 CDP 결과에서도 이웃을 알 수 없다 |

이름 규칙은 `SC-장비종류-부서`: SC는 SafeCore, R은 라우터, SW는 스위치, HQ는 본사, BR은 지사다. 입력 즉시 프롬프트가 바뀌고, 이웃 장비의 `show cdp neighbors` Device ID에 새 이름이 나온다.

### 단계 3. 본사-지사 WAN 링크, VLAN 70

**목적**: 본사 라우터와 지사 라우터를 이더넷으로 연결하고 그 구간에 192.168.70.0/24 대역을 준다. 이 링크가 정적 경로의 next-hop이 된다.

설계상으로는 SC-HQ-R1의 Gi0/0/2와 SC-BR-R1의 Gi0/1을 연결하려 했다. `show cdp neighbors`로 확인하니 실제로는 SC-HQ-R1의 Gi0/1/3(NIM 모듈 포트)에 연결되어 있었다. 모듈 포트라 단계 1과 같은 VLAN과 SVI 방식으로 설정했다. 대역은 기존 부서 대역 체계에 맞춰 VLAN 70, /24로 정했다.

**SC-HQ-R1**
```
interface GigabitEthernet0/1/3
switchport mode access
switchport access vlan 70
exit
interface vlan 70
ip address 192.168.70.1 255.255.255.0
no shutdown
exit
```

**SC-BR-R1**
```
interface GigabitEthernet0/1
ip address 192.168.70.2 255.255.255.0
no shutdown
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `interface GigabitEthernet0/1/3` | 실제로 지사와 연결된 모듈 포트 | 설계의 Gi0/0/2에 설정하면 선이 없는 포트에 IP가 들어가 WAN이 끊긴 채로 남는다. CDP로 확인한 실제 포트에 넣는다 |
| `switchport mode access` | 액세스 포트로 고정 | WAN 구간은 VLAN 하나만 쓰므로 트렁크 협상 여지를 없앤다 |
| `switchport access vlan 70` | WAN 전용 VLAN 70에 넣는다 | 빠지면 VLAN 1에 남아 SVI 70과 연결되지 않는다 |
| `interface vlan 70` | WAN용 SVI | 모듈 포트 대신 IP를 받을 자리 |
| `ip address 192.168.70.1 255.255.255.0` | 본사 쪽 WAN 주소 | 지사 라우터가 본사로 보낼 때 쓰는 next-hop(단계 5). 빠지면 지사의 정적 경로가 갈 곳이 없다 |
| `no shutdown` | SVI를 켠다 | 빠지면 WAN 전체가 down |
| `interface GigabitEthernet0/1` (지사) | 지사 라우터의 WAN 포트 | 2901의 이 포트는 일반 라우티드 포트라 VLAN 없이 바로 IP를 줄 수 있다 |
| `ip address 192.168.70.2 255.255.255.0` (지사) | 지사 쪽 WAN 주소 | 본사가 지사로 보낼 때 쓰는 next-hop. 본사와 같은 대역이어야 직접 연결된 이웃이 된다 |
| `no shutdown` (지사) | 포트를 켠다 | 라우터 포트는 기본이 꺼져 있다 |

**확인**: `show cdp neighbors`(본사 또는 지사). Device ID는 상대 장비, Local Intrfce는 내 포트, Port ID는 상대 포트다. 설계 문서가 아니라 이 결과가 실제 배선이다. 결과: SC-HQ-R1 Gig0/1/3과 SC-BR-R1 Gig0/1이 연결된 것을 확인했다. WAN 구간만 따로 ping한 기록은 없고, 단계 5의 ping 성공이 이 구간이 살아 있다는 간접 증거다.

### 단계 4. 지사 라우터(SC-BR-R1) 내부 LAN 게이트웨이

**목적**: 지사 기술지원팀(VLAN 60, 192.168.60.0/24) PC의 게이트웨이를 만든다. Gi0/0은 일반 라우티드 포트라 바로 IP를 준다.

**SC-BR-R1**
```
interface GigabitEthernet0/0
ip address 192.168.60.1 255.255.255.0
no shutdown
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `interface GigabitEthernet0/0` | 지사 스위치(SC-SW-TSBR)와 연결된 포트 | 지사 LAN의 출입구 |
| `ip address 192.168.60.1 255.255.255.0` | 지사 기술지원팀 게이트웨이 | 빠지면 지사 PC가 본사로 나갈 수 없고 이 대역이 연결된 대역(C)으로 잡히지 않는다 |
| `no shutdown` | 포트를 켠다 | 빠지면 지사 LAN 전체가 고립된다 |

라우터 포트에 직접 IP를 주는 방식이라 VLAN 60은 라우터 설정에 나타나지 않고 지사 스위치 안에서만 의미가 있다(단계 8). 이 단계만의 확인 출력은 없고 단계 10의 관리 IP 설정과 단계 5 이후 통신으로 간접 확인된다. 직접 확인하려면 `show ip interface brief`에서 Gi0/0이 192.168.60.1로 up/up인지 본다.

### 단계 5. 정적 라우팅

**목적**: 라우터는 자기에게 직접 연결된 대역만 안다. 본사 라우터는 지사 LAN(60 대역)을, 지사 라우터는 본사 LAN 5개(10, 20, 30, 40, 50 대역)를 모른다. 양쪽에 상대 대역으로 가는 길을 적어 준다. 본사 1줄, 지사 5줄인 이유는 각 라우터가 모르는 대역 수가 다르기 때문이다. 본사 입장에서 본사 5개 부서는 모두 직접 연결된 대역이고 모르는 것은 지사 1개다.

**SC-HQ-R1** (지사 네트워크로 가는 길)
```
ip route 192.168.60.0 255.255.255.0 192.168.70.2
```

**SC-BR-R1** (본사 5개 네트워크로 가는 길)
```
ip route 192.168.10.0 255.255.255.0 192.168.70.1
ip route 192.168.20.0 255.255.255.0 192.168.70.1
ip route 192.168.30.0 255.255.255.0 192.168.70.1
ip route 192.168.40.0 255.255.255.0 192.168.70.1
ip route 192.168.50.0 255.255.255.0 192.168.70.1
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `ip route 192.168.60.0 255.255.255.0 192.168.70.2` | 60 대역으로 가는 패킷은 지사 라우터의 WAN 주소로 | 빠지면 본사는 지사로 가는 패킷을 버린다. 지사 PC의 요청이 본사에 도착해도 응답이 지사로 돌아가지 못한다 |
| `ip route 192.168.10.0 ... 192.168.70.1` | 연구개발 대역 | 빠지면 지사에서 연구개발 대역으로 갈 수 없다 |
| `ip route 192.168.20.0 ... 192.168.70.1` | QA 대역 | 빠지면 지사에서 QA 대역으로 갈 수 없다 |
| `ip route 192.168.30.0 ... 192.168.70.1` | 기술지원팀 본사 대역 | 빠지면 본사와 지사 기술지원팀끼리 통신할 수 없다 |
| `ip route 192.168.40.0 ... 192.168.70.1` | 경영지원 대역 | 빠지면 지사에서 경영지원 대역으로 갈 수 없다 |
| `ip route 192.168.50.0 ... 192.168.70.1` | 서버팜 대역 | 요구사항의 핵심. 지사 기술지원팀이 쓰는 티켓 시스템과 파일 서버가 서버팜에 있다 |

연구개발 대역(10)과 경영지원 대역(40) 경로는 요구사항상 지사가 쓸 일이 없지만, "먼저 전체를 연결하고 나중에 ACL로 막는다"는 계획이라 모두 넣었다. next-hop은 상대 라우터의 WAN 주소로 지정했다. 출구 인터페이스만 적는 방식도 있지만 이더넷 구간에서는 next-hop 주소를 적는 쪽이 ARP 동작이 명확하다.

**확인**: SC-BR-R1에서 `ping 192.168.10.1`
- 라우터 ping은 `!`가 성공, `.`가 시간 초과다.
- 결과: 성공. 지사 라우터에서 본사 연구개발 게이트웨이까지 경로가 열렸다.
- 이 ping은 지사 라우터가 출발점이라 출발 주소가 192.168.70.2다. 본사는 70 대역을 직접 알고 있으므로 이 ping의 성공만으로는 본사 쪽 정적 경로(60 대역)까지 검증되지 않는다. 지사 PC(60 대역)에서 본사로 ping해야 양방향이 검증된다.
- `show ip route`를 실행했다면 SC-BR-R1에 `S 192.168.10.0/24 [1/0] via 192.168.70.1` 형태 5줄, SC-HQ-R1에 60 대역 1줄이 보여야 한다. 대괄호 안의 1은 정적 경로의 기본 AD다. 실행 결과는 기록에 없다(6장).

### 단계 6. no ip domain-lookup

**목적**: CLI에서 명령어를 잘못 입력하면 IOS는 그 단어를 호스트 이름으로 보고 DNS 조회를 시도하고, 끝날 때까지 콘솔이 멈춘 것처럼 기다린다. 이 기다림을 없앤다. 8대 전부에 적용을 요청했고 적용 확인 기록은 없다(6장).

```
! SC-HQ-R1
no ip domain-lookup
! SC-BR-R1
no ip domain-lookup
! SC-SW-RND
no ip domain-lookup
! SC-SW-QA
no ip domain-lookup
! SC-SW-TS
no ip domain-lookup
! SC-SW-ADM
no ip domain-lookup
! SC-SW-SRV
no ip domain-lookup
! SC-SW-TSBR
no ip domain-lookup
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `no ip domain-lookup` | 이름을 DNS로 조회하는 기능을 끈다 | 빠지면 오타 하나마다 수십 초씩 기다린다. 통신은 깨지지 않지만 장애 대응 중에는 그 지연이 복구 지연이 된다. 사내 DNS가 없는 실습 환경에서는 조회가 성공할 일도 없다 |

**확인**: 일부러 없는 단어를 입력해 바로 에러가 나오고 기다림이 없으면 적용된 것이다. 설정으로는 `show running-config`에서 `no ip domain-lookup`을 찾는다(IOS 버전에 따라 `no ip domain lookup`으로 표시될 수 있다).

### 단계 7. 스위치 6대의 라우터 업링크 포트 확인(CDP)

**목적**: 스위치마다 어느 포트가 라우터로 올라가는 업링크인지 확인한다. 다음 단계에서 업링크 포트까지 같은 VLAN에 넣어야 PC가 게이트웨이에 닿는다. 설계 문서가 아니라 실제 배선을 기준으로 해야 한다는 것을 단계 3에서 이미 겪었다.

```
! SC-SW-RND, SC-SW-QA, SC-SW-TS, SC-SW-ADM, SC-SW-SRV, SC-SW-TSBR 각각
show cdp neighbors
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `show cdp neighbors` | 직접 연결된 시스코 이웃의 이름, 내 포트, 상대 포트 | 건너뛰면 업링크를 추측으로 정해야 한다. 업링크를 다른 VLAN에 넣거나 shutdown 범위(단계 12)에 넣으면 그 부서 전체가 게이트웨이를 잃는다. TS와 ADM은 Fa0/4, SRV는 Fa0/5가 업링크라 "업링크는 Fa0/1"이라는 추측은 틀렸을 것이다 |

Local Intrfce가 이 스위치의 업링크 포트이고 Device ID와 Port ID가 라우터 이름과 라우터 포트다.

| 스위치 | 업링크 포트 | 상대 | VLAN |
|--------|-------------|------|------|
| SC-SW-RND | Fa0/1 | SC-HQ-R1 Gi0/0/0 | 10 |
| SC-SW-QA | Fa0/1 | SC-HQ-R1 Gi0/0/1 | 20 |
| SC-SW-TS | Fa0/4 | SC-HQ-R1 Gi0/1/0 | 30 |
| SC-SW-ADM | Fa0/4 | SC-HQ-R1 Gi0/1/1 | 40 |
| SC-SW-SRV | Fa0/5 | SC-HQ-R1 Gi0/1/2 | 50 |
| SC-SW-TSBR | Fa0/1 | SC-BR-R1 Gi0/0 | 60 |

### 단계 8. 스위치 6대 VLAN 생성과 포트 할당

**목적**: 스위치의 connected 포트 전체(PC 포트와 업링크 포트)를 그 부서 VLAN의 액세스 포트로 만든다. 업링크 포트가 각 스위치의 connected 범위 안에 있어(단계 7 표) 범위 하나로 한 번에 처리했다. VLAN이 없으면 `switchport access vlan X` 입력 때 자동 생성된다.

```
! SC-SW-RND
interface range fastEthernet 0/1-15
switchport mode access
switchport access vlan 10
exit

! SC-SW-QA
interface range fastEthernet 0/1-7
switchport mode access
switchport access vlan 20
exit

! SC-SW-TS
interface range fastEthernet 0/1-7
switchport mode access
switchport access vlan 30
exit

! SC-SW-ADM
interface range fastEthernet 0/1-9
switchport mode access
switchport access vlan 40
exit

! SC-SW-SRV
interface range fastEthernet 0/1-5
switchport mode access
switchport access vlan 50
exit

! SC-SW-TSBR
interface range fastEthernet 0/1-9
switchport mode access
switchport access vlan 60
exit

! SC-SW-QA (범위 실수 수정: 처음에 0/1-17로 잘못 넣은 것을 되돌림)
interface range fastEthernet 0/8-17
no switchport access vlan
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `interface range fastEthernet 0/1-15` | 여러 포트를 한 번에 설정 | 포트 15개를 하나씩 입력하면 빠뜨리는 포트가 생기고, 빠진 PC는 VLAN 1에 남아 고립된다 |
| `switchport mode access` | 액세스 포트로 고정 | 2960 포트 기본값은 동적 협상 모드다. 고정하지 않으면 누가 스위치를 꽂았을 때 트렁크가 맺혀 여러 VLAN이 노출될 수 있다 |
| `switchport access vlan 10` | 포트를 VLAN 10에 넣고 없으면 VLAN을 만든다 | 빠지면 모든 포트가 VLAN 1에 남아 부서 분리가 안 되고 라우터 SVI와 VLAN 번호가 의미를 잃는다 |
| `no switchport access vlan` | VLAN 지정을 지워 기본 VLAN 1로 | 잘못 넣은 미사용 포트(Fa0/8 - Fa0/17)를 QA VLAN에서 뺀다. 남겨두면 쓰지 않는 포트가 QA 대역에 붙어 단계 12의 shutdown 전까지 꽂으면 바로 QA 망에 들어온다 |

스위치 업링크 포트가 VLAN 10 액세스이고 라우터 Gi0/0/0이 라우티드 포트인 구조다. 라우터 포트에는 VLAN 개념이 없고 태그 없는 프레임만 받는데, 스위치 업링크가 액세스 포트라 태그 없이 내보내므로 두 장비가 맞물린다.

**확인**: 각 스위치 `show vlan brief`. VLAN 번호, Name, Status(active), Ports를 본다. 할당한 포트는 VLAN 1 줄에서 사라지고 부서 VLAN 줄로 옮겨가야 한다. 3일차 메인 구성 시점의 출력은 기록에 없지만 원복 후 결과(단계 15)에서 RND는 VLAN 10에 Fa0/1 - Fa0/15, QA와 TS는 Fa0/1 - Fa0/7, ADM은 Fa0/1 - Fa0/9, SRV는 Fa0/1 - Fa0/5가 남아 이 단계의 범위가 맞았음을 보여 준다. QA의 Fa0/8 - Fa0/17은 VLAN 1로 돌아가지만 `switchport mode access` 설정은 남는다. 동작에는 문제가 없다.

### 단계 9. 스위치 6대 VLAN 이름 지정

**목적**: 단계 8에서 자동 생성된 VLAN은 VLAN0010 같은 기본 이름을 가진다. 부서 이름을 붙여 `show vlan brief`만 보고 어느 부서인지 알 수 있게 한다.

```
! SC-SW-RND
vlan 10
name RnD
exit

! SC-SW-QA
vlan 20
name QA
exit

! SC-SW-TS
vlan 30
name TechSupport_HQ
exit

! SC-SW-ADM
vlan 40
name Admin
exit

! SC-SW-SRV
vlan 50
name ServerFarm
exit

! SC-SW-TSBR
vlan 60
name TechSupport_Branch
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `vlan 10` | VLAN 10의 설정 모드 | 이름을 붙일 대상 VLAN을 고른다 |
| `name RnD` | VLAN에 이름을 붙인다 | 통신에는 영향이 없지만 빠지면 장애 대응이나 감사 때 번호만 보고 부서를 외워야 한다. 잘못된 VLAN에 포트를 넣는 실수를 이름으로 걸러낼 수 있다 |
| `exit` | VLAN 설정 모드에서 나온다 | VLAN 설정은 이 모드를 나올 때 반영되는 경우가 있다 |

이름에는 공백 대신 밑줄을 썼다(TechSupport_HQ). 공백이 들어가면 따옴표 처리가 필요해 실수가 생기기 쉽다. `show vlan brief`의 Name 열에 RnD, QA, TechSupport_HQ, Admin, ServerFarm, TechSupport_Branch가 보이면 된다. 단계 15의 원복 확인에서 RND의 VLAN 10이 "VLAN10(RnD)"로 나와 이름 적용을 보여 준다.

### 단계 10. 스위치 6대 텔넷(vty), 비밀번호, 관리 IP

**목적**: 스위치에 콘솔 케이블 없이 네트워크로 접속해 관리할 수 있게 하고, 아무나 접속하거나 특권 모드에 들어가지 못하게 비밀번호를 건다. 관리 IP는 각 부서 VLAN 안의 .254를 쓴다. 부서 PC가 같은 대역에서 바로 텔넷으로 접속할 수 있게 하려는 설계이고 게이트웨이는 그 대역의 라우터 주소(.1)다.

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `enable secret <비밀번호>` | 특권 모드(`#`) 진입 비밀번호를 해시로 저장 | 빠지면 콘솔에서는 누구나 특권 모드에 들어가 설정을 바꾼다. 텔넷으로 접속한 경우 enable 비밀번호가 없으면 IOS가 특권 모드 진입을 거부해 원격 관리를 할 수 없다. `enable password`가 아니라 `secret`을 쓴 이유는 설정 파일에 평문으로 남지 않게 하려는 것이다 [4] |
| `line console 0` | 콘솔 포트 설정 모드 | 장비 앞에서 케이블로 접속하는 경로를 보호 |
| `password <비밀번호>` (console) | 콘솔 접속 비밀번호 | 빠지면 장비에 물리적으로 다가간 사람이 비밀번호 없이 사용자 모드에 들어온다 |
| `login` (console) | 접속 때 위 비밀번호를 검사 | 빠지면 비밀번호를 정해도 검사하지 않는다. `password`와 `login`은 짝이다 |
| `line vty 0 15` | 원격 접속용 가상 라인 16개 | 일부만 설정하면 나머지 라인이 다른 설정으로 남을 수 있다. 전체에 같은 규칙을 걸어 빈틈을 없앤다 |
| `password <비밀번호>` (vty) | 텔넷 접속 비밀번호 | 빠지면 IOS는 비밀번호 없는 vty 접속을 거부해 텔넷 관리가 안 된다 |
| `login` (vty) | vty 접속 때 비밀번호 검사 | 검사를 명시적으로 켠다. 기본 설정에 이미 있는 경우가 많지만 명시하면 의도가 설정 파일에 남는다 |
| `interface vlan 10` | 스위치의 관리용 SVI | 2960은 L2 스위치라 포트에 IP를 줄 수 없다. 원격 접속을 받을 IP 자리가 SVI이고, 부서 VLAN에 만들어야 같은 VLAN의 PC가 닿는다 |
| `ip address 192.168.10.254 255.255.255.0` | 관리 IP | 텔넷 접속 목적지. .254는 PC 주소(.11 등)와 게이트웨이(.1)와 겹치지 않는 끝 번호로 규칙을 정한 것 |
| `no shutdown` | 관리 SVI를 켠다 | 새 SVI는 꺼져 있다. 빠지면 관리 IP에 ping도 텔넷도 안 된다 |
| `ip default-gateway 192.168.10.1` | 스위치 자신이 다른 대역과 통신할 때 쓸 게이트웨이 | 빠지면 같은 VLAN에서는 텔넷이 되지만 다른 대역에서 접속하면 스위치가 응답을 돌려보낼 길을 모른다. 스위치는 라우팅을 하지 않으므로 `ip route`가 아니라 이 명령을 쓴다 |

**확인**: 연구개발팀 PC(Command Prompt)에서 `telnet 192.168.10.254`
- 접속되면 비밀번호를 묻고, 맞게 입력하면 `SC-SW-RND>`가 나온다. 이어서 `enable`과 enable secret을 넣어 `SC-SW-RND#`이 나오면 원격 관리까지 확인된 것이다.
- 결과: 연구개발팀 PC에서 접속에 성공했다. 나머지 5대는 설정만 하고 개별 테스트를 생략해 QA, TS, ADM, SRV, TSBR의 텔넷 동작은 검증되지 않았다. `enable` 단계까지 확인했는지는 기록에 없다(6장).

### 단계 11. 전 장비 설정 저장

**목적**: 입력한 설정은 RAM의 running-config에만 있어 재부팅하면 사라진다. NVRAM의 startup-config로 복사해 재부팅 후에도 유지되게 한다. 라우터 2대와 스위치 6대 전부에 적용했다.

```
! SC-HQ-R1, SC-BR-R1, SC-SW-RND, SC-SW-QA, SC-SW-TS, SC-SW-ADM, SC-SW-SRV, SC-SW-TSBR 각각
copy running-config startup-config
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `copy running-config startup-config` | 동작 중인 설정을 부팅 설정으로 저장 | 빠지면 정전이나 재부팅 한 번에 포트 할당, IP, 경로, 비밀번호가 전부 사라진다(VLAN 정보는 vlan.dat에 따로 저장된다). 비밀번호까지 사라지면 장비가 무방비 상태로 켜진다 |

저장할 파일 이름을 묻는 `Destination filename [startup-config]?`에서 엔터를 치면 기본 이름으로 저장되고 `[OK]`가 나오면 성공이다. 단계 15에서는 같은 역할의 `write memory`를 썼다. `show startup-config`로 running-config와 같은지 확인하는 결과는 기록에 없다(6장).

### 단계 12. 안 쓰는 포트 shutdown

**목적**: 각 스위치의 connected 범위 밖 포트(안 쓰는 FastEthernet 포트)와 기가비트 포트 Gi0/1, Gi0/2를 모두 끈다. 누군가 빈 포트에 장비를 몰래 꽂아도 통신이 되지 않게 하려는 것이다. 기록된 명령은 포트 shutdown뿐이고 VLAN을 끄거나 지운 명령은 없다.

```
! SC-SW-RND
interface range fastEthernet 0/16-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown

! SC-SW-QA
interface range fastEthernet 0/8-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown

! SC-SW-TS
interface range fastEthernet 0/8-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown

! SC-SW-ADM
interface range fastEthernet 0/10-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown

! SC-SW-SRV
interface range fastEthernet 0/6-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown

! SC-SW-TSBR
interface range fastEthernet 0/10-24
shutdown
interface range gigabitEthernet 0/1-2
shutdown

! SC-SW-SRV (실수 수정: TSBR용 범위 0/10-24를 넣어 빠진 Fa0/6 - Fa0/9를 추가로 끔)
interface range fastEthernet 0/6-9
shutdown
```

적용 후 스위치 6대에서 `copy running-config startup-config`로 다시 저장했다.

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `interface range fastEthernet 0/16-24` | connected 범위 다음 포트부터 마지막 포트까지 | 범위의 시작은 connected 범위 바로 다음이어야 한다. 하나 앞으로 당기면 사용 중인 PC나 업링크가 꺼진다 |
| `shutdown` | 고른 포트를 관리자 권한으로 끈다 | 빠지면 빈 포트에 노트북이나 무선 공유기를 꽂는 순간 네트워크에 들어온다. 미사용 포트는 기본 VLAN 1에 있어 같은 스위치의 관리 정보나 VLAN 1 트래픽에 접근할 통로가 된다 |
| `interface range gigabitEthernet 0/1-2` | 업링크용 기가비트 포트 2개 | 이 실습에서 쓰지 않는 포트다. 속도가 빨라 다른 스위치를 연결하기 좋은 자리라 더 막아 둘 이유가 있다 |

**확인**: `show ip interface brief` 또는 `show interfaces status`로 해당 포트가 administratively down(또는 disabled)인지 본다. 이 단계의 확인 출력은 기록에 없고, SRV의 범위 실수가 어떤 명령으로 발견되었는지도 기록에 없다(6장).

### 단계 13. 수업 과제: 체인 트렁크, 라우터 서브인터페이스, VTP 구성

**목적**: 메인 설계와 별개인 수업 과제다. 본사 라우터는 SC-SW-RND에만 연결을 남기고 나머지 스위치 4대는 라우터 연결을 끊은 뒤 RND부터 체인으로 이었다(RND, QA, TS, ADM, SRV 순서). 라우터는 포트 하나(Gi0/0/0)로 5개 부서를 모두 받는 Router-on-a-Stick 구조가 되고 스위치 사이 연결은 모두 트렁크가 된다. VLAN 정보는 VTP로 RND(서버)에서 나머지(클라이언트)로 전파한다.

체인 구조에서 VTP가 필요한 이유: 서버팜 PC의 프레임은 SRV, ADM, TS, QA, RND를 거쳐 라우터로 간다. 중간 스위치는 자기 부서가 아닌 VLAN 50의 프레임도 트렁크로 넘겨야 하는데, 스위치는 자기 VLAN 데이터베이스에 없는 VLAN의 프레임은 트렁크로 넘기지 않는다. 그래서 모든 스위치가 VLAN 10 - 50을 전부 알아야 하고 VTP가 이를 자동으로 맞춰 준다.

물리 연결(`show cdp neighbors`로 확인)

| 연결 | 포트 |
|------|------|
| SC-HQ-R1 Gi0/0/0 와 SC-SW-RND | Fa0/1 |
| SC-SW-RND 와 SC-SW-QA | Fa0/16 과 Fa0/1 |
| SC-SW-QA 와 SC-SW-TS | Fa0/8 과 Fa0/4 |
| SC-SW-TS 와 SC-SW-ADM | Fa0/8 과 Fa0/4 |
| SC-SW-ADM 와 SC-SW-SRV | Fa0/10 과 Fa0/5 |

새로 쓰게 된 RND Fa0/16, QA Fa0/8, TS Fa0/8, ADM Fa0/10은 단계 12에서 shutdown한 포트다. 이 포트들에 `no shutdown`을 입력한 기록은 없지만, 단계 14에서 trunking 상태로 확인되어 다시 켜진 것은 확실하다(6장).

**SC-HQ-R1** (Router-on-a-Stick 서브인터페이스로 전환)
```
interface GigabitEthernet0/0/0
no ip address
no shutdown
exit

no ip address
shutdown
exit
no interface Vlan30
no interface Vlan40
no interface Vlan50
interface GigabitEthernet0/0/0.10
encapsulation dot1Q 10
ip address 192.168.10.1 255.255.255.0
exit
interface GigabitEthernet0/0/0.20
encapsulation dot1Q 20
ip address 192.168.20.1 255.255.255.0
exit
interface GigabitEthernet0/0/0.30
encapsulation dot1Q 30
ip address 192.168.30.1 255.255.255.0
exit
interface GigabitEthernet0/0/0.40
encapsulation dot1Q 40
ip address 192.168.40.1 255.255.255.0
exit
interface GigabitEthernet0/0/0.50
encapsulation dot1Q 50
ip address 192.168.50.1 255.255.255.0
exit
interface GigabitEthernet0/1/0
shutdown
exit
interface GigabitEthernet0/1/1
shutdown
exit
interface GigabitEthernet0/1/2
shutdown
end
```

| 명령어 | 뜻 | 왜 넣는가 (빠지면 깨지는 것) |
|--------|-----|------------------------------|
| `interface GigabitEthernet0/0/0` 후 `no ip address` | 물리 포트에서 192.168.10.1을 지운다 | 같은 주소를 서브인터페이스 .10에 다시 줄 것이므로 먼저 비워야 한다. 남겨두면 "overlaps with" 에러가 난다(실수 3). 트렁크를 받는 물리 포트는 주소 없이 서브인터페이스의 그릇 역할만 한다 |
| `no shutdown` (Gi0/0/0) | 물리 포트를 켜 둔다 | 서브인터페이스는 물리 포트가 켜져 있어야 동작한다. 꺼지면 5개 부서 게이트웨이가 한꺼번에 down된다 |
| `interface GigabitEthernet0/0/1` 후 `no ip address` | QA 포트의 192.168.20.1을 지운다 | 같은 대역을 .20 서브인터페이스에 줄 것이므로 겹침을 없앤다 |
| `shutdown` (Gi0/0/1) | QA 포트를 끈다 | 이 구조에서 QA 스위치는 라우터에 직접 연결되지 않는다. 쓰지 않는 포트를 끄는 원칙(단계 12)과 같다 |
| `no interface Vlan30`, `Vlan40`, `Vlan50` | 기존 SVI 3개를 지운다 | SVI의 192.168.30.1, 40.1, 50.1을 서브인터페이스에 다시 줄 것이므로 먼저 지워야 한다. Vlan70(WAN)은 지우지 않는다. 지우면 지사와 연결이 끊긴다 |
| `interface GigabitEthernet0/0/0.10` | Gi0/0/0 아래의 논리 서브인터페이스 .10 | 물리 포트 하나를 VLAN별 논리 포트로 나누는 것이 Router-on-a-Stick의 핵심이다. 번호(.10)는 VLAN 번호와 맞추면 읽기 쉽지만 실제 VLAN을 정하는 것은 다음 줄이다 |
| `encapsulation dot1Q 10` | 이 서브인터페이스는 VLAN 10 태그 프레임을 처리 | 빠지면 라우터가 어느 VLAN의 프레임을 받을지 모른다. IOS는 캡슐화 없는 서브인터페이스에 IP를 주는 것을 허용하지 않으므로 IP보다 먼저 넣는다 [2] |
| `ip address 192.168.10.1 255.255.255.0` (서브인터페이스) | VLAN 10의 게이트웨이를 서브인터페이스에 | PC의 게이트웨이 설정은 그대로 두고 구조만 바꾸려고 같은 주소를 쓴다. 다른 주소면 모든 PC의 게이트웨이를 바꿔야 한다 |
| `.20` - `.50` 같은 형식 | 나머지 4개 부서 | 하나라도 빠지면 그 부서만 게이트웨이를 잃는다 |
| `interface GigabitEthernet0/1/0`, `0/1/1`, `0/1/2` 후 `shutdown` | 기존 모듈 포트 3개를 끈다 | 이 구조에서는 선이 연결되지 않는다 |
| `end` | 설정 모드를 한 번에 빠져나온다 | 이어서 `show`로 확인 |

스위치 쪽

| 명령어 | 뜻 | 왜 넣는가 (빠지면 깨지는 것) |
|--------|-----|------------------------------|
| `vtp domain SAFECORE` | VTP 도메인 이름 | 도메인 이름이 같은 스위치끼리만 정보를 주고받는다. 한 대라도 이름이나 대소문자가 다르면 VLAN을 받지 못한다 |
| `vtp mode server` (RND) | RND를 VLAN 정보의 원본으로 | 2960 기본값도 server이지만 명시해 의도를 분명히 한다. VLAN 생성과 삭제는 이 스위치에서만 한다 |
| `vlan 20` 후 `name QA` 등 (RND) | 서버에 VLAN 20, 30, 40, 50을 이름까지 만든다 | 클라이언트는 서버의 VLAN 목록을 그대로 따른다. 서버에 VLAN 20이 없으면 QA가 클라이언트가 되는 순간 QA의 VLAN 20이 사라지고 QA 포트가 갈 곳을 잃는다. 이름까지 넣는 이유는 클라이언트의 이름도 서버 것으로 바뀌기 때문이다. VLAN 10은 RND에 이미 있다 |
| `vtp mode client` (QA, TS, ADM, SRV) | 서버의 VLAN 정보를 받아 따르는 모드 | 빠지면 4대가 모두 server로 남아 각자 VLAN을 만들 수 있고 revision이 높은 쪽이 다른 쪽을 덮어쓰는 사고가 날 수 있다. 원본을 하나로 정해야 관리된다 [1] |
| `switchport mode trunk` (RND 라우터 쪽 포트) | 라우터로 가는 포트를 트렁크로 | 라우터 Gi0/0/0이 5개 VLAN을 태그로 구분해 받으므로 스위치도 태그를 붙여 보내야 한다. 라우터는 DTP로 협상하지 않으므로 스위치 쪽을 고정 트렁크로 둔다. 빠지면 VLAN 10만 태그 없이 나가고 나머지 부서는 게이트웨이에 닿지 못한다 |
| `switchport mode trunk` (스위치 사이 포트) | 스위치 사이 링크를 트렁크로 고정 | 2960 기본값(dynamic auto)끼리는 트렁크가 자동으로 맺히지 않는다. 양쪽 모두 고정하면 협상에 의존하지 않는다. 빠지면 체인 아래쪽 부서의 프레임이 라우터까지 올라가지 못한다 |

2960에서 `switchport trunk encapsulation dot1q`는 입력하지 않는다. 802.1Q만 지원해서 명령이 없고 입력하면 Invalid input 에러가 난다(실수 2).

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `show ip interface brief` | 인터페이스별 주소와 상태 | 서브인터페이스 5개가 up/up이고 끈 포트는 down이며 WAN은 그대로인지 한 번에 본다. 건너뛰면 WAN을 실수로 건드렸는지 알 수 없다 |
| `show vtp status` | VTP 도메인, 모드, revision, MD5 digest | 5대가 같은 도메인과 같은 데이터베이스를 가졌는지 확인. 건너뛰면 도메인 이름 오타 같은 문제를 ping 실패 뒤에야 알게 된다 |
| `show interfaces trunk` | 트렁크로 동작 중인 포트와 그 위를 지나는 VLAN | 트렁크가 실제로 맺혔는지, 어떤 VLAN이 허용되고 활성인지 본다 |
| `ping 192.168.10.11` (서버팜 PC) | 체인의 맨 끝(SRV)에서 맨 앞(RND) 부서 PC로 | 가장 긴 경로를 시험하면 중간 스위치 4대의 트렁크와 VLAN 전파, 라우터 서브인터페이스 2개(.50과 .10)를 한 번에 검증한다 |

**읽는 법과 결과**
- `show ip interface brief`: Gi0/0/0.10 - .50이 up/up이어야 한다. 결과: 모두 up/up, Gi0/0/1과 Gi0/1/0 - 0/1/2는 administratively down, Gi0/1/3(WAN)과 Vlan70은 up/up 유지.
- `show vtp status`: Domain Name이 SAFECORE, 모드가 서버 1대와 클라이언트 4대, MD5 digest가 5대 모두 같아야 한다. digest가 같으면 VLAN 데이터베이스 내용이 같다는 뜻이다. 결과: 5대 모두 MD5 digest 일치.
- `show interfaces trunk`: Mode가 on, Encapsulation이 802.1q, Status가 trunking이어야 하고 VLANs allowed and active에 전파된 VLAN이 보인다. 결과: RND는 Fa0/1과 Fa0/16, QA는 Fa0/1과 Fa0/8, TS는 Fa0/4와 Fa0/8, ADM은 Fa0/4와 Fa0/10, SRV는 Fa0/5가 모두 802.1q trunking이고 VLAN 1, 10, 20, 30, 40, 50이 전파되었다.
- PC ping: 결과 Reply 4/4 성공(0% loss). 체인 전체를 거친 통신이 정상이었다.

| `interface fastEthernet 0/16` 후 `switchport mode access`, `shutdown` (RND) | 체인용 포트를 액세스로 돌리고 끈다 | 선이 제거된 포트다. 트렁크 설정이 남은 채 켜져 있으면 누가 스위치를 꽂았을 때 모든 VLAN이 넘어간다. 원래의 미사용 포트 상태(단계 12)로 돌린다 |
| `vtp mode transparent` | VTP로 받은 정보를 따르지 않고 자기 VLAN만 관리 | 원래 설계에서는 스위치끼리 연결이 없어 VTP가 필요 없다. 클라이언트로 두면 나중에 revision이 더 높은 스위치가 같은 도메인으로 연결될 때 VLAN 정보가 덮어써질 위험이 남는다 [1] |
| `no vlan 20`, `30`, `40`, `50` (RND) | RND에서 다른 부서 VLAN을 지운다 | RND는 VLAN 10만 쓴다. 남겨두면 실수로 포트를 다른 부서 VLAN에 넣을 여지가 생긴다 |
| `interface fastEthernet 0/1` 후 `switchport access vlan 20` 등 (QA, TS, ADM, SRV) | 각 업링크를 자기 부서 VLAN 액세스로 | 업링크가 다시 라우터에 직결되었으므로 단계 8의 상태로 돌린다 |
| `interface fastEthernet 0/8` 후 `switchport mode access`, `shutdown` (QA, TS), `0/10` (ADM) | 체인용 아래쪽 포트를 원래 미사용 상태로 | RND Fa0/16과 같은 이유. SRV는 체인의 끝이라 아래쪽 포트가 없다 |

**순서가 중요한 부분**
- RND에서 `vtp mode transparent`를 VLAN 삭제보다 먼저 해야 한다. server인 상태에서 `no vlan 20`을 하면 삭제가 클라이언트로 전파되어 QA의 VLAN 20, TS의 VLAN 30 같은 자기 부서 VLAN까지 사라지고 그 스위치의 PC 포트가 모두 갈 곳을 잃는다.
- 라우터에서는 서브인터페이스를 먼저 지우고 나서 물리 포트와 SVI에 주소를 다시 준다. 반대로 하면 "overlaps with" 에러가 난다.

**확인과 결과**
```
! SC-HQ-R1
show ip interface brief

! SC-SW-RND, SC-SW-QA, SC-SW-TS, SC-SW-ADM, SC-SW-SRV 각각
show vlan brief
show interfaces trunk
```

- 읽는 법: `show vlan brief`에서 부서 VLAN 줄에 원래 포트만 남고 체인용 포트는 VLAN 1로 돌아와야 한다. `show interfaces trunk`에는 아무것도 나오지 않아야 트렁크가 완전히 없어진 것이다.
- SC-HQ-R1: Gi0/0/0(.10)과 Gi0/0/1(.20)에 직접 IP, Gi0/1/0 - 0/1/2 up/up, Vlan30, 40, 50 SVI up/up, Gi0/1/3과 Vlan70(WAN)은 그대로 유지.
- RND: VLAN 10(RnD)에 Fa0/1 - Fa0/15만 남았고 VLAN 20 - 50은 없었다. Fa0/16은 VLAN 1(default)로 돌아왔고 `show interfaces trunk`는 비어 있었다.
- QA, TS, ADM, SRV: QA는 VLAN 20에 Fa0/1 - Fa0/7, TS는 VLAN 30에 Fa0/1 - Fa0/7, ADM은 VLAN 40에 Fa0/1 - Fa0/9만 남았고 복귀 포트(QA Fa0/8, TS Fa0/8, ADM Fa0/10)는 VLAN 1로 돌아왔다. SRV는 VLAN 50에 Fa0/1 - Fa0/5가 남았다. 4대 모두 `show interfaces trunk`가 비어 있었다.

```

```
결과: 1차 시도는 4개 중 2개 timeout, 2개 성공(50% loss), 2차 시도는 Reply 4/4 성공(0% loss). 원인은 5장 결과 6에서 다룬다.

| 상황 | 기술지원팀(본사), 경영지원팀, 서버팜이 연결된 Gi0/1/0, 0/1/1, 0/1/2에 온보드 포트처럼 IP를 주려고 했다 |
| 증상 | `% Incomplete command` 에러. 어떤 명령에서 났는지는 기록마다 다르다. `ip address`를 바로 할당하려다 났다는 기록과 `no switchport`가 안 되어 났다는 기록이 있다(미확인) |
| 원인 | NIM-ES2-4는 라우터에 꽂는 스위치 모듈이다. 포트가 L2 스위치 포트로 동작해 포트 자체에 L3 주소를 둘 수 없다 |
| 해결 | 포트를 VLAN에 넣고 그 VLAN의 SVI에 IP를 줬다(단계 1). WAN 포트 Gi0/1/3도 같은 방식(단계 3) |
| 교훈 | 같은 라우터 안에서도 포트가 어느 하드웨어(온보드인지 모듈인지)에 속하느냐에 따라 설정 방식이 다르다. 설정 전에 포트 종류를 먼저 확인한다 |

### 실수 2. 2960에서 `switchport trunk encapsulation dot1q`가 Invalid input

| 항목 | 내용 |
|------|------|
| 상황 | 수업 과제에서 스위치 포트를 트렁크로 만들 때 캡슐화 방식을 먼저 지정하려고 입력 |
| 증상 | `% Invalid input` |
| 원인 | 이 명령은 802.1Q와 ISL을 모두 지원하는 스위치(3560 같은 L3 스위치)에서 하나를 고르는 명령이다. 2960은 802.1Q만 지원해 고를 것이 없고 명령 자체가 없다 |
| 해결 | `switchport mode trunk`만 입력. 단계 14에서 Encapsulation이 802.1q로 표시되어 자동 적용이 확인되었다 |
| 교훈 | 교재나 인터넷의 명령을 옮기기 전에 장비 기종이 그 명령을 지원하는지 본다 |

### 실수 3. 서브인터페이스 설정 중 "overlaps with" 에러

| 항목 | 내용 |
|------|------|
| 상황 | 수업 과제에서 SC-HQ-R1에 서브인터페이스 Gi0/0/0.20 - .50을 만들고 192.168.20.1 같은 주소를 넣었다 |
| 증상 | `% overlaps with` 에러(전문은 기록 없음) |
| 원인 | 라우터는 한 장비 안에서 두 인터페이스가 같은 대역에 속하는 것을 허용하지 않는다. 그 시점에 Gi0/0/1에는 192.168.20.1/24가, Vlan30, 40, 50 SVI에는 30.1, 40.1, 50.1이 그대로 있었다 |
| 해결 | Gi0/0/1의 `no ip address`와 SVI 3개 삭제를 서브인터페이스 설정보다 먼저 하도록 순서를 바꿨다(단계 13 블록). 원복 때도 같은 규칙을 반대로 지켜 서브인터페이스를 먼저 지웠다(단계 15) |
| 교훈 | 주소를 옮길 때는 먼저 비우고 나중에 채운다. 순서만 바꿔도 에러가 사라진다 |

### 실수 4. WAN 포트가 설계와 다름

설계상 본사 WAN 포트는 Gi0/0/2였는데 `show cdp neighbors`로 보니 실제로는 Gi0/1/3(모듈 포트)에 연결되어 있었다. Gi0/1/3에 VLAN 70과 SVI 방식으로 설정했다(단계 3). 설정은 설계 문서가 아니라 실제 배선 기준으로 하고, CDP가 실제 배선을 가장 빠르게 보여 준다.

### 실수 5. 스위치 포트 범위를 잘못 입력

- SC-SW-QA: VLAN 할당 범위를 0/1-7이 아니라 0/1-17로 넣었다. `interface range fastEthernet 0/8-17` 후 `no switchport access vlan`으로 되돌렸다(단계 8).
- SC-SW-SRV: shutdown 범위에 TSBR용 범위(0/10-24)를 넣어 Fa0/6 - Fa0/9가 켜진 채로 남았다. `interface range fastEthernet 0/6-9` 후 `shutdown`으로 추가했다(단계 12).
- 교훈: 장비마다 범위가 다르면 복사해 붙이는 과정에서 다른 장비의 값이 들어간다. 장비별 블록을 따로 만들고 입력 후 `show` 명령으로 확인한다.

### 결과 6. 원복 후 첫 ping 50% 손실

| 항목 | 내용 |
|------|------|
| 상황 | 원복 직후 연구개발팀 PC에서 서버팜 PC(192.168.50.11)로 ping |
| 결과 | 1차 4개 중 2개 timeout(50% loss), 2차 4/4 성공(0% loss) |
| 판단 | 포트 설정을 바꾼 직후라 ARP를 새로 조회하는 시간과 STP가 포트를 포워딩 상태로 바꾸는 지연이 겹친 일시적 현상으로 판단했다(미확인, 원인을 측정으로 확인하지 않았다) |
| 일반 원리 | 스위치 포트가 새로 올라오면 STP는 루프 확인 동안(listening, learning) 포트가 데이터를 넘기지 않아 그동안 보낸 패킷이 유실된다 [5]. PC와 라우터는 상대 MAC을 ARP로 다시 배워야 해서 첫 패킷이 늦거나 유실될 수 있다 |
| 교훈 | 구성 변경 직후 한 번의 실패를 바로 장애로 단정하지 않고 재시도로 확인한다. 재시도에서도 실패하면 그때 설정을 의심한다 |

## 7. 한계와 더 깊게 갈 방향

| 한계 | 왜 문제인가 | 더 깊게 갈 방향 |
|------|-------------|-----------------|
| 연구개발팀이 다른 부서와 통신 가능 | 요구사항(소스코드 유출 방지)과 어긋난다. 3일차는 의도적으로 열어 둔 상태 | SC-HQ-R1에 확장 ACL로 10 대역과 다른 부서 대역 사이를 막는다. 지사 정적 경로 중 10, 40 대역은 업무상 필요 없으므로 ACL로 막거나 경로를 재검토 |
| 텔넷 평문 관리 | 비밀번호가 네트워크에 그대로 흐른다 | SSH(도메인 이름, RSA 키, 로컬 사용자, `transport input ssh`)로 전환 |
| 모든 장비에 같은 실습용 비밀번호 | 하나가 새면 전부 뚫리고 누가 접속했는지 구분이 안 된다 | 장비별 비밀번호, `username` 기반 로컬 계정, 이후 AAA 서버 검토 |
| line 비밀번호가 설정 파일에 평문 | `show running-config`를 본 사람은 비밀번호를 안다 | `service password-encryption`으로 가린다. 강한 암호화는 아니라 SSH와 로컬 계정이 근본 대책 [4] |
| vty 접속 출발지 제한 없음 | 관리 IP에 닿는 모든 PC가 로그인을 시도할 수 있다 | vty에 `access-class`로 관리용 대역만 허용 |
| 관리 IP가 사용자 VLAN 안에 있음 | 일반 PC와 관리 트래픽이 같은 대역에 섞인다 | 별도 관리 VLAN을 두고 관리 PC만 접근 |
| 미사용 포트가 VLAN 1에 있고 shutdown만 됨 | `no shutdown` 한 줄로 다시 열린다 | 미사용 포트를 별도 VLAN으로 옮기고 port-security로 MAC 수를 제한 |
| DTP | `switchport mode access`로 고정했지만 협상 프레임 차단까지는 확인하지 않았다 | `switchport nonegotiate` 검토 |
| CDP가 전 포트에서 켜져 있음 | 장비 정보가 이웃에게 노출된다 | 사용자 포트와 외부 포트에서 `no cdp enable` 검토 [3] |
| WAN 회선 1개 | 3일차 시점에는 끊기면 본사와 지사가 완전히 끊긴다 | 4일차에 시리얼 백업 회선과 AD 250 floating static route로 보완 |
| 정적 경로의 확장성 | 대역이 늘 때마다 양쪽에 수동 추가. 지사 경로 5줄은 요약도 가능 | 5일차에 주 회선을 RIPv2로 전환. 정적을 유지한다면 요약 경로나 기본 경로 검토 |
| 본사와 지사 사이 트래픽 암호화 없음 | 티켓 내용이 WAN에서 엿보이거나 바뀔 수 있다 | IPsec VPN 검토(요구사항의 티켓 무결성) |
| 수업 과제 흔적 | 본사 스위치 5대에 VTP 도메인 이름 SAFECORE가 남아 있고(도메인 제거 명령이 없다), 4대에 다른 부서 VLAN이 남아 있을 수 있다 | `show vlan brief`로 확인하고 불필요한 VLAN 삭제 |
| 검증 범위 | 텔넷은 1대만, ping은 일부 조합만 기록되어 있다 | 6개 대역 전체 조합 ping과 스위치 6대 텔넷을 표로 기록. `show ip route`, `show startup-config` 출력도 남긴다 |
| 첫 ping 유실 원인 | 추정만 했다 | 포트 변경 직후 `show spanning-tree`로 포트 상태 변화를, `arp -a`로 ARP 학습을 직접 관찰. 사용자 포트에 PortFast 적용 검토 [5] |

## 8. 보안 3요소와의 연결

### 기밀성

| 3일차 설정 | 기여 | 남은 약점 |
|-----------|------|-----------|
| 부서별 VLAN 분리 | 부서마다 브로드캐스트 도메인이 나뉘어 다른 부서의 L2 트래픽이 보이지 않는다. 소스코드(연구개발)와 인사 자료(경영지원)를 분리하는 기반 | 라우터에서 모든 부서 간 통신이 열려 있다. ACL이 들어가기 전까지 연구개발 대역에 다른 부서가 닿을 수 있다 |
| enable secret, console과 vty 비밀번호 | 장비 설정과 라우팅 정보를 아무나 볼 수 없게 한다 | 텔넷이 평문이라 비밀번호가 노출될 수 있고 line 비밀번호는 설정 파일에 평문이다 |
| 미사용 포트 shutdown | 빈 포트로 들어와 내부 트래픽을 엿보는 경로를 막는다 | shutdown만 되어 있고 VLAN 1에 남아 있다 |
| CDP 사용 | 기밀성에는 오히려 약점. 장비 정보가 이웃에게 노출된다 | 외부 포트에서 끄는 작업이 남아 있다 |

### 무결성

| 3일차 설정 | 기여 | 남은 약점 |
|-----------|------|-----------|
| 비밀번호와 enable secret | "아무나 라우터에 접속해 설정을 바꾼다"에 대한 1차 대책. 특권 모드 없이는 설정을 바꿀 수 없다 | 비밀번호 설정은 스위치 6대 기준이고 라우터 2대 적용 여부는 기록에 없다. 같은 비밀번호를 공유해 누가 바꿨는지 추적할 수 없다 |
| 설정 저장 | 재부팅 후에도 의도한 설정이 그대로 올라온다. 저장하지 않으면 비밀번호까지 사라진 무방비 상태로 켜진다 | 저장본을 장비 밖에 백업한 기록은 없다 |
| VTP를 transparent로 되돌림 | revision이 높은 스위치가 연결되어 VLAN 정보가 덮어써지는 위험을 줄인다 | 도메인 이름이 남아 있다 |
| 원복 순서 지키기 | VLAN 삭제가 다른 스위치로 전파되어 의도치 않게 설정이 바뀌는 것을 막았다 | 사람이 순서를 기억해야 한다. 변경 절차서로 남기는 것이 좋다 |
| 본사와 지사 사이 정적 경로 | 티켓 시스템에 닿는 길을 열었다 | 전송 구간 암호화나 무결성 검증이 없다. "티켓 내용이 엿보이거나 바뀐다"는 아직 대책이 없다 |

### 가용성

| 3일차 설정 | 기여 | 남은 약점 |
|-----------|------|-----------|
| 부서 게이트웨이와 정적 경로 | 지사 기술지원팀이 본사 티켓 시스템과 파일 서버(서버팜)를 쓸 수 있게 되었다. 요구사항을 충족하는 핵심 | WAN 회선이 1개뿐이라 끊기면 지사 업무가 멈춘다(4일차에 보완) |
| 전용 포트 방식 유지 | Router-on-a-Stick처럼 포트 하나에 모든 부서가 몰리지 않아 포트 하나의 장애가 한 부서에만 영향을 준다 | 라우터 자체는 1대라 라우터가 멈추면 본사 전체가 멈춘다 |
| 관리 IP와 텔넷 | 장애 때 콘솔 케이블 없이 원격으로 들어가 빨리 조치할 수 있다 | 관리 경로가 사용자 망과 같아 사용자 망이 끊기면 관리 접속도 같이 끊긴다 |
| `no ip domain-lookup` | 장애 대응 중 오타로 인한 지연을 없앤다 | 적용 확인 기록이 없다 |
| 원복 후 재시도 검증 | 원복한 뒤 같은 시험을 다시 해서 결과를 확인했다 | STP 수렴 지연 자체를 줄이는 설정(PortFast)은 아직 없다 |

### 9-1. 개념

| 질문 | 답 요지 |
|------|---------|
| VLAN은 왜 쓰나? | 같은 물리 스위치 위에서 네트워크를 논리적으로 나누기 위해서다. VLAN마다 브로드캐스트 도메인이 따로 생겨 불필요한 브로드캐스트가 줄고, 부서 간 통신은 라우터를 거쳐 그 지점에서 ACL로 통제할 수 있다. 연구개발팀 소스코드와 경영지원팀 인사 자료를 분리하는 기반으로 썼다 |
| 액세스 포트와 트렁크 포트의 차이는? | 액세스 포트는 VLAN 하나에 속하고 태그 없이 프레임을 보낸다. 트렁크 포트는 여러 VLAN의 프레임을 802.1Q 태그로 구분해 한 선으로 보낸다. 메인 설계는 모든 스위치 포트가 액세스였고 수업 과제의 체인 구조에서만 트렁크를 썼다 |
| 네이티브 VLAN이란? | 트렁크에서 태그 없이 지나가는 VLAN으로 기본값은 VLAN 1이다. 양쪽 설정이 어긋나면 문제가 생기고 VLAN 호핑 공격과 관련된다 |
| Router-on-a-Stick과 전용 포트의 차이는? | Router-on-a-Stick은 라우터 포트 하나에 트렁크를 받고 서브인터페이스로 VLAN을 나눈다 [2]. 포트는 아끼지만 모든 부서 간 트래픽이 한 선에 몰리고 그 포트 하나가 고장 나면 전 부서가 끊긴다. 전용 포트는 부서마다 라우터 포트를 쓴다 |
| 서브인터페이스 설정에서 `encapsulation dot1Q`를 왜 IP보다 먼저 넣나? | 라우터가 어느 VLAN의 프레임을 그 서브인터페이스로 받을지 정해야 하고, IOS는 캡슐화가 없는 서브인터페이스에 IP를 주는 것을 허용하지 않는다 [2] |
| VTP란? 위험은? | VLAN 정보를 트렁크로 자동 전파하는 시스코 프로토콜이다. configuration revision이 더 높은 스위치가 같은 도메인에 연결되면 그 정보로 전체가 덮어써질 수 있다 [1] |
| 정적 라우팅의 장단점은? | 단순하고 부하가 없고 예측하기 쉽지만, 대역이 늘 때마다 양쪽에 수동 추가해야 하고 next-hop 너머의 장애를 스스로 감지하지 못한다 |
| CDP란? | 직접 연결된 시스코 이웃의 이름, 기종, 포트를 주고받는 L2 프로토콜이다. 실제 배선을 확인하는 데 유용하지만 장비 정보가 노출되므로 신뢰하지 않는 네트워크와 닿는 인터페이스에서는 끈다 [3] |

### 9-2. 설계 판단

| 질문 | 답 요지 |
|------|---------|
| 같은 라우터인데 어떤 포트는 직접 IP, 어떤 포트는 SVI를 쓴 이유는? | 포트가 속한 하드웨어가 다르다. ISR4331의 온보드 포트(Gi0/0/0, Gi0/0/1)는 라우티드 포트라 바로 IP를 준다. NIM-ES2-4 모듈 포트(Gi0/1/0 - 0/1/3)는 스위치 포트라 IP를 직접 받지 못해, VLAN에 넣고 SVI에 IP를 줬다 |
| 왜 전용 포트를 메인으로 했나? | 실제 토폴로지가 이미 부서별 전용 포트였고, 병목과 단일 장애점이 없고 구조가 단순하다. Router-on-a-Stick은 수업 과제로 구성하고 검증한 뒤 되돌렸다 |
| 정적 경로가 본사 1줄, 지사 5줄인 이유는? | 라우터는 직접 연결된 대역은 이미 안다. 본사에게 본사 5개 부서는 직접 연결이고 모르는 것은 지사 1개다. 지사는 반대로 본사 5개를 모른다. 갈 길과 올 길이 모두 있어야 통신되므로 양쪽에 넣었다 |
| 스위치에 관리 IP와 `ip default-gateway`를 넣은 이유는? | L2 스위치는 포트에 IP가 없어 원격 접속을 받을 주소를 SVI에 둔다. `ip default-gateway`가 없으면 같은 VLAN에서는 접속되지만 다른 대역에서는 응답을 돌려보낼 길을 모른다. 스위치는 라우팅을 하지 않으므로 `ip route`가 아니라 이 명령을 쓴다 |
| 안 쓰는 포트를 왜 shutdown했나? | 빈 포트에 장비를 꽂는 순간 내부망에 들어오는 것을 막기 위해서다. 미사용 포트는 기본 VLAN 1에 있어 관리 트래픽과 섞일 수 있다. shutdown만으로는 `no shutdown` 한 줄에 다시 열리므로 별도 VLAN으로 옮기고 port-security를 거는 것이 더 안전하다 |
| 원복할 때 RND에서 vtp mode를 VLAN 삭제보다 먼저 바꾼 이유는? | server 상태에서 `no vlan 20`을 하면 삭제가 클라이언트로 전파되어 다른 스위치의 자기 부서 VLAN까지 사라진다. transparent로 먼저 바꿔 전파를 끊었다 |

### 9-3. 트러블슈팅과 검증

| 질문 | 답 요지 |
|------|---------|
| 모듈 포트에 IP를 주려다 에러가 났을 때 어떻게 했나? | 포트가 L2 스위치 포트로 동작해 L3 주소를 직접 받지 못하는 것이 원인이다. VLAN에 넣고 SVI에 IP를 주는 방식으로 해결했다. 설정 전에 포트 종류부터 확인해야 한다 |
| "overlaps with" 에러는 어떻게 해결했나? | 한 라우터 안에서 두 인터페이스가 같은 대역을 가질 수 없어서 난 에러다. QA 물리 포트와 SVI 3개에 같은 주소가 남아 있었다. 기존 주소를 먼저 지우고 서브인터페이스를 만드는 순서로 바꿨고 원복 때도 서브인터페이스를 먼저 지웠다. 주소를 옮길 때는 먼저 비우고 나중에 채운다 |
| 2960에서 `switchport trunk encapsulation dot1q`가 안 되는 이유는? | 2960은 802.1Q만 지원해 고를 것이 없다. `switchport mode trunk`만 넣으면 자동으로 802.1Q로 동작하고 `show interfaces trunk`의 Encapsulation으로 확인했다 |
| 설계와 실제 배선이 다를 때는? | WAN 포트가 설계의 Gi0/0/2가 아니라 Gi0/1/3이었다. `show cdp neighbors`로 실제 배선을 확인하고 그에 맞춰 설정했다. 업링크도 CDP로 확인해서 TS, ADM이 Fa0/4, SRV가 Fa0/5라는 것을 알았다 |
| 체인 구조에서 VTP가 왜 필요했나? | 중간 스위치가 자기 부서가 아닌 VLAN의 프레임도 트렁크로 넘겨야 하는데, 스위치는 자기 VLAN 데이터베이스에 없는 VLAN은 넘기지 않는다. 5대 모두 VLAN 10 - 50을 알아야 했고 VTP로 맞췄다. MD5 digest가 5대 모두 일치하는 것으로 동기화를 확인했다 |
| 원복 후 첫 ping이 50% 실패했는데 장애로 보지 않은 이유는? | 포트 설정을 바꾼 직후에는 STP가 포트를 포워딩 상태로 바꾸는 시간과 ARP를 다시 배우는 시간이 있다 [5][6]. 그 사이의 유실로 판단하고 재시도했고 2차에서 4/4가 성공했다. 원인을 측정으로 확인한 것은 아니라서 "추정했고 재시도로 검증했다"고 말한다 |
| 지사 라우터에서 본사 게이트웨이로 한 ping이 양방향 검증인가? | 아니다. 출발 주소가 70 대역이라 본사가 70 대역을 직접 알고 있어서 본사 쪽 정적 경로(60 대역)까지는 검증되지 않는다. 지사 PC(60 대역)에서 본사로 ping해야 양방향이 검증된다 |

### 9-4. 보안

| 질문 | 답 요지 |
|------|---------|
| `enable secret`과 `enable password`의 차이는? | `enable secret`은 해시로 저장되고 `enable password`는 설정 파일에서 되돌릴 수 있는 약한 방식으로 저장된다. Cisco는 secret 사용을 권한다 [4] |
| 텔넷의 문제와 대안은? | 접속 과정 전체가 평문이라 중간에서 비밀번호가 보인다. 실무에서는 SSH로 바꾸고 vty에 ACL을 걸어 관리 PC에서만 접속하게 한다. 학습 단계라 텔넷으로 구성했고 SSH 전환은 후속 항목이다 |
| 모든 장비가 같은 비밀번호인 문제는? | 하나가 새면 전부 뚫리고 누가 접속했는지 구분이 안 된다. 장비별 비밀번호와 `username` 기반 로컬 계정, 이후 AAA 서버로 개선한다 |
| 3일차 시점에 연구개발팀 격리가 됐나? | 되지 않았다. 일부러 전체 라우팅을 먼저 연결하고 ACL은 보안 단계에서 하기로 했다. VLAN 분리는 L2 분리일 뿐이고 라우터에서 모든 부서 간 통신이 열려 있었다 |
| CDP를 어떻게 활용했고 위험은? | 설계상 WAN 포트와 실제 배선의 차이, 스위치 업링크 포트를 찾는 데 썼다. 장비 이름, 기종, IOS 정보를 이웃에게 알려주므로 신뢰하지 않는 네트워크와 닿는 인터페이스에서는 끈다 [3] |

### 9-5. 확장과 한계

| 질문 | 답 요지 |
|------|---------|
| 정적 라우팅의 한계를 어떻게 다뤘나? | 3일차에는 회선이 하나라 WAN이 끊기면 본사와 지사가 완전히 끊긴다. 4일차에 백업 회선과 floating static route로, 5일차에 RIPv2로 한계를 다뤘다 |
| 스위치 6대에 텔넷 설정을 했는데 검증은? | 연구개발팀 PC에서 1대만 접속을 확인했고 나머지 5대는 설정만 했다. 검증 범위가 좁았다는 것을 한계로 기록했고, 6개 대역 전체 ping과 6대 텔넷을 표로 남기는 것이 개선 방향이다 |
| 첫 ping 유실을 줄이려면? | 사용자 포트에 PortFast를 적용해 listening과 learning 단계를 건너뛰게 할 수 있다. 호스트가 연결되는 포트에서만 쓰고 BPDU Guard와 함께 쓰는 것이 권장된다 [5] |

## 참고 자료

번호가 없는 내용은 이번 실습에서 직접 확인한 결과다.

1. Cisco, [Troubleshooting VLAN Trunk Protocol (VTP)](https://www.cisco.com/c/en/us/support/docs/lan-switching/vtp/98155-tshoot-vlan.html) - revision 번호가 가장 높은 장비의 VLAN 설정을 도메인이 따름, transparent 모드. 덮어쓰기는 VTP 버전 1, 2 기준이며 버전 3은 다르다
2. Cisco, [Configuring Routing Between VLANs with IEEE 802.1Q Encapsulation](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/lanswitch/configuration/xe-16/lanswitch-xe-16-book/lnsw-conf-vlan-ieee.html) - 서브인터페이스, `encapsulation dot1q`, IP 주소 지정
3. Cisco, [Harden IOS Devices](https://www.cisco.com/c/en/us/support/docs/ip/access-lists/13608-21.html) - 신뢰하지 않는 네트워크와 닿는 인터페이스에서 CDP 비활성화
4. Cisco, [Cisco IOS Security Command Reference: enable secret](https://www.cisco.com/c/en/us/td/docs/ios-xml/ios/security/d1/sec-d1-cr-book/sec-cr-e1.html) - `enable secret`은 비가역 해시로 저장, `enable password`보다 권장
5. Cisco, [Understand Spanning Tree PortFast and BPDU Guard Features](https://www.cisco.com/c/en/us/support/docs/lan-switching/spanning-tree-protocol/10586-65.html) - PortFast는 listening과 learning을 건너뛰고 바로 forwarding, BPDU Guard와 함께 사용 권장
6. IETF, [RFC 826: An Ethernet Address Resolution Protocol](https://www.rfc-editor.org/info/rfc826/) - ARP

1번은 VTP 일반 동작의 근거이며 이번 Packet Tracer 2960의 VTP 버전은 확인하지 않았다. 3, 4번은 설정 문서가 아니라 보안 권고와 명령 설명이므로 장비와 버전에 맞는 문서를 확인한다.
