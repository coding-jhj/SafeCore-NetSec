### 단계 0. 5일차 종료 상태 확인과 브랜치 생성

**목적**: 실험이 실패해도 돌아올 수 있게 RIP 상태를 main에 남기고, 실험은 `ospf` 브랜치에서 한다. `.pkt`는 바이너리라 병합해도 내용이 합쳐지지 않으므로 실험 중 main은 바꾸지 않는다.

**SC-HQ-R1**
```
show ip route rip
show running-config | include ip route
show running-config | include router rip
```

**SC-BR-R1**
```
show ip route rip
show running-config | include ip route
show running-config | include router rip
```

**결과**
- 본사: `R 192.168.60.0/24`, `R 192.168.90.0/24` (via 192.168.70.2, Vlan70). 설정의 `ip route`는 끝이 250인 2줄(60 대역, 90 대역)이고 `router rip`이 있다.
- 지사: `R 192.168.10`, `20`, `30`, `40`, `50.0/24` (via 192.168.70.1, Gi0/1). 설정의 `ip route`는 끝이 250인 5줄이고 `router rip`이 있다.
- Packet Tracer 파일을 저장한 뒤 main에 커밋하고 `git switch -c ospf`로 브랜치를 만들었다.

### 단계 1. RIP 기준선 측정

**목적**: RIP를 지우기 전에 장애를 얼마나 늦게 알아채는지 잰다. OSPF 결과와 같은 지표로 비교한다.

**방법**
- 본사 `interface vlan 70`을 shutdown 한다. 본사 `Gi0/1/3` 포트를 내리면 지사도 링크 끊김을 바로 알아서 타이머를 잴 수 없으므로, 지사 쪽 링크는 살려 둔 채 본사 SVI만 내린다.
- 지표는 지사 라우터의 시계 하나로 잰다. 마지막 RIP 갱신을 받은 시각에서 경로표가 예비 경로로 바뀐 시각까지의 간격이다. 본사와 지사의 시계가 달라서 생기는 오차를 피하려는 것이다.
- Packet Tracer를 Realtime 모드로 둔다. Simulation 모드는 재생할 때만 시간이 흘러서 타이머 측정에 맞지 않는다.

**SC-BR-R1** (디버그 메시지에 시각을 붙이고 RIP 갱신을 기록)
```
configure terminal
service timestamps debug datetime msec
end
debug ip rip
debug ip routing
```

**SC-HQ-R1** (본사 VLAN 70 SVI만 내린다)
```
configure terminal
interface vlan 70
shutdown
end
```

**SC-BR-R1** (경로가 바뀌는지 확인)
```
show ip route | include 192.168.50.0
show clock
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `service timestamps debug datetime msec` | 디버그 메시지에 날짜와 밀리초 시각을 붙인다 | 마지막 갱신의 시각을 라우터가 직접 기록하게 해서 사람이 재는 오차를 없앤다 |
| `debug ip rip` | RIP 갱신을 보내고 받을 때마다 화면에 출력 | 마지막으로 받은 갱신의 시각을 찾는다 |
| `debug ip routing` | 라우팅 테이블 변경을 출력 | 경로 전환 시각을 찍기를 기대했지만 이 Packet Tracer는 변경 줄을 출력하지 않았다 |
| `interface vlan 70` + `shutdown` | 본사의 VLAN 70 가상 인터페이스를 내린다 | 지사 쪽 링크를 유지한 채 본사가 RIP 갱신을 못 보내게 한다 |
| `show ip route \| include 192.168.50.0` | 경로표에서 이 대역 줄만 표시 | `R`에서 `S`로 바뀌는 시점을 본다 |
| `show clock` | 라우터의 현재 시각 | 확인 시점을 디버그 시각과 같은 시계로 맞춘다 |

**결과**

| 시각(지사 라우터) | 마지막 갱신 후 | 경로 상태 |
|-------------------|----------------|-----------|
| 03:36:48 | 0초 | 마지막 RIP 갱신 수신(`received v2 update from 192.168.70.1`) |
| 03:42:20 | 338초 | `R 192.168.50.0/24 is possibly down, routing via 192.168.70.1` |
| 03:43:30 | 402초 | 같은 상태 |
| 03:44:43 | 475초 | `S 192.168.50.0/24 [250/0] via 192.168.80.1` |

- **RIP는 마지막 갱신 후 402초에서 475초 사이(6분 42초 - 7분 55초)에 예비 경로로 전환되었다.**
- 그 전까지 지사 경로표에는 죽은 다음 홉(192.168.70.1)을 가리키는 R 경로가 `possibly down` 상태로 남아 있었다. 이 경로가 AD 120으로 AD 250 예비 경로보다 우선해서 예비 경로가 올라오지 못했다.
- RIP의 기본 invalid 타이머는 180초다 [1]. 180초가 지난 뒤에도 경로가 곧바로 지워지지 않고 `possibly down`으로 남았다. 이 지연이 어떤 타이머 때문인지는 미확인이다.
- 전환 순간은 로그에 찍히지 않아 범위로만 확정했다.
- 장애 중에도 지사 PC의 `ping 192.168.50.1 -t`는 끊기지 않았다. Vlan70을 내려도 Packet Tracer에서 데이터 경로가 유지되는 것으로 보이며(미확인), 그래서 ping 유실 수는 감지 시간의 지표로 쓰지 않았다.

**복구**

**SC-BR-R1**
```
undebug all
```

**SC-HQ-R1**
```
configure terminal
interface vlan 70
no shutdown
end
```

**SC-BR-R1** (R 경로가 돌아오는지 확인)
```
show ip route | include 192.168.50.0
```

**결과**: `R 192.168.50.0/24 [120/1] via 192.168.70.1, 00:00:21, GigabitEthernet0/1`로 복귀했다. 복구는 수동 조작 없이 본사 `no shutdown` 뒤 한 번의 갱신 주기 안에 이루어졌다.

### 단계 2. RIP와 예비 정적 경로 삭제

**목적**: OSPF를 켜기 전에 기존 라우팅을 모두 걷어내서, 이후 경로가 전부 OSPF에서 온 것임을 확인할 수 있게 한다. 예비 정적 경로를 남기면 OSPF가 죽어도 통신이 되는 것처럼 보여 OSPF 장애 실험이 흐려진다.

**삭제 전 저장**: 양쪽 라우터에서 `write memory`로 5일차 종료 상태(RIPv2 동작, 예비 정적 유지)를 startup-config에 저장했다. 삭제 명령은 running-config에만 반영되므로, 도중에 꼬이면 `reload`로 이 상태로 돌아올 수 있다. 삭제 후에는 OSPF 이웃이 확인될 때까지 저장하지 않는다.

**삭제 전 확인 (두 라우터)**
```
show running-config | include ip route
show ip route
```

- 본사: `ip route`는 예비 2줄(`192.168.60.0`, `192.168.90.0`, 다음 홉 192.168.80.2, AD 250)뿐이었다.
- 지사: 예비 5줄(`192.168.10`~`50.0`, 다음 홉 192.168.80.1, AD 250)뿐이었다.
- 5일차에 주 회선을 RIP로 바꾸면서 기본 정적 경로(AD 1)는 이미 없어진 상태였다. 예비 경로는 AD 250이라 RIP(AD 120)에 가려져 경로표에는 `R`만 보였다.

**SC-HQ-R1**
```
configure terminal
no router rip
no ip route 192.168.60.0 255.255.255.0 192.168.80.2 250
no ip route 192.168.90.0 255.255.255.0 192.168.80.2 250
end
```

**SC-BR-R1**
```
configure terminal
no router rip
no ip route 192.168.10.0 255.255.255.0 192.168.80.1 250
no ip route 192.168.20.0 255.255.255.0 192.168.80.1 250
no ip route 192.168.30.0 255.255.255.0 192.168.80.1 250
no ip route 192.168.40.0 255.255.255.0 192.168.80.1 250
no ip route 192.168.50.0 255.255.255.0 192.168.80.1 250
end
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `no router rip` | RIP 프로세스와 그 안의 network, passive-interface 설정을 한 번에 삭제 | RIP가 남으면 OSPF와 경로가 섞여 어느 쪽에서 온 경로인지 구분하기 어렵다 |
| `no ip route ... 250` | 같은 경로와 같은 AD로 입력했던 예비 정적 경로를 삭제 | `no ip route`는 입력했던 줄과 글자가 같아야 지워진다. 삭제 전에 `include ip route`로 실제 줄을 확인한 이유다 |

**확인 (두 라우터)**
```
show ip protocols
show running-config | include ip route
show ip route
```
```
SC-BR-R1# ping 192.168.50.10
SC-HQ-R1# ping 192.168.60.1
SC-HQ-R1# ping 192.168.90.1
```

**결과**
- `show ip protocols`: 두 라우터 모두 출력이 없다(실행 중인 라우팅 프로토콜 없음).
- `show running-config | include ip route`: 두 라우터 모두 출력이 없다(정적 경로 0개).
- 본사 경로표: `C`와 `L`만 남았다(192.168.10, 20, 30, 40, 50, 70.0/24, 192.168.80.0/30). 이전에 있던 `R 192.168.60.0/24`와 `R 192.168.90.0/24`가 사라졌다.
- 지사 경로표: `C`와 `L`만 남았다(192.168.60, 70, 90.0/24, 192.168.80.0/30). `R 192.168.10`~`50.0/24` 5줄이 사라졌다.
- ping: 지사에서 192.168.50.10, 본사에서 192.168.60.1과 192.168.90.1 모두 0/5 실패. 본사와 지사 사이에 경로가 하나도 없다는 뜻이며 의도한 결과다.
- 주 회선 연결 대역(192.168.70.0/24)과 시리얼 구간(192.168.80.0/30)은 `C`로 남아 있다. 이 구간의 ping은 확인하지 않았다(미검증).
- 이 상태는 단계 4(OSPF area 0)에서 이웃이 맺어질 때까지 이어진다. 단계 5에서 `O` 경로가 되살아나는 것과 비교한다.

### 단계 3. 루프백과 router-id

**목적**: OSPF는 라우터마다 고유한 router-id(32비트 식별자)가 필요하다. 인터페이스 주소가 바뀌거나 내려가도 흔들리지 않도록 루프백 주소를 따로 만들어 router-id로 쓴다. 지사의 창고 루프백은 기존 `Loopback0`을 router-id용으로 넘기고 `Loopback1`로 옮긴다.

**지사 현재 상태 확인**
```
show ip interface brief
show running-config | section Loopback
```
- `Loopback0`이 `192.168.90.1/24`(설명 `Warehouse_Loopback`) 하나뿐이었다.

**SC-HQ-R1**
```
configure terminal
interface loopback 0
description RouterID_Loopback
ip address 192.168.255.1 255.255.255.255
no shutdown
exit
router ospf 1
router-id 192.168.255.1
end
```

**SC-BR-R1**
```
configure terminal
no router ospf 1
no interface loopback 0
interface loopback 0
description RouterID_Loopback
ip address 192.168.255.2 255.255.255.255
no shutdown
exit
interface loopback 1
description Warehouse_Loopback
ip address 192.168.90.33 255.255.255.224
no shutdown
exit
router ospf 1
router-id 192.168.255.2
end
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `interface loopback 0` + `/32` 주소 | 물리 링크가 없는 가상 인터페이스에 호스트 주소 하나를 준다 | 링크가 내려가도 항상 up 상태라 router-id가 바뀌지 않는다. /32는 이 주소 하나만 쓰겠다는 뜻이다 |
| `router ospf 1` | OSPF 프로세스 1을 만든다. 번호는 이 라우터 안에서만 쓰는 값이라 양쪽이 같을 필요는 없다 | 이웃과 맞춰야 하는 값은 프로세스 번호가 아니라 area 번호다 |
| `router-id 192.168.255.x` | router-id를 직접 지정한다 | 지정하지 않으면 가장 큰 루프백 주소, 없으면 가장 큰 인터페이스 주소가 자동 선택되어 나중에 주소를 바꿀 때 router-id가 달라질 수 있다. 같은 router-id를 가진 두 라우터는 이웃이 안 된다 |
| `no interface loopback 0` | 루프백 인터페이스와 그 안의 설정을 통째로 삭제 | 기존 창고 주소 192.168.90.1/24를 깨끗이 지우고 용도를 바꿔 다시 만든다 |
| 창고 `192.168.90.33 255.255.255.224` | 창고 대역을 /24에서 /27(192.168.90.32/27)로 줄인 새 루프백 | 계획서 확정값. 이후 OSPF에서 창고가 경로 하나로 전달되는지 본다 |

**확인**
```
show ip interface brief
show ip route
show ip protocols
```

**결과**
- 본사: `Loopback0 192.168.255.1 up/up`. 경로표에 `C 192.168.255.1/32 ... Loopback0`이 추가되었다. `show ip protocols`에 `ospf 1`, `Router ID 192.168.255.1`, `Number of areas in this router is 0`, `Routing for Networks`는 비어 있다.
- 지사: `Loopback0 192.168.255.2`, `Loopback1 192.168.90.33`이 모두 up/up이고 이전의 `192.168.90.1`은 없다. `show ip protocols`에 `ospf 1`, `Router ID 192.168.255.2`가 나온다. 지사 경로표에는 `C 192.168.90.32/27 ... Loopback1`, `L 192.168.90.33/32`, `C 192.168.255.2/32 ... Loopback0`이 있고 이전의 `192.168.90.0/24` 줄은 없다(`192.168.90.0/24 is variably subnetted, 2 subnets, 2 masks`는 /27과 /32가 같은 대역 아래 묶여 보이는 표시다).
- network 문이 아직 없어서 area가 0개이고 이웃과 `O` 경로는 없다. 단계 4에서 넣는다.

**막힌 곳**: 본사용 명령을 지사에 먼저 입력해 지사 router-id가 `192.168.255.1`(본사 값)로 잡혔다. `no router ospf 1`로 프로세스를 지우고 지사용 블록을 처음부터 다시 입력해서 `192.168.255.2`로 바로잡았다. router-id가 두 라우터에서 같으면 이웃이 맺어지지 않으므로, OSPF 설정 후에는 `show ip protocols`의 `Router ID`를 장비마다 확인해야 한다.

### 단계 4. OSPF area 0 선언과 이웃 확인

**목적**: 각 라우터가 어느 인터페이스를 OSPF에 참여시킬지 `network` 문으로 선언해, 이웃을 맺고 경로를 자동으로 주고받게 한다. 단계 2에서 모두 걷어낸 본사-지사 경로가 OSPF로 되살아나는지 확인한다.

**SC-HQ-R1**
```
configure terminal
router ospf 1
network 192.168.10.0 0.0.0.255 area 0
network 192.168.20.0 0.0.0.255 area 0
network 192.168.30.0 0.0.0.255 area 0
network 192.168.40.0 0.0.0.255 area 0
network 192.168.50.0 0.0.0.255 area 0
network 192.168.70.0 0.0.0.255 area 0
network 192.168.80.0 0.0.0.3 area 0
network 192.168.255.1 0.0.0.0 area 0
end
```

**SC-BR-R1**
```
configure terminal
router ospf 1
network 192.168.60.0 0.0.0.255 area 0
network 192.168.70.0 0.0.0.255 area 0
network 192.168.80.0 0.0.0.3 area 0
network 192.168.255.2 0.0.0.0 area 0
network 192.168.90.32 0.0.0.31 area 0
end
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `network <주소> <와일드카드> area 0` | 이 범위에 속한 주소를 가진 인터페이스를 OSPF에 참여시키고 area 0에 넣는다 | RIP의 `network`와 달리 와일드카드로 범위를 정확히 지정하고, 인터페이스의 area까지 같이 정한다. 선언한 대역은 경로로 광고되고, 그 인터페이스로 hello를 보내 이웃을 찾는다 |
| 와일드카드 `0.0.0.255` / `0.0.0.3` / `0.0.0.31` / `0.0.0.0` | 서브넷 마스크의 반대. 0이 "반드시 일치", 1이 "무관" | /24, /30, /27, /32에 각각 대응한다. 루프백은 `0.0.0.0`으로 정확히 그 주소만 지정한다 |
| `area 0` | 백본 area. 모든 다른 area는 area 0에 붙어야 한다 | 이번 토폴로지는 라우터가 둘뿐이라 area 0 하나로 충분하다 |

**확인**
```
show ip ospf neighbor
show ip route ospf
show ip protocols
```

**결과**
- 본사 이웃: `192.168.255.2`가 두 줄로 나온다. `FULL/  -`(Serial0/2/0, 점대점이라 DR 선출이 없어 `-`)와 `FULL/BDR`(Vlan70). 같은 상대 라우터가 두 링크로 각각 이웃을 맺은 것이며 정상이다. Vlan70에서는 지사가 BDR이므로 본사가 DR이다. Dead Time은 둘 다 39초대로, 기본 dead 시간 40초에서 줄어드는 값이다(hello 10초 기준).
- 본사 `O` 경로: `192.168.60.0 [110/2] via 192.168.70.2, Vlan70`, `192.168.90.33 [110/2]`(창고, /32), `192.168.255.2 [110/2]`. 모두 주 회선(Vlan70)을 지난다.
- 지사 `O` 경로: `192.168.10`~`50.0 [110/2] via 192.168.70.1, Gi0/1` 5줄, `192.168.255.1 [110/2]`.
- 경로 종류가 RIP와 다르다. AD가 120에서 110으로, 메트릭이 홉 수(1)에서 cost(2)로 바뀌었다. 예비 회선(시리얼)으로도 이웃이 맺어졌지만, 경로표에는 주 회선 쪽 경로만 올라온다(cost가 더 낮기 때문. 시리얼 cost는 단계 5에서 확인).
- `show ip protocols`: 본사는 `Router ID 192.168.255.1`에 network 8줄, 지사는 `Router ID 192.168.255.2`에 network 5줄이 area 0으로 나온다. `Number of areas in this router is 1`.
- ping: 지사에서 `192.168.50.1`, 본사에서 `192.168.60.1`과 `192.168.90.33`이 모두 5/5 성공했다. 단계 2에서 0/5였던 같은 경로가 OSPF로 복구되었다.
- 지사 이웃 표: 본사 `192.168.255.1`이 `FULL/  -`(Serial0/3/0, 192.168.80.1)와 `FULL/DR`(Gi0/1, 192.168.70.1) 두 줄로 나온다. 이웃 표의 `DR`과 `BDR`은 상대 라우터의 역할이다. 본사 표에서 지사가 `FULL/BDR`, 지사 표에서 본사가 `FULL/DR`이므로 Vlan70 구간에서는 본사가 DR, 지사가 BDR로 서로 일치한다. Pri는 시리얼이 0, 이더넷이 1이다.
- **창고가 /27이 아니라 /32(`192.168.90.33`)로 보인다.** 루프백은 OSPF가 기본적으로 호스트 경로로 광고하기 때문이다. 단계 5에서 `ip ospf network point-to-point`로 바꿔 /27이 보이게 한다.

### 단계 5. 창고 /27 광고와 cost 확인

**목적**: 창고 루프백이 /32가 아닌 원래 대역(/27)으로 전달되게 하고, 주 회선과 예비 회선의 cost를 비교해 경로표에 왜 주 회선만 올라오는지 확인한다.

**변경 전 확인 (SC-HQ-R1)**
```
show ip route ospf
```
- 창고가 `192.168.90.0/32 is subnetted` 아래 `O 192.168.90.33 [110/2] via 192.168.70.2, Vlan70`으로 보였다(/32 호스트 경로).

**SC-BR-R1**
```
configure terminal
interface loopback 1
ip ospf network point-to-point
end
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `ip ospf network point-to-point` | 이 인터페이스를 점대점 네트워크 타입으로 취급한다 | 루프백의 기본 타입은 loopback이라 OSPF가 주소를 `/32` 호스트 경로로 광고한다. 점대점으로 바꾸면 인터페이스에 설정한 서브넷 마스크(/27) 그대로 광고한다 |

**변경 후 확인**
```
show ip route ospf
show ip ospf interface brief
```

**결과**
- 본사 경로표: `192.168.90.0/27 is subnetted, 1 subnets` 아래 `O 192.168.90.32 [110/2] via 192.168.70.2, Vlan70`. /32 줄은 사라지고 /27 한 줄만 남았다. 이 줄의 시간이 00:00:13으로 새로 갱신된 것이 변경 시점과 맞는다.
- 지사 `Lo1`의 State가 `POINT`, 주소는 `192.168.90.33/255.255.255.224`이다. `Lo0`은 `WAIT`이다.
- cost:

| 인터페이스 | 본사 | 지사 | Cost |
|------------|------|------|------|
| LAN과 Vlan70, Gi0/1 | Gig0/0/0, Gig0/0/1, Vlan30, 40, 50, 70 | Gig0/0, Gig0/1 | 1 |
| 시리얼(예비) | Se0/2/0 | Se0/3/0 | 64 |
| 루프백 | Lo0 | Lo0, Lo1 | 1 |

- 본사에서 지사로 가는 경로 비용은 주 회선 경유가 2(Vlan70 1 + 지사 쪽 연결 대역 1), 예비 경유는 이보다 크다(시리얼 64가 들어감). OSPF는 cost가 가장 낮은 경로만 경로표에 올리므로 주 회선만 보이고, 예비는 대기 상태다. 이 구조가 RIP의 홉 수 기준과 다른 점이다. RIP는 두 경로가 모두 1홉이라 속도 차이를 몰랐다.
- cost 계산은 기준 대역폭(reference bandwidth, 기본 100Mbps)을 인터페이스 대역폭으로 나눈 값이다. 시리얼 1.544Mbps는 64, 이더넷은 1이다. 기가비트도 1이다. 지사 `Gi0/1`은 `show interfaces gigabitEthernet 0/1`에서 `BW 1000000 Kbit`로 나오는데, 100Mbps를 1Gbps로 나누면 1보다 작아서 cost는 최솟값 1이 된다. 그래서 기가비트와 패스트이더넷의 cost가 같아진다. 기본 기준 대역폭이 100Mbps라는 줄은 이 Packet Tracer의 `show ip ospf`에 나오지 않아 직접 확인하지 못했다(미검증). 둘을 구분하려면 `auto-cost reference-bandwidth`를 올려야 한다. 같은 출력에 `Full Duplex, 100Mbps`도 보이는데, 이는 실제 협상 속도이고 OSPF cost는 `BW` 값을 쓴다.
- 본사 인터페이스 표의 `Nbrs F/C` 열이 Vlan70과 Se0/2/0에서 `0/0`으로 나온다. 같은 시점에 이웃 표에는 FULL 이웃이 있었다. 본사에서 `show ip ospf interface`를 인자 없이 입력하자 Vlan70(`Neighbor Count is 1, Adjacent neighbor count is 1`, 지사가 Backup Designated Router)와 Serial0/2/0(`Neighbor Count is 1`, `Adjacent with neighbor 192.168.255.2`)에 이웃이 1개씩 잡혀 있었다. 따라서 요약표의 `0/0`은 Packet Tracer의 표시 한계다. 같은 출력에서 타이머는 `Hello 10, Dead 40`이고, 시리얼은 `Network Type POINT-TO-POINT, Cost: 64`, 루프백은 `LOOPBACK, Cost: 1`, `treated as a stub Host`로 나온다.
- 지사에서 확인한 이웃과 DR 역할은 단계 4에 적었다.

**막힌 곳: 이웃은 FULL인데 지사에 OSPF 경로가 없었다**
- 증상: 단계 6 장애 실험 직전 점검(6-0)에서 지사의 `show ip route | include 192.168.50.0`이 빈 출력이었다. `show ip route ospf`도 비었고 `show ip route 192.168.50.0`은 `% Network not in table`이었다. 그런데 `show ip ospf neighbor`는 본사와 FULL 두 줄이었다.
- 원인 진단: 본사 `show ip ospf database`에는 라우터 LSA 2개와 Vlan70 네트워크 LSA 1개가 있었지만, 지사에는 지사 자신의 라우터 LSA 1개뿐이었다. 본사 LSA가 지사 LSDB에 없어서 SPF가 본사 쪽 경로를 계산하지 못한 것이다. 이웃 상태가 FULL이어도 LSDB가 비어 있으면 경로가 생기지 않는다.
- 단계 4에서는 지사에 `O` 경로가 있었으므로 그 뒤에 LSDB에서 사라진 것이다. 언제 어떤 이유로 사라졌는지는 확인하지 못했다(미확인). Realtime 모드였고 단계 5 이후 장비 조작은 없었다. 단계 5의 `ip ospf network point-to-point`가 영향을 줬는지도 가리지 못했다.
- 문제가 지사 쪽에만 있었다는 증거: 복구 뒤 본사 `show ip route ospf`의 경로 시간이 22분, 15분, 21분으로 끊기지 않고 이어져 있었다. 본사는 한 번도 경로를 잃지 않았다.
- 복구: 지사에서 `clear ip ospf process`를 입력하고 프롬프트 `Reset ALL OSPF processes? [no]:`에 `yes`를 직접 입력했다. 처음에는 엔터만 쳐서 기본값 `no`로 처리되어 초기화가 되지 않았다(LSA Age가 계속 늘어난 것이 증거).
- 복구 결과: LSDB에 라우터 LSA 2개와 네트워크 LSA 1개가 보이고, 지사에 `O 192.168.10`~`50.0`과 `O 192.168.255.1`이 돌아왔다(`[110/2] via 192.168.70.1`).
- 부수 변화: 초기화 후 Vlan70 구간의 DR이 바뀌었다. 지사 이웃 표에서 본사가 `FULL/DR`에서 `FULL/BDR`로, 네트워크 LSA의 광고자가 지사(`192.168.70.2`)로 나온다. DR 선출은 우선순위가 같으면 router-id가 큰 쪽이 이기고(지사 255.2 > 본사 255.1), 이미 DR이 있으면 나중에 뒤집히지 않는다. 이번에는 양쪽이 같이 다시 시작해서 router-id가 큰 지사가 DR이 된 것으로 보이지만, 선출 과정은 직접 확인하지 않았다.
- 교훈: 경로 문제는 이웃 표만 보지 말고 `show ip ospf database`와 경로표를 함께 본다. 장애 실험 전에 지사 `show ip route ospf`로 정상 상태를 확인하는 단계(6-0)를 넣은 것이 이 문제를 잡았다.

#### (나) 본사 Vlan70 shutdown (지사 링크는 유지, hello만 막는 장애)

**목적**: RIP 기준선과 같은 조건(지사 링크를 살려 둔 채 본사 Vlan70만 내림)에서 OSPF가 장애를 알아채는 시간을 잰다.

**SC-BR-R1** (디버그 준비)
```
configure terminal

end
debug ip ospf hello
debug ip ospf ?
debug ip ospf events
```

- `debug ip ospf hello`는 `% Invalid input`으로 거부되었다. `debug ip ospf ?`로 지원 항목을 확인하니 `adj`(OSPF adjacency events)와 `events`(OSPF events) 둘뿐이었다. `events`를 켜자 10초마다 hello 수신 줄이 찍혔다. Gi0/1(192.168.70.1)에서는 매 분 끝자리 7초(04:45:37, 47, 57, 04:46:07), Serial0/3/0에서는 끝자리 9초에 `OSPF: Rcv hello from 192.168.255.1 ...`이 나온다.

**SC-HQ-R1** (Gi0/1 hello가 찍힌 직후에)
```
configure terminal
interface vlan 70
shutdown
end
```

**SC-BR-R1** (장애 후)
```
show clock
show ip route ospf
show ip ospf neighbor
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `debug ip ospf events` | OSPF 이벤트를 콘솔에 출력(이 Packet Tracer에서는 hello 수신 포함) | 마지막 hello를 받은 시각을 지사 시계로 직접 읽는다 |
| `show clock` | 지사 라우터의 현재 시각 | 경로 나이에서 전환 시각을 거꾸로 계산하는 기준으로 쓴다 |

**결과** (지사 시계)
- 장애 후 확인 시각 `4:47:54.278`. 경로는 `[110/65] via 192.168.80.1, Serial0/3/0`이고 나이는 1분 8초(68초)다. `show clock` 직후 몇 초 안에 경로표를 봤으므로 거꾸로 계산한 전환 시각은 4:46:46에서 4:46:51 사이다.
- 이웃 표에는 시리얼 줄(`FULL/  -`)만 남고 Gi0/1 줄이 없다. LSDB의 LSA는 3개 그대로다(`Number of LSA 3`).
- 디버그 로그 전체(지사 시계)로 확인한 시각:

| 시각 | 사건 |
|------|------|
| 04:46:37 | 마지막으로 받은 Gi0/1(192.168.70.1) hello. 이후 04:46:47에는 Gi0/1 hello가 오지 않았다(시리얼 hello만 계속 옴) |
| 04:46:46 - 04:46:51 | 경로가 `Serial0/3/0` 경유 `[110/65]`로 전환(경로 나이로 계산) |
| 04:47:17 | `%OSPF-5-ADJCHG: Process 1, Nbr 192.168.255.1 on GigabitEthernet0/1 from FULL to DOWN, Neighbor Down: Dead timer expired` |

- **dead 타이머는 마지막 hello(04:46:37)에서 정확히 40초 뒤인 04:47:17에 끝났다.** hello 10초의 4배라는 기본값과 일치한다.
- **그런데 경로는 그보다 약 30초 먼저 바뀌었다.** 마지막 hello 후 약 9초에서 14초 만에 시리얼 경유로 전환되어, 이웃이 내려간(DOWN) 시각보다 앞선다. 이 시점에 지사 쪽 Gi0/1은 링크가 살아 있어 지사가 스스로 장애를 알 수 있는 상태가 아니었다.
- **이유는 추정이다.** 본사가 Vlan70을 내리면서 자기 라우터 LSA를 갱신했고, 이 갱신이 살아 있는 시리얼 이웃을 통해 지사로 전달되었다. 지사의 SPF 계산(SPF schedule delay 5초)에서 본사가 더 이상 Vlan70 연결을 광고하지 않으므로 Gi0/1 경유 경로가 제외된 것으로 보인다. 로그에 LSA 수신 줄은 찍히지 않아(`debug ip ospf events`의 한계) 직접 확인하지는 못했고, 시각 순서가 이 설명과 맞는다는 것이 근거의 전부다.
- 장애 중 지사 ping 결과는 기록하지 못했다(미검증). Gi0/1 DOWN 로그 직후 DR/BDR 재선출이 일어나 지사가 DR이 되었다(`Elect DR 192.168.255.2`, `BDR: none`).

**RIP와 비교**

| 항목 | RIP(단계 1) | OSPF(단계 6 나) |
|------|-------------|------------------|
| 마지막 신호에서 경로 전환까지 | 마지막 갱신 후 402초에서 475초 사이 | 마지막 hello 후 약 9초에서 14초 |
| 이웃 다운(타이머 만료)까지 | 해당 로그 없음(경로 상태가 `possibly down`으로 남음) | 마지막 hello 후 40초(dead 타이머) |
| 예비로 바뀐 표시 | `R`에서 `S [250/0]` | `O [110/2]`에서 `O [110/65]`(같은 프로토콜 안에서 다른 경로) |

- 같은 지표(마지막 신호에서 경로가 예비로 바뀐 시각까지)로 비교하면 OSPF가 RIP보다 대략 30배에서 50배 빠르다(402초에서 475초를 약 9초에서 14초로 나눈 범위. 시각 계산에 기반한 추정).
- 예상과 달랐던 점: 타이머 기반 감지는 40초라고 보았는데, 실제 경로 전환은 타이머 만료 전에 일어났다. 전환을 일으킨 것은 지사의 감지가 아니라 본사의 LSA 갱신이 시리얼 이웃으로 전달된 것으로 보인다(추정).
- RIP 실험에서는 시리얼 구간이 passive라 본사가 이 변화를 시리얼로 알릴 수 없었고, 죽은 경로가 AD 120으로 AD 250 예비 경로를 계속 이겼다. OSPF는 예비 시리얼 구간에도 이웃이 맺혀 있어 장애 정보가 그 링크로 바로 전달되고, 예비 경로도 같은 OSPF 안에서 cost로 비교된다. 이 차이가 감지 속도 차이의 가장 큰 이유로 보인다(추정).
- 본사가 지사에 이 변화를 알릴 시리얼 경로가 없었다면 타이머 40초가 전환 시간이 되었을 것이다. 이 경우는 실험하지 않았다(미검증).

**복구**

**SC-BR-R1**
```
undebug all
```

**SC-HQ-R1**
```
configure terminal
interface vlan 70
no shutdown
end
```

**SC-BR-R1** (복구 확인)
```
show ip route ospf
show ip ospf neighbor
show ip ospf database
```

**결과**: 지사 경로표가 `[110/2] via 192.168.70.1, GigabitEthernet0/1`(나이 4초)로 돌아왔다. 이웃은 시리얼 `FULL/  -`와 Gi0/1 `FULL/BDR` 두 줄이다. LSDB에는 라우터 LSA 2개(Age 16)와 Vlan70 네트워크 LSA 1개(광고자 192.168.70.2, Age 737)가 있어 단계 5에서 겪은 LSDB 문제는 재발하지 않았다. (가)와 (나) 모두 수동 조작 없이 본사 `no shutdown`만으로 주 회선 경로가 돌아왔다.

### 단계 7. passive-interface default와 이웃 구간만 열기

**목적**: PC가 있는 LAN 쪽 포트로는 OSPF hello를 보낼 필요가 없다. 기본을 passive로 막고 이웃이 있는 구간만 열어, LAN으로 OSPF 패킷이 나가는 것을 막는다. passive 인터페이스의 대역도 `network` 문에 포함되어 있으면 계속 경로로 광고된다.

**SC-HQ-R1**
```
configure terminal
router ospf 1
passive-interface default
no passive-interface vlan 70
no passive-interface serial 0/2/0
end
```

**SC-BR-R1**
```
configure terminal
router ospf 1
passive-interface default
no passive-interface gigabitethernet 0/1
no passive-interface serial 0/3/0
end
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `passive-interface default` | 모든 인터페이스를 passive로 만든다 | 새 인터페이스가 생겨도 기본이 passive라서, 이웃이 필요한 구간만 의도적으로 열게 된다 |
| `no passive-interface <인터페이스>` | 그 인터페이스만 passive를 해제한다 | 이웃 구간(본사 Vlan70과 Serial0/2/0, 지사 Gi0/1과 Serial0/3/0)에서는 hello를 주고받아야 이웃이 유지된다 |

**주의**: `passive-interface default`를 입력하는 순간 이웃 구간도 passive가 되어 이웃이 dead 타이머(40초) 뒤에 끊긴다. 그래서 `no passive-interface`를 곧바로 이어서 입력하도록 한 블록으로 붙여넣었다.

**확인**
```
show ip protocols
show ip ospf neighbor
show ip route ospf
```
```
SC-HQ-R1# ping 192.168.60.1
SC-BR-R1# ping 192.168.50.1
```

**결과**
- 본사 `Passive Interface(s)`: Gi0/0/0, Gi0/0/1, Gi0/0/2, Serial0/2/1, Vlan30, Vlan40, Vlan50, Loopback0. Vlan70과 Serial0/2/0은 목록에 없다(열려 있다).
- 지사 `Passive Interface(s)`: Vlan1, Gi0/0, Serial0/3/1, Loopback0, Loopback1. Gi0/1과 Serial0/3/0은 목록에 없다.
- 사용하지 않는 포트(본사 Gi0/0/2, Serial0/2/1, 지사 Vlan1, Serial0/3/1)도 `default` 덕분에 자동으로 passive가 된다.
- 양쪽 이웃은 시리얼 `FULL/  -`와 주 회선 `FULL/BDR`(본사 표) 또는 `FULL/DR`(지사 표) 두 줄로 유지되었고, `O` 경로도 그대로다(본사: 60.0, 90.32/27, 255.2, 지사: 10~50.0, 255.1). 본사 `ping 192.168.60.1`과 지사 `ping 192.168.50.1`은 5/5 성공했다.
- LAN 쪽으로 hello가 실제로 나가지 않는지는 확인하지 않았다(미검증. `show ip ospf interface`에서 passive 표시를 보면 확인할 수 있다).

### 단계 8. MD5 인증

강사님 순서대로 인터페이스 방식을 적용하고, 취소한 뒤 area 방식으로 다시 한다. 키 값은 문서에 쓰지 않는다(아래는 `<키>`로 표시).

#### 8-1. 인터페이스 방식 (주 회선 Vlan70 구간)

**목적**: 구간마다 본사에만 먼저 설정해 이웃이 끊기는 것을 확인하고, 지사에 설정해 복구되는지 본다.

**SC-HQ-R1** (본사만 먼저)
```
configure terminal
interface vlan 70
ip ospf authentication message-digest
ip ospf message-digest-key 1 md5 <키>
end
```

**SC-BR-R1** (지사 설정)
```
configure terminal
interface gigabitethernet 0/1
ip ospf authentication message-digest
ip ospf message-digest-key 1 md5 <키>
end
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `ip ospf authentication message-digest` | 이 인터페이스에서 MD5 인증을 쓰겠다고 선언한다 | 선언하지 않으면 키가 있어도 인증 없이 hello를 주고받는다 |
| `ip ospf message-digest-key 1 md5 <키>` | 키 번호 1에 MD5 키 값을 지정한다 | 키 번호와 키 값이 양쪽에서 같아야 서로의 패킷을 믿는다. 번호는 키를 교체할 때 구분하는 용도다 |

**결과**
- 설정 후 지사 `show ip ospf interface gigabitEthernet 0/1`: 이웃은 `Neighbor Count is 1, Adjacent neighbor count is 1`(본사, 이 시점에 지사가 DR)이고 `Message digest authentication enabled`, `Youngest key id is 1`이 나온다.
- 양쪽 이웃은 시리얼 `FULL/  -`와 주 회선 FULL 두 줄이고, `O` 경로(본사 60.0, 90.32/27, 255.2, 지사 10~50.0, 255.1)가 Vlan70과 Gi0/1 경유 cost 2로 있다. 경로 나이가 21초(본사)와 39초(지사)로 짧아 최근에 다시 계산된 것으로 보인다.
- **본사만 설정한 직후 이웃이 끊기는지는 기록하지 못했다(미검증).** 결과 출력이 양쪽 설정을 마친 뒤의 것이다.
- 키 값은 이 출력에 나타나지 않았다.
