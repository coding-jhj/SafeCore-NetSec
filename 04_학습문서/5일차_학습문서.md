## 1. 한눈에 보기

| 항목 | 내용 |
|------|------|
| 문제 | 정적 라우팅은 지사에 네트워크가 늘 때마다 양쪽 라우터에 경로를 손으로 추가해야 한다 |
| 한 일 | 주 회선 구간을 RIPv2로 전환, 예비 회선(시리얼, AD 250 정적)은 유지, 시리얼과 LAN 쪽 passive |
| 증명 | 지사에 창고(루프백 192.168.90.0/24)를 만들고 `network` 한 줄만 추가하자 본사가 자동 학습 |
| 발견 | RIP이 자동으로 해 주는 것은 주 회선뿐이다. 예비 회선은 새 네트워크마다 본사에 정적 경로를 추가해야 한다 |
| 못 한 것 | RIP 인증, 경로 필터, 유니캐스트 이웃은 Packet Tracer 미지원 |

## 2. 왜 하는가

- 지금까지 본사와 지사 라우터에는 경로를 사람이 직접 적어 두었다(정적 라우팅). 지사에 네트워크가 하나 늘면 양쪽에 경로를 추가해야 하고, 빠뜨리면 그 네트워크는 본사와 통신이 안 된다.
- RIP은 라우터끼리 자기가 아는 네트워크를 서로 알려주는 동적 라우팅 프로토콜이다. 지사 라우터에 새 네트워크 선언만 추가하면 본사가 학습한다.
- 4일차의 예비 회선(시리얼, AD 250 정적 경로)은 그대로 두고 주 회선 구간만 정적에서 RIP으로 바꾼다.
- 사무실(PC) 쪽 포트로는 RIP 광고가 나가지 않게 막는다(passive). RIP 인증으로 가짜 라우터를 막는 것은 개념으로 정리하고 실습을 시도했으나 Packet Tracer가 지원하지 않아 검증하지 못했다(단계 6).

## 3. 핵심 개념

### 3-1. 정적 라우팅과 동적 라우팅

| 구분 | 정적 | 동적 |
|------|------|------|
| 경로 입력 | 관리자가 직접 | 라우터끼리 교환 |
| 네트워크 추가 | 양쪽에 수동 추가 | 선언만 추가하면 상대가 학습 |
| 장애 대응 | 인터페이스가 down일 때만 경로가 사라짐 | 광고가 끊기면 경로가 사라짐 |
| 부하 | 거의 없음 | 주기적 광고 필요 |

### 3-2. 라우팅 프로토콜의 분류

| 기준 | 종류 |
|------|------|
| 적용 범위 | IGP(조직 내부: RIP, OSPF, EIGRP), EGP(조직 사이: BGP) |
| 계산 방식 | 거리 벡터(RIP: 이웃이 알려준 경로와 거리를 믿음), 링크 상태(OSPF: 전체 지도를 만들어 직접 계산) |

### 3-3. RIP의 특성

| 항목 | 내용 |
|------|------|
| 종류 | 거리 벡터 방식의 IGP |
| metric | 홉 수만 본다(대역폭과 지연은 고려하지 않음). 최대 15홉이며 16은 도달 불가 |
| 광고 | 30초마다 라우팅 테이블을 이웃에게 광고(UDP 520) |
| 기본 타이머 | update 30초, invalid 180초, holddown 180초, flush 240초. 그래서 수렴이 느리다 |
| 기본 AD | 120. 정적(1)보다는 못 믿고, 우리 예비 경로(250)보다는 더 믿는다 |

### 3-4. RIPv1과 RIPv2

| 구분 | v1 | v2 |
|------|-----|-----|
| 서브넷 마스크 전달 | 안 함(클래스풀) | 함(클래스리스, VLSM 가능) |
| 광고 방식 | 브로드캐스트 | 멀티캐스트 224.0.0.9 |
| 인증 | 없음 | 지원 |

### 3-5. auto-summary

다른 클래스 경계를 넘을 때 자동으로 클래스 단위로 요약하는 기능이다. 192.168.80.0/30 같은 작은 대역이 섞인 우리 구성에서는 경로가 틀어질 수 있어 끈다.

### 3-6. network 명령은 클래스 기준이다

- RIP의 `network`는 "어느 인터페이스에서 RIP을 켤지"를 정하며, 주소는 클래스 기준으로 해석된다.
- 192.168.x.0은 C 클래스라서 대역마다 따로 선언해야 한다. `network 192.168.0.0` 하나로는 192.168.0.x 대역만 해당하고 우리 대역에는 RIP이 켜지지 않는다(실수 2).

### 3-7. passive-interface

- 해당 인터페이스로 RIP 광고를 내보내지 않게 한다. 고전적인 RIP에서는 송신만 막고 수신은 막지 않는다(Packet Tracer의 수신 동작은 시험하지 않았다).
- LAN 쪽 용도: PC 쪽으로 내부 대역 정보를 보낼 이유가 없고, 그 포트에서 이웃 라우터 관계가 만들어지는 것을 막는다. PC가 보내는 가짜 광고를 거부하는 효과는 없다.
- 예비 시리얼 용도: 예비 회선을 4일차의 정적 floating route로만 쓰려는 설계 의도다.

### 3-8. RIPv2 인증

- 이웃이 맞는 키를 가졌을 때만 광고를 받아들이게 한다. 평문 인증은 패킷에 비밀번호가 그대로 보이고, MD5는 해시로 보내서 직접 보이지 않는다.
- 한쪽에만 걸면 이웃 관계가 끊기므로 양쪽에 같이 걸어야 한다.
- 이 Packet Tracer는 인터페이스에 RIP 인증을 적용하는 명령을 지원하지 않는다(단계 6-4).

### 단계 0. 작업 전 상태 확인

**목적**: 바꾸기 전 상태를 기록하고 예비 경로가 실제로 설정에 있는지 확인한다. 예비 경로 없이 주 경로를 지우면 연결이 끊긴다.

**SC-HQ-R1**
```
show ip route static

```

**SC-BR-R1**
```
show ip route static
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `show ip route static` | 라우팅 테이블 중 정적 경로만 표시 | 지금 쓰이는 정적 경로를 확인한다. AD 250 예비 경로는 대기 중이라 여기에 안 보이는 게 정상이다 |
| `show running-config \| include ip route` | 설정 중 `ip route`가 들어간 줄만 표시 | 대기 중인 예비 경로(AD 250)까지 설정 전체를 확인한다 |
| `show ip route` | 라우팅 테이블 전체 | 연결(C), 자기 주소(L), 정적(S)을 한눈에 본다 |
| `ping 192.168.10.1` | 지사에서 본사 연구개발 게이트웨이로 ICMP | 변경 전 통신 기준을 잡는다 |

**결과**

- 지사 ping 80%(4/5). 첫 패킷만 유실되었고, ARP 학습 과정으로 추정한다.

### 단계 1. 주 회선 정적 경로 삭제 (예비는 유지)

**목적**: RIP이 경로를 대신 학습하도록 주 회선(192.168.70.x)을 next-hop으로 하는 정적 경로(AD 1)를 지운다. 남아 있으면 AD 1이 RIP의 AD 120보다 우선해서 RIP 경로가 올라오지 못한다.

**SC-HQ-R1**
```
configure terminal
no ip route 192.168.60.0 255.255.255.0 192.168.70.2
exit
```

**SC-BR-R1**
```
configure terminal
no ip route 192.168.10.0 255.255.255.0 192.168.70.1
no ip route 192.168.20.0 255.255.255.0 192.168.70.1
no ip route 192.168.30.0 255.255.255.0 192.168.70.1
no ip route 192.168.40.0 255.255.255.0 192.168.70.1
no ip route 192.168.50.0 255.255.255.0 192.168.70.1
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `configure terminal` | 전역 설정 모드 진입 | 설정을 바꾸려면 필요하다 |
| `no ip route 대역 마스크 192.168.70.x` | 해당 정적 경로 삭제 | next-hop까지 정확히 적어야 그 경로(AD 1)만 지워지고 같은 대역의 예비 경로(192.168.80.x, AD 250)는 남는다 |
| `exit` | 설정 모드 종료 | 이후 `show` 명령을 쓰기 위해서다 |

**확인**: 양쪽 `show ip route static`, `show running-config | include ip route`, 지사 `ping 192.168.10.1`

**결과**
- 양쪽 라우팅 테이블에 `S ... [250/0]` 예비 경로가 올라왔다(본사 1줄, 지사 5줄). 주 경로가 사라지자 대기하던 AD 250 경로가 선택된 것이다.
- 지사 ping 5/5 성공, 왕복 2/20/39 ms(최소/평균/최대). 단계 0의 0 ms와 비교하면 트래픽이 느린 시리얼 선으로 옮겨 갔음을 알 수 있다.

### 단계 2. 두 라우터에 RIPv2 설정

**목적**: 라우터끼리 경로를 자동으로 주고받게 한다. 대역마다 `network`를 선언해서 해당 인터페이스에서 RIP이 켜지게 한다.

**SC-HQ-R1**
```
configure terminal
router rip
version 2
no auto-summary
no network 192.168.0.0
network 192.168.10.0
network 192.168.20.0
network 192.168.30.0
network 192.168.40.0
network 192.168.50.0
network 192.168.70.0
network 192.168.80.0
exit
exit
```

**SC-BR-R1**
```
configure terminal
router rip
version 2
no auto-summary
no network 192.168.0.0
network 192.168.60.0
network 192.168.70.0
network 192.168.80.0
exit
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `router rip` | RIP 설정 모드 진입 | RIP 프로세스를 켜고 설정한다 |
| `version 2` | RIP 버전 2 | 서브넷 마스크를 전달해서 /24와 /30이 섞인 구성에 맞고 인증도 쓸 수 있다 |
| `no auto-summary` | 클래스 경계 자동 요약 끄기 | 켜져 있으면 192.168.80.0/30 같은 작은 대역이 요약되어 경로가 틀어질 수 있다 |
| `no network 192.168.0.0` | 잘못 넣은 선언 제거 | 처음에 넣은 `network 192.168.0.0`은 효과가 없어 정리한다(실수 2) |
| `network 192.168.X.0` | 해당 대역의 인터페이스에서 RIP 활성화 | C 클래스라 대역마다 선언한다. 이 선언이 있어야 그 인터페이스로 광고를 보내고 받는다 |

이 단계에서는 부서 LAN, 주 회선, 예비 시리얼 대역을 전부 선언했다. 아직 passive가 없어서 RIP이 예비 시리얼로도 나간다. 그 동작을 먼저 관찰하고 단계 3에서 막는다.

**확인**: 양쪽 `show ip protocols`, `show ip route`, 지사 `ping 192.168.10.1`

| 명령어 | 읽는 법 |
|--------|---------|
| `show ip protocols` | `Routing for Networks`에 선언한 대역, Interface 목록의 Send/Recv, `Routing Information Sources`의 이웃 주소를 본다 |
| `show ip route` | 앞에 `R`이 붙고 `[120/1]`인 줄이 RIP 경로다. 예비 정적 `[250/0]`가 `R`로 대체된다 |

**결과 (정정 후)**
- 양쪽 `show ip protocols`: 선언한 대역이 모두 나열되고, RIP이 켜진 인터페이스가 전부 표시되었다(Send 2, Recv 2는 version 2 송수신, 본사 7개와 지사 3개). Key-chain 열은 비어 있다(인증은 단계 6). `Routing Information Sources`에 이웃이 나타났다(본사 쪽 192.168.70.2, 192.168.80.2 / 지사 쪽 192.168.70.1, 192.168.80.1, 둘 다 distance 120).
- 본사 `show ip route`: `R 192.168.60.0/24 [120/1] via 192.168.70.2, Vlan70`과 `[120/1] via 192.168.80.2, Serial0/2/0`, 같은 경로가 두 줄.
- 지사 `show ip route`: 192.168.10, 20, 30, 40, 50 대역이 각각 `via 192.168.70.1, GigabitEthernet0/1`과 `via 192.168.80.1, Serial0/3/0` 두 줄씩.
- 4일차의 `S [250/0]` 예비 정적 경로는 테이블에서 사라졌다. 설정에서 지워진 것이 아니라 RIP(AD 120)이 예비(AD 250)보다 우선해서 대기 상태가 된 것이다.
- 지사 `ping 192.168.10.1`: 5/5 성공, 0/5/26 ms. 이더넷과 시리얼을 섞어 쓴 결과로 추정한다(확인 필요).
- 캡처: `5일차_3_RIP적용후_본사_경로2줄.png`, `5일차_4_RIP적용후_지사_경로2줄.png`

**읽을 점: 왜 경로가 두 줄인가**
- RIP의 metric은 홉 수뿐이다. 이더넷 주 회선과 시리얼 예비 회선 모두 한 홉이라 metric이 1로 같고, RIP은 대역폭 차이를 구분하지 못한다.
- metric이 같으면 동등 비용 경로를 모두 올린다(`Maximum path: 4`). 그래서 트래픽이 빠른 이더넷과 느린 시리얼로 나뉠 수 있다.
- 시리얼을 예비로만 쓰려는 우리 설계 의도와 다르다. 그래서 단계 3에서 시리얼을 passive로 막는다.

### 단계 3. 예비 회선(시리얼) passive

**목적**: RIP 광고가 예비 시리얼로 나가지 않게 막아서 RIP 경로가 주 회선 하나로만 학습되게 한다. 예비 회선은 4일차의 정적 floating route(AD 250)로만 쓴다.

**SC-HQ-R1**
```
configure terminal
router rip
passive-interface Serial0/2/0
exit
exit
```

**SC-BR-R1**
```
configure terminal
router rip
passive-interface Serial0/3/0
exit
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `router rip` | RIP 설정 모드 진입 | passive 설정은 이 모드 안에서 한다 |
| `passive-interface Serial0/2/0` | 해당 인터페이스로 RIP 광고를 보내지 않음 | 시리얼로 RIP 경로가 오가면 이더넷과 같은 metric이라 트래픽이 나뉜다. 광고를 막으면 RIP은 이더넷으로만 학습한다 |

**확인**: 양쪽 `show ip protocols`, `show ip route`, 지사 `ping 192.168.10.1`

| 확인 | 읽는 법 |
|------|---------|
| `show ip protocols` | `Passive Interface(s)`에 Serial 인터페이스가 나타난다 |
| `show ip route` | 이미 시리얼로 학습한 경로는 바로 사라지지 않고 invalid 타이머(180초)가 지나야 사라진다. 시간이 지나면 R 경로가 주 회선 한 줄만 남는다 |

**결과 (입력 직후)**
- 양쪽 `show ip protocols`: `Passive Interface(s)`에 해당 시리얼(본사 Serial0/2/0, 지사 Serial0/3/0)이 표시되고 Interface Send/Recv 목록에서 시리얼이 빠졌다. `Routing for Networks`에는 192.168.80.0이 남아 있다. 대역 선언은 유지한 채 광고 송신만 막은 것이다.
- `show ip route`: 입력 직후에는 시리얼 경로가 남아 있었다. 지사 쪽은 주 회선 경로(192.168.70.1)가 00:00:22로 계속 갱신되는 반면 시리얼 경로(192.168.80.1)는 00:01:48로 시간이 늘고 있다. 본사가 시리얼로 광고하지 않아 갱신이 끊기고 노화가 시작된 것이다. Routing Information Sources에서도 192.168.80.1의 Last Update가 00:01:45로 길어졌다.
- 본사 쪽 192.168.80.2는 Last Update가 00:00:21로 아직 짧았다. 지사에 passive를 본사보다 늦게 입력해서 노화 시작이 늦은 것으로 추정한다(확인 필요).
- 지사 `ping 192.168.10.1`: 5/5 성공, 0/3/14 ms.

**결과 (타이머 경과 후)**
- 본사: `R 192.168.60.0/24 [120/1] via 192.168.70.2, 00:00:08, Vlan70` 한 줄만 남았다. 시리얼 경유 경로는 사라졌다.
- 지사: 192.168.10, 20, 30, 40, 50 대역이 모두 `[120/1] via 192.168.70.1, GigabitEthernet0/1` 한 줄씩만 남았다.
- 양쪽 Last Update가 00:00:08, 00:00:02로 짧아서 주 회선으로는 광고를 계속 주고받는다.
- 192.168.80.0/30은 `C`(직접 연결)로 남아 있다. 시리얼 선은 up이고 RIP 광고만 막은 것이다.
- 해석: 시리얼로 광고가 오가지 않아 이미 학습한 시리얼 경로가 갱신이 끊긴 채 타이머를 넘겨 사라졌다. RIP 경로는 주 회선 하나로만 남고 예비 회선은 AD 250 정적 경로로만 쓰이는 상태가 됐다. 이 정적 경로는 설정에 남아 있고 RIP 경로가 사라질 때 올라온다(단계 5).
- 캡처: `5일차_5_시리얼passive후_본사_경로1줄.png`, `5일차_6_시리얼passive후_지사_경로1줄.png`. 단계 2 캡처(경로 두 줄)와 비교하면 passive의 효과가 보인다. 경로가 줄어드는 중간 장면은 캡처하지 못했다.
- 이 시점의 `show ip protocols`는 보지 않았고, 단계 6-1에서 시리얼 passive 표시를 확인했다.

### 단계 4. 지사에 창고 네트워크 추가, 동적 학습 확인

**목적**: 오늘 목표의 핵심 증명이다. 지사에 새 네트워크를 만들고 지사 라우터에 RIP `network` 선언만 추가했을 때 본사가 경로를 손으로 적지 않아도 자동 학습하는지 확인한다.

| 항목 | 값 |
|------|-----|
| 방식 | 루프백(가상 인터페이스) |
| 창고 네트워크 | 192.168.90.0/24 |
| 만드는 곳 | 지사 라우터 SC-BR-R1의 Loopback0, 주소 192.168.90.1 |

- 수업에서 루프백으로 배웠고, 루프백도 본사 PC에서 `ping 192.168.90.1`로 통신 증거를 남길 수 있어서 루프백으로 정했다.
- 참고: 처음에는 지사 라우터(2901)에 HWIC-4ESW 모듈을 넣어 실제 LAN(VLAN 90, 스위치, PC)을 만들려고 했다. 이 모듈은 설정 모드의 `vlan 90`이 거부되고(`% Invalid input detected`), 특권 모드의 `vlan database`로 VLAN을 만들어야 한다는 것까지 확인한 뒤 루프백으로 바꿨다. 만든 VLAN 90은 삭제했고 모듈은 꽂아 둔 채 쓰지 않는다.

**4-1. 추가 전 상태 확인**
- 지사 `show ip route`: R 경로 192.168.10, 20, 30, 40, 50이 `[120/1] via 192.168.70.1, GigabitEthernet0/1`로 올라와 있고 192.168.90.0은 없다. 캡처: `5일차_7_창고추가전_지사_경로.png`
- 확인하지 못한 것: 본사의 추가 전 `show ip route`는 캡처하지 못했다. 본사 쪽 증거는 추가 후 출력만 있다.

**4-2. 지사에 루프백 생성 (SC-BR-R1)**
```
configure terminal
interface loopback 0
description Warehouse_Loopback
ip address 192.168.90.1 255.255.255.0
exit
end
show ip interface brief
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `interface loopback 0` | 라우터 안의 가상 인터페이스 | 케이블과 장비 없이 "지사에 새 네트워크가 생긴 상황"을 만든다. 항상 up이라 안정적이다 |
| `ip address 192.168.90.1 255.255.255.0` | 창고 네트워크 주소 | 192.168.90.0/24를 지사 라우터의 직접 연결 네트워크로 만든다 |

**결과**: `Loopback0 192.168.90.1 YES manual up up`. 다른 인터페이스(Gi0/0, Gi0/1, Serial0/3/0)는 그대로 up/up이다.

**4-3. 핵심: RIP network 한 줄 추가 (SC-BR-R1)**
```
configure terminal
router rip
network 192.168.90.0
end
copy running-config startup-config
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `network 192.168.90.0` | 이 대역에 RIP을 켜고 광고 대상에 포함 | 오늘 목표의 증명이다. 본사 라우터에는 아무것도 입력하지 않는다 |

**4-4. 본사에서 자동 학습 확인 (SC-HQ-R1)**
```
show ip route
ping 192.168.90.1
```

**결과**
- 본사 `show ip route`에 `R 192.168.90.0/24 [120/1] via 192.168.70.2, 00:00:03, Vlan70`이 올라왔다. 본사에는 이 경로를 입력한 적이 없다.
- 본사 `ping 192.168.90.1`: 4/5 성공(첫 패킷 `.`, 이후 `!!!!`), 평균 0 ms. 첫 패킷은 ARP 해석으로 유실된 것으로 추정한다.
- 해석: `network` 한 줄만 추가했는데 본사가 30초 이내에 자동 학습했다. 정적이었다면 본사에 `ip route 192.168.90.0 255.255.255.0 192.168.70.2`를 따로 넣어야 했다.

**4-5. 추가 증거: 본사 PC ping과 정적 경로 부재**
```
(본사 PC Command Prompt) ping 192.168.90.1
(SC-HQ-R1) show running-config | include ip route
(SC-HQ-R1) show ip route 192.168.90.0
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| 본사 PC `ping 192.168.90.1` | PC에서 창고까지 통신 확인 | 라우터가 아니라 사용자 PC에서 새 네트워크까지 통신되는 증거를 남긴다 |
| `show running-config \| include ip route` | 설정 안의 정적 경로만 표시 | 본사에 90 대역 정적 경로를 넣지 않았다는 증거 |
| `show ip route 192.168.90.0` | 이 대역 경로의 학습 방법과 출처 | `Known via "rip"`이면 RIP으로 배웠다는 직접 증거 |

**결과**
- 본사 PC ping: 4개 응답, `Sent = 4, Received = 4, Lost = 0 (0% loss)`, time<1ms, TTL=254. 첫 패킷도 유실되지 않았다(PC의 ARP가 이미 해결된 상태로 추정). 캡처: `5일차_8_창고추가후_본사PC_ping.png`
- `show running-config | include ip route`: `ip route 192.168.60.0 255.255.255.0 192.168.80.2 250` 한 줄뿐. 4일차 예비 경로만 있고 90 대역 정적 경로는 없다.
- `show ip route 192.168.90.0`: `Known via "rip", distance 120, metric 1`, `Last update from 192.168.70.2 on Vlan70, 00:00:24 ago`.
- 출발 PC 확인: `ipconfig`에서 IPv4 192.168.40.11, 마스크 255.255.255.0, 게이트웨이 192.168.40.1. ping은 경영지원 PC(VLAN 40)에서 나갔다. ping 캡처와 ipconfig 캡처(`5일차_9_본사PC_ipconfig.png`)는 별도 화면이다.
- 해석: 본사에 90 대역 정적 경로가 없고, 경로는 RIP으로 지사 라우터(192.168.70.2)에서 배웠으며, 본사 PC에서 그 네트워크까지 통신된다. 지사에 네트워크가 늘어도 `network` 한 줄이면 본사와 연결된다는 목표가 증명됐다.
- 한계: 본사의 추가 전 경로표는 없다. 대신 지사의 추가 전 경로표(5일차_7)와 정적 경로 부재 확인으로 "경로를 입력하지 않았다"를 보였다.

### 단계 5. 장애 실습, 예비 경로 /24 확인

**목적**: 주 회선을 끊었을 때 예비 회선으로 전환되는지, 유실 패킷 수와 복구 동작이 4일차 정적 방식과 어떻게 다른지 본다. 예비 경로는 이미 네트워크별 /24(255.255.255.0)다.

**방식**: 4일차와 같다. 지사 PC에서 `ping 192.168.50.1 -t`를 걸어 두고 본사 `GigabitEthernet0/1/3`을 shutdown, 이후 no shutdown으로 복구한다.

**5-1. 장애 전 상태 (양쪽 `show ip route`)**
- 화면이 길어 위쪽과 아래쪽을 나눠 캡처했다.
- 본사(`5일차_10`, `5일차_11`): `R 192.168.60.0/24 [120/1] via 192.168.70.2, Vlan70`, `R 192.168.90.0/24 [120/1] via 192.168.70.2, Vlan70`. 192.168.80.0/30은 Serial0/2/0 직접 연결(C). S 경로 없음(예비는 대기 중).
- 지사(`5일차_12`, `5일차_13`): 192.168.10, 20, 30, 40, 50이 `R [120/1] via 192.168.70.1, GigabitEthernet0/1`, 192.168.90.0/24는 Loopback0 직접 연결(C). S 경로 없음.

**5-2. 연속 ping 시작 (지사 PC)**
```
ping 192.168.50.1 -t
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `ping 192.168.50.1 -t` | 멈출 때까지 계속 ping | 전환 순간의 유실을 보려면 연속 ping이 필요하다. 4일차와 같은 목적지(본사 서버팜 게이트웨이)로 비교한다 |

**5-3. 주 회선 차단 (SC-HQ-R1)**
```
configure terminal
interface GigabitEthernet0/1/3
shutdown
exit
end
```

**5-4. 전환 확인**
```
(SC-HQ-R1) show ip interface brief
(SC-HQ-R1) show ip route
(SC-BR-R1) show ip route
```

**결과**
- ping 통계(`Ctrl+C`로 멈춤): `Sent = 140, Received = 140, Lost = 0 (0% loss)`, 최소 0ms, 최대 47ms, 평균 8ms. 장애를 걸었는데 유실이 0이었다. 캡처는 하지 못했다(통계 텍스트만 확인).
- 본사 `show ip interface brief`: Gi0/1/3 `administratively down down`, Vlan70 `up down`(포트가 내려가 VLAN 70의 라인 프로토콜이 down). 시리얼 Serial0/2/0은 up/up.
- 본사 `show ip route`: R 경로가 모두 사라지고 `S 192.168.60.0/24 [250/0] via 192.168.80.2`가 올라왔다. 192.168.70.0/24(C, L)도 사라졌다. **192.168.90.0/24 경로는 본사 표에 없다.**
- 지사 `show ip route`: R 경로가 사라지고 `S [250/0] via 192.168.80.1` 5줄(192.168.10 - 50)이 올라왔다. 192.168.90.0/24는 Loopback0 직접 연결로 남아 있다.
- 해석: 포트를 직접 내리면 양쪽 라우터가 회선 단절을 즉시 알아서 RIP 경로를 지우고 예비 정적 경로(AD 250)로 전환했다. 이 방식에서는 RIP의 느린 타이머(invalid 180초 등)가 드러나지 않는다. 유실 0은 전환이 ping 간격(1초)보다 빨랐다는 뜻으로 추정하며, 4일차(패킷 1개 유실)와 다른 이유는 확인하지 못했다.
- **발견: 예비 경로가 창고 네트워크를 덮지 못한다.** 본사의 예비 정적 경로는 192.168.60.0/24 한 줄뿐이다. 창고는 RIP으로만 학습했기 때문에 주 회선이 끊기면 본사는 창고로 가는 길을 잃는다. 5-5에서 확인했다.

**5-5. 장애 중 창고 도달성 확인 (경영지원 PC 192.168.40.11)**
```
ipconfig
ping 192.168.90.1
ping 192.168.60.1
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `ping 192.168.90.1` | 본사 PC에서 창고로 | 5-4에서 본 "90 대역 없음"이 실제 통신 실패로 이어지는지 확인한다 |
| `ping 192.168.60.1` | 본사 PC에서 지사 LAN 게이트웨이로 | 같은 장애에서 예비 경로가 있는 대역은 되는지 대조군으로 쓴다 |

**결과**
- `ipconfig`: IPv4 192.168.40.11, 게이트웨이 192.168.40.1.
- `ping 192.168.90.1`: 4개 모두 실패(Lost = 4, 100%). `Reply from 192.168.40.1: Destination host unreachable`로, 본사 라우터가 "갈 길이 없다"고 돌려보낸 것이다.
- `ping 192.168.60.1`: 4/4 성공, 1 - 17ms, TTL=254(시리얼을 거쳐 라우터를 한 번 지남).
- 해석: 같은 장애에서 지사 LAN(60)은 예비 정적 경로가 있어 통신되고, 창고(90)는 예비 경로가 없어 통신되지 않는다. 주 회선에서는 RIP이 새 네트워크를 자동으로 알려 주지만, 예비 회선은 정적 경로라서 새 네트워크마다 본사에 경로를 추가해야 한다.
- 시험 중 실수는 5장의 실수 3 참조.

**5-6. 창고용 예비 경로 추가 (SC-HQ-R1, 장애 상태에서)**
```
configure terminal
ip route 192.168.90.0 255.255.255.0 192.168.80.2 250
end
show ip route
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `ip route 192.168.90.0 255.255.255.0 192.168.80.2 250` | 창고 대역으로 가려면 지사 시리얼 주소로 보낸다. AD 250 | 주 회선이 끊기면 RIP이 알려 준 창고 경로도 사라져서 본사가 길을 잃는다. 정적 경로로 예비 길을 만든다. AD를 250으로 하는 이유는 4일차와 같다. RIP(120)이 살아 있을 때는 대기하고 RIP 경로가 사라질 때 올라온다 |

**결과**
- 본사 `show ip route`: `S 192.168.60.0/24 [250/0] via 192.168.80.2`와 `S 192.168.90.0/24 [250/0] via 192.168.80.2` 두 줄.
- 경영지원 PC `ping 192.168.90.1`: 4/4 성공, 1 - 25ms(평균 13ms), TTL=254. 5-5에서는 같은 ping이 4/4 실패였다.
- 지사 쪽은 창고가 직접 연결이고 본사로 가는 예비 경로가 이미 있어서 추가할 것이 없었다.
- **정리: RIP이 자동으로 해 주는 것은 주 회선뿐이다.** 새 네트워크를 지사에 만들면 주 회선은 지사의 `network` 한 줄로 끝나지만, 예비 회선은 본사에 정적 경로를 따로 넣어야 한다. 라우팅 비교의 핵심 항목이다.

**5-7. 복구 (SC-HQ-R1)**
```
configure terminal
interface GigabitEthernet0/1/3
no shutdown
exit
end
show ip interface brief
show ip route
(SC-BR-R1) show ip route
```

**결과**
- 본사 `show ip interface brief`: Gi0/1/3 `up up`, Vlan70 `up up`.
- 본사: `R 192.168.60.0/24 [120/1] via 192.168.70.2, 00:00:20, Vlan70`, `R 192.168.90.0/24 [120/1] via 192.168.70.2, 00:00:20, Vlan70`이 돌아왔고 S 250 두 줄은 표에서 사라졌다.
- 지사: 192.168.10 - 50이 `R [120/1] via 192.168.70.1, 00:00:16, GigabitEthernet0/1`로 돌아왔고 S 250 다섯 줄은 사라졌다.
- 해석: 복구하자 양쪽 모두 RIP 경로(AD 120)가 자동으로 돌아오고 AD 250 예비 경로는 설정에 남은 채 표에서 물러났다. 4일차에는 지사가 `[250]`으로 남아 있다가 `ping 192.168.70.1`로 ARP를 다시 학습시킨 뒤에야 돌아왔는데, 이번에는 수동 조작 없이 양쪽이 돌아왔다.
- 확인하지 못한 것: 복구에 걸린 정확한 시간(경과 16 - 20초라 그 안에 돌아온 것으로 보이나 `no shutdown` 시각을 재지 않았다), 복구 중 `ping -t` 유실 통계.

**5-8. 예비 경로가 설정에 남아 있는지 확인**
```
(SC-HQ-R1) show running-config | include ip route
(SC-BR-R1) show running-config | include ip route
```

**결과**: 본사 `ip route 192.168.60.0 ... 192.168.80.2 250`, `ip route 192.168.90.0 ... 192.168.80.2 250` 두 줄. 지사 192.168.10, 20, 30, 40, 50 대역 다섯 줄이 모두 `192.168.80.1 250`. 예비 경로는 설정에 남고 경로표에서만 물러나 있어서 다음 주 회선 장애 때 다시 올라온다.

**단계 5 정리**

| 비교 항목 | 4일차(정적) | 5일차(RIPv2) |
|-----------|-------------|--------------|
| 장애 때 유실 | 패킷 1개 | 0개(140개 중. 전환이 ping 간격보다 빨랐던 것으로 추정) |
| 복구 때 | 본사 즉시, 지사는 수동 `ping 192.168.70.1` 필요 | 양쪽 모두 수동 조작 없이 R 경로 복귀 |
| 새 네트워크(창고) | 양쪽에 경로 직접 입력 | 주 회선은 지사 `network` 한 줄, 예비 경로는 본사에 정적 경로 추가 필요 |

한계: 포트를 직접 내리는 방식이라 RIP의 느린 타이머가 드러나지 않았다. 복구 중 유실 수와 복구 시간은 측정하지 못했다.

### 단계 6. 사무실 쪽 passive, RIP 포트 인증

**목적**: PC가 있는 쪽 포트로 RIP 광고가 나가지 않게 막고(passive), RIP이 오가는 주 회선에 인증을 걸어 본다. passive는 적용했고 인증은 Packet Tracer가 지원하지 않아 검증하지 못했다.

**6-1. 본사 LAN 쪽 passive (SC-HQ-R1)**
```
configure terminal
router rip
passive-interface GigabitEthernet0/0/0
passive-interface GigabitEthernet0/0/1
passive-interface Vlan30
passive-interface Vlan40
passive-interface Vlan50
end
show ip protocols
show ip route
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `passive-interface <포트>` | 이 포트로는 RIP 광고를 보내지 않는다 | PC가 있는 포트로 내부 대역 목록이 나가는 것과 그 포트에서 이웃 관계가 맺어지는 것을 막는다. 광고를 막아도 `network`로 선언한 대역 자체는 다른 라우터에 계속 알려진다. 주의: 고전적인 RIP에서 passive는 송신만 막고 수신은 막지 않아서, PC가 보낸 가짜 RIP 패킷을 거부하지는 못한다 |

**6-2. 지사 LAN 쪽 passive (SC-BR-R1)**
```
configure terminal
router rip
passive-interface GigabitEthernet0/0
passive-interface Loopback0
end
show ip protocols
show ip route
copy running-config startup-config
```

**결과**
- 본사 `show ip protocols`: `Interface Send Recv`에는 Vlan70(Send 2, Recv 2) 하나뿐. `Passive Interface(s)`에 Gi0/0/0, Gi0/0/1, Serial0/2/0, Vlan30, Vlan40, Vlan50. `Routing for Networks`는 10, 20, 30, 40, 50, 70, 80 대역. 단계 3에서 확인하지 못했던 시리얼 passive가 이번에 표시됐다. 타이머는 30초 갱신, invalid 180초, hold down 180초, flushed 240초이며 `Key-chain` 열은 비어 있다.
- 지사 `show ip protocols`: Interface에는 Gi0/1 하나뿐. `Passive Interface(s)`에 Gi0/0, Serial0/3/0, Loopback0. `Routing for Networks`는 60, 70, 80, 90 대역. `Key-chain` 열은 비어 있다.
- 양쪽 `Routing Information Sources`는 상대 라우터 한 대뿐(본사 192.168.70.2, 지사 192.168.70.1).
- `show ip route`는 passive 전과 같다. 본사는 `R 192.168.60.0`과 `R 192.168.90.0`, 지사는 `R 192.168.10` - `50`이 주 회선으로 유지된다. passive는 경로를 지우지 않고 광고만 막는다.
- 양쪽 모두 `copy running-config startup-config`로 저장했다.

**6-3. 인증용 key chain 지원 확인 (SC-BR-R1)**
```
configure terminal
key chain RIPKEY
key 1
key-string <실습용 키>
exit
exit
end
show running-config | section key
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `key chain RIPKEY` | 인증 키 묶음(이름 RIPKEY) 생성 | RIP 인증은 키 묶음을 인터페이스에 연결하는 방식이다. 묶음만 만들면 라우팅에 영향이 없어 지원 여부를 안전하게 시험할 수 있다 |
| `key 1` | 키 번호 1 | 묶음 안에서 키를 구분하고, 교체할 때 번호로 순서를 관리한다 |
| `key-string <문자열>` | 실제 비밀 문자열 | 양쪽이 같은 문자열을 가져야 서로의 광고를 받아들인다. 대소문자를 구분한다 |

**결과**: `key chain`, `key 1`, `key-string`이 에러 없이 입력되고 `show running-config | section key`에 보인다. 키 문자열 값은 문서에 적지 않는다. 아직 인터페이스에 적용하지 않아서 라우팅에는 영향이 없다.

**6-4. 인터페이스에 RIP 인증 적용 시도 (SC-BR-R1)**
```
configure terminal
interface GigabitEthernet0/1
ip rip authentication mode text
```

**결과 (실패)**
- `^`가 `authentication` 위치를 가리키며 `% Invalid input detected at '^' marker.`
- 같은 인터페이스에서 `ip rip ?`를 입력하자 `% Unrecognized command`. `ip rip` 아래의 명령이 하나도 없다는 뜻이다.
- 본사 SC-HQ-R1(ISR4331)의 `interface Vlan70`에서도 `ip rip ?`가 `% Unrecognized command`. 지사와 본사 모두 RIP 인증을 지원하지 않는 것으로 확정한다.
- 영향: 명령이 거부되어 라우팅 설정은 바뀌지 않았다. 만든 key chain RIPKEY는 영향 없이 남아 있다.
- 한계: Packet Tracer에서는 RIP 인증(평문, MD5)을 검증하지 못했다. 실제 장비용 설정(검증하지 못함):

```
key chain RIPKEY
 key 1
  key-string <키>
interface <RIP이 켜진 포트>
 ip rip authentication mode md5
 ip rip authentication key-chain RIPKEY
```

**6-5. 대체 통제 지원 확인 (SC-BR-R1)**
```
configure terminal
router rip
distribute-list ?
neighbor ?
end
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `distribute-list` | 주고받는 경로를 ACL로 거른다 | 인증이 안 되어 대신 받아들일 경로를 제한하려고 시험했다 |
| `neighbor` | RIP 광고를 지정한 이웃에게만 직접(유니캐스트) 보낸다 | 광고 범위를 좁히려고 시험했다 |

**결과 (둘 다 실패)**: 두 명령 모두 `% Unrecognized command`. 이 Packet Tracer의 RIP에서는 인증, 경로 필터, 유니캐스트 이웃 지정이 모두 지원되지 않아, 쓸 수 있는 RIP 보안 통제는 passive-interface뿐이다.

**단계 6 정리**

| 구분 | 내용 |
|------|------|
| 적용한 것 | LAN 쪽 passive(본사 5개, 지사 2개 포트)와 시리얼 passive. `show ip protocols`로 확인 |
| 검증하지 못한 것 | RIP 인증(평문, MD5), 경로 필터, 유니캐스트 이웃. 명령이 인식되지 않아 증거 화면으로 남김 |
| 알아 둘 점 | passive는 광고 송신만 막는다. LAN의 PC가 보내는 가짜 RIP 패킷은 LAN 쪽 포트 ACL(UDP 520 차단)로 막아야 하고, ACL 단계에서 시험한다 |
| 개념 | RIP 인증은 key chain을 만들고 인터페이스에서 인증 방식(평문 또는 MD5)과 key chain을 연결한다. 평문은 키가 그대로 실려 도청에 약하고, MD5는 해시만 실려 키가 노출되지 않는다. 양쪽 키가 다르면 광고를 서로 받지 않는다 |

| 1 | 지사용 명령을 본사 라우터에 입력 | `no ip route 192.168.10.0 ... 192.168.70.1`에 `%No matching route to delete` | 192.168.10.0 경로는 지사에만 있고 본사에는 192.168.60.0 하나뿐이라 지울 대상이 없었다. 프롬프트를 보지 않았다 | 명령 입력 전에 프롬프트(`SC-HQ-R1`, `SC-BR-R1`)를 본다. 설정은 망가지지 않고 에러만 났다 |

| 3 | 시험 출발 PC를 잘못 선택 | 본사 PC에서 한다고 생각했는데 ping이 모두 성공했다 | 실제로는 지사 PC(192.168.60.11)에서 입력했다. 두 대상 주소가 모두 지사 라우터 주소였고 TTL=255(라우터를 거치지 않음)로 나와서 알아챘다. `ipconfig`로 확인 | 시험 전에 `ipconfig`로 출발 PC를 확인한다 |

## 6. 한계와 더 깊게 갈 방향

- RIP은 홉 수만 보고, 수렴이 느리고(타이머 180초대), 15홉 제한이 있다. OSPF로 바꿔 비교할 수 있다(6일차).
- 장애 전환 시간은 포트를 직접 내리는 방식이라 RIP 타이머가 드러나지 않았다. 회선은 살아 있는 채 중간 장비만 고장 나는 장애, 복구 시간, 복구 중 유실 수는 측정하지 못했다.
- RIP 인증(평문, MD5), 틀린 키 시험, 경로 수신 제한(distribute-list)은 Packet Tracer 미지원으로 시험하지 못했다. LAN 쪽 ACL(UDP 520 차단)은 ACL 단계에서 시험한다.
- 정적과 RIPv2의 항목별 비교는 [라우팅 비교](../03_설계도/라우팅_비교.md)에 정리했다.

## 7. 보안 3요소와의 연결

- **무결성**: passive-interface는 LAN 쪽으로 내부 경로 정보가 새는 것과 LAN 쪽 이웃 관계 형성을 막는다. 가짜 라우터와 PC가 보낸 RIP 패킷을 거부하는 통제는 RIP 인증, 경로 필터, LAN 쪽 ACL(UDP 520 차단)인데, 앞의 둘은 이 Packet Tracer에서 검증하지 못했다. LAN 쪽 ACL은 ACL 단계에서 시험한다.
- **가용성**: 동적 라우팅과 예비 정적 경로로 주 회선 장애에도 본사와 지사 통신이 유지되게 한다.

### 8-1. 개념

| 질문 | 답 요지 |
|------|---------|
| 정적과 동적 라우팅의 차이와 선택 기준은? | 정적은 관리자가 경로를 입력하고 동적은 라우터끼리 교환한다. 변화가 잦고 네트워크가 늘어나는 구간은 동적, 고정된 구간과 예비 경로는 정적이 단순하다. 우리는 주 회선에 RIPv2, 예비 회선에 정적을 썼다 |
| 거리 벡터와 링크 상태의 차이는? | 거리 벡터(RIP)는 이웃이 알려준 경로와 거리를 믿고 전달한다. 링크 상태(OSPF)는 전체 지도를 모아 각 라우터가 직접 최단 경로를 계산한다. 그래서 링크 상태가 수렴이 빠르고 대규모에 맞다고 알려져 있다(OSPF는 링크 상태 데이터베이스와 최단 경로 계산, area를 사용한다 [6]). 수렴 속도 비교는 6일차에 직접 측정한다 |
| IGP와 EGP의 차이는? | IGP는 한 조직 내부(RIP, OSPF, EIGRP), EGP는 조직 사이(BGP) 라우팅이다 |
| RIP의 특성을 설명하라 | 홉 수가 metric이고 최대 15(16은 도달 불가), 30초마다 광고(UDP 520), invalid 180초, flush 240초라 수렴이 느리다 [1][2]. 기본 AD는 120이다 [3] |
| RIPv1과 v2의 차이는? | v2는 서브넷 마스크를 전달(클래스리스, VLSM)하고, 멀티캐스트 224.0.0.9로 광고하며, 인증을 지원한다. v1은 클래스풀에 브로드캐스트다 [2][8] |
| AD(관리 거리)란? | 같은 목적지에 대해 출처가 다른 경로가 여럿일 때 어느 출처를 믿을지 정하는 값으로 작을수록 우선한다. 직접 연결 0, 정적 1, OSPF 110, RIP 120. 우리 예비 경로는 일부러 250으로 높였다 [3] |
| auto-summary를 왜 끄나? | 클래스 경계를 넘을 때 자동 요약하면 192.168.80.0/30 같은 작은 대역이 섞인 구성에서 경로가 틀어질 수 있다 |
| passive-interface는 무엇이고 한계는? | 해당 인터페이스로 RIP 광고를 보내지 않게 한다. 사무실 쪽으로 내부 대역 정보가 새는 것과 이웃 관계 형성을 막는다. 고전적인 RIP에서는 송신만 막고 수신은 막지 않아 PC가 보낸 가짜 RIP 패킷을 거부하지는 못한다 [5] |

### 8-2. 설계 판단

| 질문 | 답 요지 |
|------|---------|
| 주 회선 정적 경로는 왜 지웠나? | 남아 있으면 AD 1이 RIP(120)보다 우선해서 RIP 경로가 테이블에 올라오지 못한다 |
| 예비 경로는 왜 남겼나? | AD 250이라 RIP이 정상일 때는 대기하고, RIP 경로가 사라지는 장애에서 마지막 수단으로 올라온다(floating static). 복구하면 다시 물러나는 것도 확인했다 |
| 시리얼에 passive를 건 이유는? | RIP을 켜면 이더넷과 시리얼이 모두 홉 1로 같은 metric이라 경로가 두 줄로 올라와 트래픽이 느린 시리얼로도 나뉜다. RIP은 대역폭 차이를 구분하지 못한다. 시리얼을 passive로 막아 RIP 경로는 주 회선만 남겼다 |
| 왜 RIPv2를 선택했나? | 서브넷 마스크를 전달해 /24와 /30이 섞인 구성에 맞고, 멀티캐스트 광고와 인증을 지원한다. 수업 진도에 맞춘 선택이기도 하다 |
| 창고 네트워크를 왜 루프백으로 만들었나? | 케이블과 장비 없이 "지사에 새 네트워크가 생긴 상황"을 만들 수 있고, 항상 up이라 안정적이며, 본사 PC에서 ping으로 증거를 남길 수 있다. 실제 LAN(HWIC-4ESW)은 시도했지만 VLAN 생성 방식 제약으로 루프백으로 바꿨다 |

### 8-3. 트러블슈팅과 검증

| 질문 | 답 요지 |
|------|---------|
| 지사에 네트워크가 늘어도 자동 연결된다는 것을 어떻게 증명했나? | 지사에 `network` 한 줄만 추가하고, 본사 설정에 정적 경로가 없고(`show running-config`), 경로가 `Known via "rip"`이며(`show ip route 192.168.90.0`), 본사 PC에서 ping이 성공함을 함께 보였다. 세 증거를 겹쳐서 "입력하지 않았다 - RIP으로 배웠다 - 통신된다"를 증명했다 |
| `network 192.168.0.0`이 안 먹은 이유와 발견 방법은? | `network`가 클래스 기준이라 C 클래스는 대역마다 선언해야 한다. `show ip protocols`에서 인터페이스 목록과 이웃 출처가 비어 있고 경로표에 R이 없는 것으로 찾았다 |
| ping이 되는데 왜 RIP이 안 된다고 판단했나? | 통신은 예비 정적 경로가 처리하고 있었다. ping 성공은 경로가 어디서 왔는지 알려 주지 않으므로 라우팅 테이블의 경로 출처(R/S)를 본다 |
| 장애 중 창고가 끊긴 원인과 해결은? | 창고는 RIP으로만 학습했고 예비 정적 경로는 60 대역 한 줄뿐이라, 주 회선이 끊기면 본사가 창고 경로를 잃었다. 본사 PC에서 `Destination host unreachable`로 재현하고(대조군으로 60 대역은 성공), 창고용 예비 경로를 추가해 해결했다. 교훈은 새 네트워크를 만들 때 예비 경로를 함께 챙기는 절차가 필요하다는 것이다 |
| 시험 결과가 이상할 때 어떻게 확인하나? | 출발지부터 의심한다. 모두 성공한 ping의 TTL이 255로 나와 라우터를 거치지 않았음을 알았고, `ipconfig`로 출발 PC가 틀렸음을 확인했다 |
| 장애 전환 속도는 정적과 RIP 중 어느 쪽이 빠른가? | 포트를 내리는 시험에서는 둘 다 즉시 전환됐다(정적 1개 유실, RIP 0개 유실이고 차이의 이유는 확인 못 함). 회선은 살아 있고 통신만 끊기는 경우는 시험하지 못했다. 이론상 정적은 스스로 감지하지 못해 IP SLA와 track이 필요하고 [9], RIP은 갱신이 180초 오지 않을 때 무효 처리한다 [1] |

### 8-4. 보안

| 질문 | 답 요지 |
|------|---------|
| 동적 라우팅의 보안 위험은? | 광고를 받기 때문에 가짜 라우터나 PC가 RIP 패킷을 보내 잘못된 경로를 주입하거나 트래픽을 우회시킬 수 있다. 정적은 광고가 없어 이 공격면이 없는 대신 입력 실수와 변경 누락이 약점이다 |
| RIP 보안 통제에는 무엇이 있나? | passive-interface(송신 차단), 인증(평문, MD5), 경로 필터(distribute-list), 유니캐스트 이웃(neighbor), LAN 쪽 ACL(UDP 520 차단) |
| 평문 인증과 MD5의 차이는? | 평문은 키가 패킷에 그대로 실려 도청에 약하다. MD5는 키 대신 해시값만 실려서 키가 노출되지 않는다. 양쪽 키가 다르면 광고를 서로 받지 않아 한쪽만 걸면 이웃이 끊긴다 [4] |
| 인증을 적용하지 못했는데 어떻게 처리했나? | `ip rip ?`가 `Unrecognized command`인 것으로 미지원임을 확인해 증거를 남기고, 실제 장비용 설정은 "검증하지 못함"으로 표시해 문서화했다. 적용한 것(passive)과 하지 못한 것을 구분해 기록했다 |
| passive만으로 충분한가? | 아니다. 송신만 막으므로 PC가 보낸 가짜 RIP 패킷은 막지 못한다. LAN 쪽 포트 ACL로 UDP 520을 차단하는 것이 필요하고 ACL 단계에서 시험할 계획이다 |

### 8-5. 확장과 한계

| 질문 | 답 요지 |
|------|---------|
| RIP의 한계와 OSPF로 가는 이유는? | RIP은 홉 수만 보고(회선 속도를 모름), 최대 15홉, 타이머 때문에 수렴이 느리다. OSPF는 링크 비용(cost)으로 경로를 고른다. cost는 기준 대역폭(기본 100Mbps)을 인터페이스 대역폭으로 나눈 값이라 회선 속도를 반영한다 [7]. 링크 상태 방식이고 area로 계층화하며 인증을 지원한다 [6]. 6일차에 같은 토폴로지에서 직접 비교한다 |
| 이 구성의 한계는? | 포트를 직접 내리는 장애만 시험했고, 복구 시간과 복구 중 유실은 측정하지 못했으며, RIP 인증은 환경 제약으로 검증하지 못했다. 예비 경로가 정적이라 새 네트워크마다 수동 추가가 필요하다 |
| 지사가 여러 곳으로 늘면? | 주 회선은 지사별 `network` 선언으로 자동 확장되지만, 예비 회선은 지사 수와 네트워크 수만큼 정적 경로가 늘어 관리 부담이 커진다. 이때는 예비 회선에도 동적 라우팅(OSPF)을 쓰는 것이 낫다 |
