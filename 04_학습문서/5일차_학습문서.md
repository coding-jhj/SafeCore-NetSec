# 5일차 학습 문서: 정적 라우팅에서 RIPv2 동적 라우팅으로

- 날짜: 2026-11-21
- 상태: 완료(단계 0부터 6)
- 계획과 결과 요약은 `02_작업 계획/5일차_작업계획서.md`, 정적과 RIPv2 비교는 `04_학습문서/라우팅_비교.md`에 있다.

## 1. 왜 하는가

- 지금까지 본사와 지사 라우터에는 경로를 사람이 직접 적어 두었다(정적 라우팅). 지사에 네트워크가 하나 늘면 본사와 지사 양쪽에 경로를 손으로 추가해야 하고, 빠뜨리면 그 네트워크는 본사와 통신이 안 된다.
- RIP은 라우터끼리 자기가 아는 네트워크를 서로 알려주는 동적 라우팅 프로토콜이다. 지사 라우터에 새 네트워크 선언만 추가하면 본사가 알아서 학습한다.
- 4일차에 만든 예비 회선(시리얼, AD 250 정적 경로)은 그대로 두고, 주 회선 구간만 정적에서 RIP으로 바꾼다.
- 사무실(PC) 쪽 포트로는 RIP 광고가 나가지 않게 막는다(passive). RIP 인증으로 가짜 라우터를 막는 것은 개념으로 정리하고 실습을 시도했으나, Packet Tracer가 지원하지 않아 검증하지 못했다(단계 6).

## 2. 핵심 개념

### 정적 라우팅과 동적 라우팅

| 구분 | 정적 | 동적 |
|------|------|------|
| 경로 입력 | 관리자가 직접 | 라우터끼리 교환 |
| 네트워크 추가 | 양쪽에 수동 추가 | 선언만 추가하면 상대가 학습 |
| 장애 대응 | 인터페이스가 down일 때만 경로가 사라짐 | 광고가 끊기면 경로가 사라짐 |
| 부하 | 거의 없음 | 주기적 광고 필요 |

### 라우팅 프로토콜의 분류
- 같은 조직 내부에서 쓰는 IGP(RIP, OSPF, EIGRP)와 조직 사이에서 쓰는 EGP(BGP)로 나눈다.
- 계산 방식으로는 거리 벡터(RIP: 이웃이 알려준 경로와 거리를 믿음)와 링크 상태(OSPF: 전체 지도를 만들어 직접 계산)로 나눈다.

### RIP의 특성
- 홉 수만 보고 대역폭이나 지연은 고려하지 않는다. 15홉 제한이 있어 큰 네트워크에 맞지 않는다.
- 거리 벡터 방식의 IGP다. metric은 홉 수이고 최대 15홉이며 16은 도달 불가다.
- 30초마다 라우팅 테이블을 이웃에게 광고한다(UDP 520).
- 기본 타이머는 update 30초, invalid 180초, holddown 180초, flush 240초다. 그래서 수렴이 느리다.
- 기본 AD는 120이다. 정적 경로(AD 1)보다는 못 믿고 우리 예비 경로(AD 250)보다는 더 믿는다.

### RIPv1과 RIPv2

| 구분 | v1 | v2 |
|------|-----|-----|
| 서브넷 마스크 전달 | 안 함(클래스풀) | 함(클래스리스, VLSM 가능) |
| 광고 방식 | 브로드캐스트 | 멀티캐스트 224.0.0.9 |
| 인증 | 없음 | 지원 |

### auto-summary
다른 클래스 경계를 넘을 때 자동으로 클래스 단위로 요약하는 기능이다. 우리처럼 192.168.80.0/30 같은 작은 대역이 섞인 구성에서는 경로가 틀어질 수 있어 끈다.

### network 명령은 클래스 기준이다
- RIP의 `network` 명령은 "어느 인터페이스에서 RIP을 켤지"를 정한다. 이때 주소는 클래스 기준으로 해석된다.
- 192.168.x.0은 C클래스라서 대역마다 따로 선언해야 한다. `network 192.168.0.0` 하나로는 192.168.0.x 대역만 해당하고, 우리 대역에는 RIP이 켜지지 않는다(아래 단계 2의 실수 참고).

### passive-interface
- 해당 인터페이스로 RIP 광고를 내보내지 않게 하는 설정이다. 고전적인 RIP에서는 송신만 막고 수신은 막지 않는다(Packet Tracer에서 수신 동작은 시험하지 않았다).
- 사무실 PC 쪽으로 우리 내부 대역 정보를 보낼 이유가 없고, 그 포트에서 이웃 라우터 관계가 만들어지는 것도 막으려는 것이다. PC가 보내는 가짜 광고를 거부하는 효과는 없다.
- 예비 시리얼 회선에 쓰는 것은 예비 회선을 4일차의 정적 floating route로만 쓰려는 우리의 설계 의도다.

### RIPv2 인증
- 이웃이 맞는 키를 가졌을 때만 광고를 받아들이게 한다. 평문 인증은 패킷에 비밀번호가 그대로 보이고, MD5 인증은 해시로 보내서 직접 보이지 않는다.
- 한쪽에만 걸면 이웃 관계가 끊기므로 양쪽에 같이 걸어야 한다.
- 이 Packet Tracer는 인터페이스에 RIP 인증을 적용하는 명령을 지원하지 않는다(단계 6-4).

## 3. 단계별 실습

### 단계 0. 작업 전 상태 확인

**목적**: 바꾸기 전 상태를 기록하고, 예비 경로가 실제로 설정에 있는지 확인한다. 예비 경로가 없는 채로 주 경로를 지우면 연결이 끊긴다.

**SC-HQ-R1**
```
show ip route static
show running-config | include ip route
show ip route
```

**SC-BR-R1**
```
show ip route static
show running-config | include ip route
show ip route
ping 192.168.10.1
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `show ip route static` | 라우팅 테이블 중 정적 경로만 표시 | 지금 실제로 쓰이는 정적 경로를 확인한다. AD 250 예비 경로는 대기 중이라 여기에 안 보이는 게 정상이다 |
| `show running-config \| include ip route` | 설정 파일에서 `ip route`가 들어간 줄만 표시 | 라우팅 테이블이 아니라 설정에 들어 있는 경로 전체를 본다. 대기 중인 예비 경로(AD 250)까지 확인할 수 있다 |
| `show ip route` | 라우팅 테이블 전체 | 연결된 대역(C), 자기 주소(L), 정적(S)을 한눈에 본다 |
| `ping 192.168.10.1` | 지사에서 본사 연구개발 게이트웨이로 ICMP | 변경 전 통신이 되는지 기준을 잡는다 |

**결과**
- 본사에 `192.168.60.0/24 via 192.168.70.2`(AD 1)와 `via 192.168.80.2 250`(예비), 지사에 192.168.10, 20, 30, 40, 50 대역 각각 `via 192.168.70.1`(AD 1)과 `via 192.168.80.1 250`(예비)이 설정에 있었다. 예비 경로는 전부 마스크가 255.255.255.0이다.
- 지사 ping은 80 percent(4/5)였고 첫 패킷만 유실되었다. 첫 패킷 유실은 ARP 학습 과정으로 추정한다. 이후 4개는 성공했다.
- 캡처: `99_첨부파일/5일차_1_정적라우팅_본사_변경전.png`, `5일차_2_정적라우팅_지사_변경전.png`

### 단계 1. 주 회선 정적 경로 삭제 (예비는 유지)

**목적**: RIP이 경로를 대신 학습하도록 주 회선(192.168.70.x)을 next-hop으로 하는 정적 경로(AD 1)를 지운다. 정적 경로가 남아 있으면 AD 1이 RIP의 AD 120보다 우선해서 RIP 경로가 라우팅 테이블에 올라오지 못한다.

**SC-HQ-R1**
```
configure terminal
no ip route 192.168.60.0 255.255.255.0 192.168.70.2
exit
```

**SC-BR-R1**
```
configure terminal
no ip route 192.168.10.0 255.255.255.0 192.168.70.1
no ip route 192.168.20.0 255.255.255.0 192.168.70.1
no ip route 192.168.30.0 255.255.255.0 192.168.70.1
no ip route 192.168.40.0 255.255.255.0 192.168.70.1
no ip route 192.168.50.0 255.255.255.0 192.168.70.1
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `configure terminal` | 전역 설정 모드 진입 | 설정을 바꾸려면 이 모드가 필요하다 |
| `no ip route 대역 마스크 192.168.70.x` | 해당 정적 경로 삭제 | next-hop(192.168.70.x)까지 정확히 적어야 그 경로(AD 1)만 지워지고 같은 대역의 예비 경로(192.168.80.x, AD 250)는 남는다 |
| `exit` | 설정 모드 종료 | 이후 `show` 명령을 쓰기 위해서다 |

**확인**

**SC-HQ-R1**
```
show ip route static
show running-config | include ip route
```

**SC-BR-R1**
```
show ip route static
show running-config | include ip route
ping 192.168.10.1
```

**결과**
- 양쪽 라우팅 테이블에 `S ... [250/0]` 예비 경로가 올라왔다(본사 1줄, 지사 5줄). 주 경로가 사라지자 대기하던 AD 250 경로가 선택된 것이다.
- 지사 ping은 5/5 성공이었고 왕복 시간이 2/20/39 ms(최소/평균/최대)였다. 단계 0의 0 ms와 비교하면 트래픽이 느린 시리얼 선으로 옮겨 간 것을 알 수 있다.

### 단계 2. 두 라우터에 RIPv2 설정

**목적**: 라우터끼리 경로를 자동으로 주고받게 한다. 대역마다 `network`를 선언해서 해당 인터페이스에서 RIP이 켜지게 한다.

**SC-HQ-R1**
```
configure terminal
router rip
version 2
no auto-summary
no network 192.168.0.0
network 192.168.10.0
network 192.168.20.0
network 192.168.30.0
network 192.168.40.0
network 192.168.50.0
network 192.168.70.0
network 192.168.80.0
exit
exit
```

**SC-BR-R1**
```
configure terminal
router rip
version 2
no auto-summary
no network 192.168.0.0
network 192.168.60.0
network 192.168.70.0
network 192.168.80.0
exit
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `router rip` | RIP 설정 모드 진입 | RIP 프로세스를 켜고 설정한다 |
| `version 2` | RIP을 버전 2로 | v2는 서브넷 마스크를 전달해서 /24와 /30이 섞인 우리 구성에 맞고, 인증도 쓸 수 있다 |
| `no auto-summary` | 클래스 경계 자동 요약 끄기 | 켜져 있으면 192.168.80.0/30 같은 작은 대역이 요약되어 경로가 틀어질 수 있다 |
| `no network 192.168.0.0` | 잘못 넣은 선언 제거 | 처음에 넣은 `network 192.168.0.0`은 효과가 없으므로 정리한다 |
| `network 192.168.X.0` | 해당 대역에 속한 인터페이스에서 RIP 활성화 | C클래스라 대역마다 따로 선언해야 한다. 이 선언이 있어야 그 인터페이스로 광고를 보내고 받는다 |

- 이 단계에서는 부서 LAN, 주 회선, 예비 시리얼 대역을 전부 선언했다. 아직 passive를 걸지 않아서 RIP이 예비 시리얼로도 나간다. 그 동작을 먼저 관찰하고 단계 3에서 막는다.

**확인**

**SC-HQ-R1**
```
show ip protocols
show ip route
```

**SC-BR-R1**
```
show ip protocols
show ip route
ping 192.168.10.1
```

| 명령어 | 읽는 법 |
|--------|---------|
| `show ip protocols` | `Routing for Networks`에 선언한 대역이 나열되는지, Interface 목록에 Send/Recv가 표시되는지, `Routing Information Sources`에 이웃 라우터 주소가 나타나는지 본다 |
| `show ip route` | 앞에 `R`이 붙고 `[120/1]`로 표시되는 줄이 RIP으로 학습한 경로다. 예비 정적 `[250/0]`가 `R`로 대체된다 |

**결과 (정정 후)**
- 양쪽 `show ip protocols`: `Routing for Networks`에 선언한 대역이 모두 나열되고, Interface 목록에 RIP이 켜진 인터페이스가 전부 표시되었다(Send 2, Recv 2는 version 2로 송수신한다는 뜻, 본사 7개와 지사 3개). Key-chain 열은 아직 비어 있다(인증은 단계 6에서 설정). `Routing Information Sources`에 이웃 라우터 주소가 나타났다(본사 쪽 192.168.70.2, 192.168.80.2 / 지사 쪽 192.168.70.1, 192.168.80.1, 둘 다 distance 120).
- 본사 `show ip route`: `R 192.168.60.0/24 [120/1] via 192.168.70.2, Vlan70`과 `[120/1] via 192.168.80.2, Serial0/2/0`, 즉 같은 경로가 두 줄로 올라왔다.
- 지사 `show ip route`: 192.168.10, 20, 30, 40, 50 대역이 각각 `[120/1] via 192.168.70.1, GigabitEthernet0/1`과 `[120/1] via 192.168.80.1, Serial0/3/0` 두 줄씩 올라왔다.
- 4일차의 `S [250/0]` 예비 정적 경로는 라우팅 테이블에서 사라졌다. 설정에서 지워진 것이 아니라 RIP(AD 120)이 정적 예비(AD 250)보다 우선해서 대기 상태로 들어간 것이다.
- 지사 `ping 192.168.10.1`: 5/5 성공, 0/5/26 ms(최소/평균/최대). 이더넷과 시리얼 경로를 섞어 쓴 결과로 추정한다(확인 필요).
- 캡처: `99_첨부파일/5일차_3_RIP적용후_본사_경로2줄.png`(본사 `R 192.168.60.0/24`가 Vlan70과 Serial0/2/0 두 경로), `5일차_4_RIP적용후_지사_경로2줄.png`(지사 192.168.10, 20, 30, 40, 50 대역이 GigabitEthernet0/1과 Serial0/3/0 두 경로)

**읽을 점: 왜 경로가 두 줄인가**
- RIP의 metric은 홉 수뿐이다. 이더넷 주 회선과 시리얼 예비 회선 모두 한 홉이라 metric이 1로 똑같고, RIP은 대역폭이 다른 것을 구분하지 못한다.
- metric이 같으면 라우터는 동등 비용 경로를 모두 올린다(`Maximum path: 4`, 최대 4개까지). 그래서 트래픽이 빠른 이더넷과 느린 시리얼로 나뉘어 갈 수 있다.
- 우리 설계 의도는 시리얼을 예비로만 쓰는 것이므로 이 상태는 의도와 다르다. 이것이 단계 3에서 시리얼을 passive로 막는 이유다.

### 단계 3. 예비 회선(시리얼) passive

**목적**: RIP 광고가 예비 시리얼로 나가지 않게 막아서, RIP 경로는 주 회선 하나로만 학습되게 한다. 예비 회선은 4일차의 정적 floating route(AD 250)로만 쓴다.

**SC-HQ-R1**
```
configure terminal
router rip
passive-interface Serial0/2/0
exit
exit
```

**SC-BR-R1**
```
configure terminal
router rip
passive-interface Serial0/3/0
exit
exit
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `router rip` | RIP 설정 모드 진입 | passive 설정은 RIP 설정 모드 안에서 한다 |
| `passive-interface Serial0/2/0` | 해당 인터페이스로 RIP 광고를 보내지 않음 | 시리얼로 RIP 경로가 오가면 이더넷과 같은 metric이라 트래픽이 나뉜다. 광고를 막으면 RIP은 이더넷으로만 학습한다 |

**확인**

**SC-HQ-R1**
```
show ip protocols
show ip route
```

**SC-BR-R1**
```
show ip protocols
show ip route
ping 192.168.10.1
```

| 확인 | 읽는 법 |
|------|---------|
| `show ip protocols` | `Passive Interface(s)`에 Serial 인터페이스가 나타난다 |
| `show ip route` | 이미 시리얼로 학습한 경로는 이웃이 더 이상 광고하지 않아서 바로 사라지지 않고 타이머(invalid 180초)가 지나야 사라진다. 시간이 지나면 `R` 경로가 주 회선 한 줄만 남는다 |

**결과 (입력 직후)**
- 양쪽 `show ip protocols`: `Passive Interface(s)`에 해당 시리얼(본사 Serial0/2/0, 지사 Serial0/3/0)이 표시되었고, Interface Send/Recv 목록에서 시리얼이 빠졌다. `Routing for Networks`에는 192.168.80.0이 그대로 남아 있다. 즉 대역 선언은 유지한 채 광고 송신만 막은 것이다.
- `show ip route`: 입력 직후에는 시리얼 경로가 아직 남아 있었다. 지사 쪽을 보면 주 회선 경로(192.168.70.1)는 00:00:22로 계속 갱신되는 반면 시리얼 경로(192.168.80.1)는 00:01:48로 시간이 계속 늘어나고 있다. 본사가 더 이상 시리얼로 광고하지 않아서 갱신이 끊기고 노화가 시작된 것이다. `show ip protocols`의 Routing Information Sources에서도 192.168.80.1의 Last Update가 00:01:45로 길어졌다.
- 본사 쪽 192.168.80.2는 Last Update가 00:00:21로 아직 짧았다. 지사에 passive를 본사보다 늦게 입력해서 노화 시작이 늦은 것으로 추정한다(확인 필요).
- 지사 `ping 192.168.10.1`: 5/5 성공, 0/3/14 ms.
- 시리얼 경로는 invalid 타이머(180초)가 지나면 무효가 되어 사라질 것으로 예상했고, 재확인 결과는 아래와 같다.

**결과 (타이머 경과 후)**
- 본사 `show ip route`: `R 192.168.60.0/24 [120/1] via 192.168.70.2, 00:00:08, Vlan70` 한 줄만 남았다. 시리얼(Serial0/2/0) 경유 경로는 사라졌다.
- 지사 `show ip route`: 192.168.10, 20, 30, 40, 50 대역이 모두 `[120/1] via 192.168.70.1, GigabitEthernet0/1` 한 줄씩만 남았다. 시리얼(Serial0/3/0) 경유 경로는 사라졌다.
- 양쪽 모두 Last Update가 00:00:08, 00:00:02로 짧아서 주 회선으로는 광고를 계속 주고받는 중이다.
- 192.168.80.0/30은 `C`(직접 연결)로 그대로 남아 있다. 시리얼 선 자체는 up이고, RIP 광고만 막은 것이다.
- 해석: passive 설정 후 시리얼로는 RIP 광고가 오가지 않아서, 이미 학습했던 시리얼 경로가 갱신이 끊긴 채 타이머를 넘겨 사라졌다. RIP 경로는 주 회선 하나로만 남고, 예비 회선은 4일차의 AD 250 정적 경로로만 쓰이는 상태가 됐다. 이 정적 경로는 설정에 남아 있고, RIP 경로가 사라질 때 올라온다(단계 5의 장애 실습에서 확인한다).
- 캡처: `99_첨부파일/5일차_5_시리얼passive후_본사_경로1줄.png`, `5일차_6_시리얼passive후_지사_경로1줄.png`. 단계 2의 캡처(5일차_3, 5일차_4, 경로 두 줄)와 비교하면 passive의 효과가 보인다. 경로가 줄어드는 중간 장면은 캡처하지 못했다.
- 이 시점의 `show ip protocols`는 보지 않았고, 단계 6-1에서 시리얼 passive 표시를 확인했다.

### 단계 4. 지사에 창고 네트워크 추가, 동적 학습 확인

**목적**: 오늘 목표의 핵심 증명이다. 지사에 새 네트워크를 만들고, 지사 라우터에 RIP `network` 선언만 추가했을 때 본사에서 경로를 손으로 적지 않아도 자동으로 학습하는지 확인한다.

**방식: 루프백(가상 인터페이스)**

| 항목 | 값 |
|------|-----|
| 창고 네트워크 | 192.168.90.0/24 |
| 만드는 곳 | 지사 라우터 SC-BR-R1의 Loopback0, 주소 192.168.90.1 |

- 수업에서 루프백으로 배웠고, 루프백도 본사 PC에서 `ping 192.168.90.1`로 통신 증거를 남길 수 있어서 루프백으로 정했다.
- 참고: 처음에는 지사 라우터(2901)에 HWIC-4ESW 모듈을 넣어 실제 LAN(VLAN 90, 스위치, PC)을 만들려고 했다. 이 모듈은 설정 모드의 `vlan 90`이 거부되고(`% Invalid input detected`), 특권 모드의 `vlan database`로 VLAN을 만들어야 한다는 것까지 확인한 뒤 루프백으로 바꿨다. 만든 VLAN 90은 삭제했고, 모듈은 꽂아 둔 채 쓰지 않는다.

**4-1. 추가 전 상태 확인**

- 지사 `show ip route`(캡처: `99_첨부파일/5일차_7_창고추가전_지사_경로.png`): R 경로 192.168.10, 20, 30, 40, 50 대역이 `[120/1] via 192.168.70.1, GigabitEthernet0/1`로 올라와 있고, 192.168.90.0은 없다.
- 확인하지 못한 것: 본사의 추가 전 `show ip route`는 캡처하지 못했다. 본사 쪽 증거는 추가 후 출력만 있다.

**4-2. 지사에 루프백 생성 (SC-BR-R1)**

```
configure terminal
interface loopback 0
description Warehouse_Loopback
ip address 192.168.90.1 255.255.255.0
exit
end
show ip interface brief
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `interface loopback 0` | 라우터 안의 가상 인터페이스 | 케이블과 장비 없이 "지사에 새 네트워크가 생긴 상황"을 만든다. 항상 up이라 상태가 안정적이다 |
| `ip address 192.168.90.1 255.255.255.0` | 창고 네트워크의 주소 | 192.168.90.0/24를 지사 라우터의 직접 연결 네트워크로 만든다 |

**결과**: `Loopback0 192.168.90.1 YES manual up up`. 다른 인터페이스(Gi0/0, Gi0/1, Serial0/3/0)는 그대로 up/up이다.

**4-3. 핵심: RIP network 한 줄 추가 (SC-BR-R1)**

```
configure terminal
router rip
network 192.168.90.0
end
copy running-config startup-config
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `network 192.168.90.0` | 이 대역에 RIP을 켜고 광고 대상에 포함 | 오늘 목표의 증명이다. 본사 라우터에는 아무것도 입력하지 않는다 |

**4-4. 본사에서 자동 학습 확인 (SC-HQ-R1)**

```
show ip route
ping 192.168.90.1
```

**결과**
- 본사 `show ip route`에 `R 192.168.90.0/24 [120/1] via 192.168.70.2, 00:00:03, Vlan70`이 올라왔다. 본사에는 이 경로를 입력한 적이 없다.
- 본사 `ping 192.168.90.1`: 4/5 성공(첫 패킷 `.`, 이후 `!!!!`), 평균 0 ms. 첫 패킷은 ARP 해석 때문에 유실된 것으로 보이며 이후는 모두 성공했다(추정).
- 해석: 지사 라우터에 `network` 한 줄만 추가했는데 본사가 30초 이내에 경로를 자동으로 학습했다. 정적 라우팅이었다면 본사 라우터에 `ip route 192.168.90.0 255.255.255.0 192.168.70.2`를 따로 넣어야 했을 것이다. 이것이 오늘 목표다.

**4-5. 추가 증거: 본사 PC ping과 정적 경로 부재 확인**

```
(본사 PC Command Prompt) ping 192.168.90.1
(SC-HQ-R1) show running-config | include ip route
(SC-HQ-R1) show ip route 192.168.90.0
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| 본사 PC에서 `ping 192.168.90.1` | PC에서 창고(지사 루프백)까지 통신 확인 | 라우터가 아니라 사용자 PC에서 새 네트워크까지 통신이 되는 증거를 남긴다 |
| `show running-config \| include ip route` | 설정 안의 정적 경로만 표시 | 본사에 90 대역 정적 경로를 입력하지 않았다는 증거다 |
| `show ip route 192.168.90.0` | 이 대역 경로의 학습 방법과 출처 | `Known via "rip"`이면 정적이 아니라 RIP으로 배웠다는 직접 증거다 |

**결과**
- 본사 PC ping(캡처: `99_첨부파일/5일차_8_창고추가후_본사PC_ping.png`): `Reply from 192.168.90.1`이 4개, `Sent = 4, Received = 4, Lost = 0 (0% loss)`, time<1ms, TTL=254. 첫 패킷도 유실되지 않았다(PC의 ARP는 이미 해결된 상태였을 것으로 추정).
- `show running-config | include ip route`: `ip route 192.168.60.0 255.255.255.0 192.168.80.2 250` 한 줄뿐이다. 4일차 예비 경로만 있고 90 대역 정적 경로는 없다.
- `show ip route 192.168.90.0`: `Known via "rip", distance 120, metric 1`, `Last update from 192.168.70.2 on Vlan70, 00:00:24 ago`.
- 해석: 본사에 90 대역 정적 경로가 없고, 경로는 RIP으로 지사 라우터(192.168.70.2)에서 배웠으며, 본사 PC에서 그 네트워크까지 통신이 된다. 지사에 네트워크가 늘어도 지사 라우터의 `network` 한 줄만으로 본사와 연결된다는 오늘 목표가 증명됐다.
- 출발 PC 확인(캡처: `99_첨부파일/5일차_9_본사PC_ipconfig.png`): `ipconfig`에서 IPv4 192.168.40.11, 서브넷 마스크 255.255.255.0, 기본 게이트웨이 192.168.40.1이다. 즉 위 ping은 경영지원 PC(VLAN 40)에서 나갔다. 단, ping 캡처와 ipconfig 캡처는 별도 화면이다.
- 한계: 본사 라우터의 추가 전 `show ip route`는 캡처하지 못했다. 대신 지사의 추가 전 경로표(5일차_7)와 위의 정적 경로 부재 확인으로 "경로를 입력하지 않았다"를 보였다.

### 단계 5. 장애 실습, 예비 경로 /24 확인

**목적**: 주 회선을 끊었을 때 예비 회선으로 전환되는지, 유실 패킷 수와 복구 동작이 4일차 정적 방식과 어떻게 다른지 본다. 예비 경로는 이미 네트워크별 /24(255.255.255.0)다.

**방식**: 4일차와 같다. 지사 PC에서 `ping 192.168.50.1 -t`를 걸어 두고 본사 `GigabitEthernet0/1/3`을 shutdown, 이후 no shutdown으로 복구한다.

**5-1. 장애 전 상태 (SC-HQ-R1, SC-BR-R1)**

```
show ip route
```

**결과** (화면이 길어 위쪽과 아래쪽을 나눠 캡처했다)
- 본사(캡처: `5일차_10_장애전_본사_경로_위쪽.png`, `5일차_11_장애전_본사_경로_아래쪽.png`): `R 192.168.60.0/24 [120/1] via 192.168.70.2, Vlan70`과 `R 192.168.90.0/24 [120/1] via 192.168.70.2, Vlan70`. 192.168.80.0/30은 Serial0/2/0에 직접 연결(C)이다. S 경로는 보이지 않는다(예비 경로는 대기 중).
- 지사(캡처: `5일차_12_장애전_지사_경로_위쪽.png`, `5일차_13_장애전_지사_경로_아래쪽.png`): 192.168.10, 20, 30, 40, 50이 `R [120/1] via 192.168.70.1, GigabitEthernet0/1`이고, 192.168.90.0/24는 Loopback0에 직접 연결(C)이다. S 경로는 보이지 않는다.

**5-2. 연속 ping 시작 (지사 PC)**

```
ping 192.168.50.1 -t
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `ping 192.168.50.1 -t` | 멈출 때까지 계속 ping | 전환 순간의 유실을 보려면 연속 ping이 필요하다. 4일차와 같은 목적지(본사 서버팜 게이트웨이)로 비교한다 |

**5-3. 주 회선 차단 (SC-HQ-R1)**

```
configure terminal
interface GigabitEthernet0/1/3
shutdown
exit
end
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `interface GigabitEthernet0/1/3` + `shutdown` | 본사의 주 회선 포트를 내림 | 4일차와 같은 방식으로 주 회선 장애를 재현한다 |

**5-4. 전환 확인**

```
(SC-HQ-R1) show ip interface brief
(SC-HQ-R1) show ip route
(SC-BR-R1) show ip route
```

**결과**
- ping 통계(`Ctrl+C`로 멈춤): `Sent = 140, Received = 140, Lost = 0 (0% loss)`, 최소 0ms, 최대 47ms, 평균 8ms. 장애를 걸었는데도 유실이 0이었다. 캡처는 하지 못했다(통계 텍스트만 확인).
- 본사 `show ip interface brief`: GigabitEthernet0/1/3이 `administratively down down`, Vlan70이 `up down`(포트가 내려가서 VLAN 70의 라인 프로토콜이 down). 즉 shutdown은 실제로 적용됐다. 시리얼 Serial0/2/0은 up/up이다.
- 본사 `show ip route`: R 경로가 모두 사라졌고 `S 192.168.60.0/24 [250/0] via 192.168.80.2`가 올라왔다. 또한 192.168.70.0/24(C, L)도 사라졌다. **192.168.90.0/24 경로는 본사 표에 없다.**
- 지사 `show ip route`: R 경로가 사라지고 `S [250/0] via 192.168.80.1` 5줄(192.168.10, 20, 30, 40, 50)이 올라왔다. 192.168.90.0/24는 Loopback0 직접 연결로 지사에 남아 있다.
- 해석: 포트를 직접 내리면 양쪽 라우터가 회선 단절을 즉시 알아서 RIP 경로를 지우고 예비 정적 경로(AD 250)로 전환했다. 이 방식에서는 RIP의 느린 타이머(invalid 180초 등)가 드러나지 않는다. 유실 0은 전환이 ping 간격(1초)보다 빨랐다는 뜻으로 추정하며, 4일차(패킷 1개 유실)와 다른 이유는 확인하지 못했다.
- **발견: 예비 경로가 창고 네트워크(192.168.90.0)를 덮지 못한다.** 본사의 예비 정적 경로는 192.168.60.0/24 한 줄뿐이다. 창고는 RIP으로만 학습했기 때문에, 주 회선이 끊기면 본사는 창고로 가는 길을 잃는다(위 본사 경로표에 90 대역이 없다). 이는 다음 5-5에서 본사 PC ping으로 확인했다.

**5-5. 장애 중 창고 도달성 확인 (본사 PC)**

```
(경영지원 PC 192.168.40.11) ipconfig
(경영지원 PC 192.168.40.11) ping 192.168.90.1
(경영지원 PC 192.168.40.11) ping 192.168.60.1
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `ping 192.168.90.1` | 본사 PC에서 창고(지사 루프백)로 | 5-4에서 본사 경로표에 90 대역이 없다는 것을 봤다. 실제로 통신이 안 되는지 확인한다 |
| `ping 192.168.60.1` | 본사 PC에서 지사 LAN 게이트웨이로 | 같은 장애 상태에서 예비 경로가 있는 대역은 되는지 대조군으로 쓴다 |

**결과**
- `ipconfig`: IPv4 192.168.40.11, 게이트웨이 192.168.40.1(경영지원 PC가 맞다).
- `ping 192.168.90.1`: 4개 모두 실패(Lost = 4, 100%). 응답은 `Reply from 192.168.40.1: Destination host unreachable`으로, 본사 라우터가 "갈 길이 없다"고 돌려보낸 것이다.
- `ping 192.168.60.1`: 4/4 성공, 1~17ms, TTL=254(시리얼을 거쳐 라우터를 한 번 지남).
- 해석: 같은 장애 상태에서 지사 LAN(60)은 예비 정적 경로가 있어서 통신되고, 창고(90)는 예비 경로가 없어서 통신되지 않는다. 5-4의 발견이 확인됐다. 주 회선에서는 RIP이 새 네트워크를 자동으로 알려 주지만, 예비 회선은 정적 경로라서 새 네트워크마다 본사에 경로를 손으로 추가해야 한다.
- 참고(시험 중 실수): 처음에 지사 PC(192.168.60.11)에서 같은 ping을 해서 모두 성공했다. 두 주소가 모두 지사 라우터 주소이고 TTL=255(라우터를 거치지 않음)로 나와서 출발 PC가 틀렸음을 알았고, `ipconfig`로 확인했다. 시험은 반드시 `ipconfig`로 출발 PC를 확인한 뒤 해야 한다.

**5-6. 창고용 예비 경로 추가 (SC-HQ-R1, 장애 상태에서)**

```
configure terminal
ip route 192.168.90.0 255.255.255.0 192.168.80.2 250
end
show ip route
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `ip route 192.168.90.0 255.255.255.0 192.168.80.2 250` | 창고 대역으로 가려면 지사 시리얼 주소(192.168.80.2)로 보낸다. AD는 250 | 주 회선이 끊기면 RIP이 알려 준 창고 경로도 사라져서 본사가 길을 잃는다(5-5). 정적 경로로 예비 길을 만든다. AD를 250으로 하는 이유는 4일차와 같다. RIP(120)이 살아 있을 때는 대기만 하고 RIP 경로가 사라질 때 올라온다 |

**결과**
- 본사 `show ip route`: `S 192.168.60.0/24 [250/0] via 192.168.80.2`와 `S 192.168.90.0/24 [250/0] via 192.168.80.2` 두 줄이 있다.
- 경영지원 PC(192.168.40.11)에서 `ping 192.168.90.1`: 4/4 성공, 1~25ms(평균 13ms), TTL=254. 5-5에서는 같은 ping이 4/4 실패였다.
- 해석: 본사에 예비 경로 한 줄을 추가하자 장애 중에도 창고와 통신된다. 지사 쪽은 창고가 직접 연결된 네트워크고 본사로 가는 예비 경로가 이미 있어서 추가할 것이 없었다.
- **정리: RIP이 자동으로 해 주는 것은 주 회선뿐이다.** 새 네트워크를 지사에 만들면 주 회선은 `network` 한 줄(지사에만)로 본사가 자동 학습하지만, 예비 회선은 본사에 정적 경로를 따로 넣어야 한다. `라우팅_비교.md`의 핵심 비교 항목이다.

**5-7. 복구 (SC-HQ-R1)**

```
configure terminal
interface GigabitEthernet0/1/3
no shutdown
exit
end
show ip interface brief
show ip route
(SC-BR-R1) show ip route
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `no shutdown` (Gi0/1/3) | 내렸던 주 회선 포트를 올림 | 복구 후 RIP 경로가 돌아오는지, 예비 경로가 대기로 물러나는지 본다 |

**결과**
- 본사 `show ip interface brief`: Gi0/1/3 `up up`, Vlan70 `up up`.
- 본사 `show ip route`: `R 192.168.60.0/24 [120/1] via 192.168.70.2, 00:00:20, Vlan70`과 `R 192.168.90.0/24 [120/1] via 192.168.70.2, 00:00:20, Vlan70`이 돌아왔다. S 250 두 줄은 표에서 사라졌다.
- 지사 `show ip route`: 192.168.10, 20, 30, 40, 50이 `R [120/1] via 192.168.70.1, 00:00:16, GigabitEthernet0/1`로 돌아왔고, S 250 다섯 줄은 사라졌다.
- 해석: 복구하자 양쪽 모두 RIP 경로(AD 120)가 자동으로 돌아왔고, AD 250 예비 경로는 설정에는 남은 채 표에서 물러났다. 4일차에는 지사가 `[250]`으로 남아 있다가 `ping 192.168.70.1`로 ARP를 다시 학습시킨 뒤에야 돌아왔는데, 이번에는 수동 조작 없이 양쪽이 모두 돌아왔다.
- 확인하지 못한 것: 복구에 걸린 정확한 시간(경로의 경과 시간이 16~20초라서 그 안에 돌아온 것으로 보이지만 `no shutdown` 입력 시각을 재지 않았다), 복구 중 `ping -t`의 유실 통계.

**5-8. 예비 경로가 설정에 남아 있는지 확인**

```
(SC-HQ-R1) show running-config | include ip route
(SC-BR-R1) show running-config | include ip route
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `show running-config \| include ip route` | 설정 안의 정적 경로만 표시 | 복구 후 경로표에서는 S 250이 사라졌지만, 다음 장애에 대비해 설정에는 남아 있어야 한다 |

**결과**
- 본사: `ip route 192.168.60.0 255.255.255.0 192.168.80.2 250`, `ip route 192.168.90.0 255.255.255.0 192.168.80.2 250` 두 줄.
- 지사: 192.168.10.0, 20.0, 30.0, 40.0, 50.0 대역 다섯 줄이 모두 `192.168.80.1 250`이다.
- 해석: 예비 경로는 설정에 남아 있고 경로표에서만 물러나 있다. 다음 주 회선 장애 때 다시 올라온다.

**단계 5 정리**

| 비교 항목 | 4일차(정적) | 5일차(RIPv2) |
|-----------|-------------|--------------|
| 장애 때 유실 | 패킷 1개 | 0개(140개 중, 유실 없음. 전환이 ping 간격보다 빨랐던 것으로 추정) |
| 복구 때 | 본사는 즉시, 지사는 수동 `ping 192.168.70.1` 필요 | 양쪽 모두 수동 조작 없이 R 경로 복귀 |
| 새 네트워크(창고) | 양쪽에 경로 직접 입력 | 주 회선은 지사 `network` 한 줄, 단 예비 경로는 본사에 정적 경로를 따로 추가해야 함 |

- 한계: 포트를 직접 내리는 방식이라 RIP의 느린 타이머(invalid 180초 등)가 드러나지 않았다. 복구 중 유실 수와 복구 시간은 측정하지 못했다(복구 중 `ping -t`를 걸지 않았다).

### 단계 6. 사무실 쪽 passive, RIP 포트 인증

**목적**: PC가 있는 쪽 포트로 RIP 광고가 나가지 않게 막고(passive), RIP이 오가는 주 회선에 인증을 걸어 보려 했다. passive는 적용했고 인증은 Packet Tracer가 지원하지 않아 검증하지 못했다(6-4, 6-5).

**6-1. 본사 LAN 쪽 passive (SC-HQ-R1)**

```
configure terminal
router rip
passive-interface GigabitEthernet0/0/0
passive-interface GigabitEthernet0/0/1
passive-interface Vlan30
passive-interface Vlan40
passive-interface Vlan50
end
show ip protocols
show ip route
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `passive-interface <포트>` | 이 포트로는 RIP 광고를 보내지 않는다 | PC가 있는 포트로 우리 라우팅 정보(내부 대역 목록)가 나가는 것을 막는다. 또 그 포트로 이웃 라우터 관계를 맺는 것도 막는다. 광고를 막아도 `network`로 선언한 그 대역 자체는 계속 다른 라우터에 알려진다. 주의: 고전적인 RIP에서 passive는 보내는 방향만 막고 받는 방향은 막지 않는다. 그래서 passive만으로 PC가 보낸 가짜 RIP 패킷을 거부하지는 못한다(아래 6-5와 한계 참조) |

**6-2. 지사 LAN 쪽 passive (SC-BR-R1)**

```
configure terminal
router rip
passive-interface GigabitEthernet0/0
passive-interface Loopback0
end
show ip protocols
show ip route
copy running-config startup-config
```

**결과**
- 본사 `show ip protocols`: `Interface Send Recv`에는 Vlan70(Send 2, Recv 2) 하나뿐이다. `Passive Interface(s)`에 Gi0/0/0, Gi0/0/1, Serial0/2/0, Vlan30, Vlan40, Vlan50이 들어 있다. `Routing for Networks`에는 10, 20, 30, 40, 50, 70, 80 대역이 있다. 단계 3에서 확인하지 못했던 시리얼 passive가 이번에 표시됐다. 타이머는 30초 갱신, invalid 180초, hold down 180초, flushed 240초이며 `Key-chain` 열은 비어 있다(인증 미적용).
- 지사 `show ip protocols`: `Interface`에는 Gi0/1 하나뿐이고, `Passive Interface(s)`에 Gi0/0, Serial0/3/0, Loopback0이 들어 있다. `Routing for Networks`는 60, 70, 80, 90 대역이다. `Key-chain` 열은 비어 있다.
- 양쪽 `Routing Information Sources`는 상대 라우터 한 대(본사에서는 192.168.70.2, 지사에서는 192.168.70.1)뿐이다.
- `show ip route`는 passive 전과 같다. 본사는 `R 192.168.60.0`과 `R 192.168.90.0`, 지사는 `R 192.168.10`부터 `50`까지가 주 회선으로 유지된다. passive는 경로를 지우지 않고 광고만 막는다는 것을 확인했다.
- 양쪽 라우터 모두 `copy running-config startup-config`로 저장했다.

**6-3. 인증용 key chain 지원 확인 (SC-BR-R1)**

```
configure terminal
key chain RIPKEY
key 1
key-string SafecoreRip#1
exit
exit
end
show running-config | section key
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `key chain RIPKEY` | 인증 키를 담는 묶음(이름 RIPKEY)을 만든다 | RIP 인증은 키 묶음을 인터페이스에 연결하는 방식이다. 묶음만 만들면 라우팅에는 영향이 없어서 지원 여부를 안전하게 시험할 수 있다 |
| `key 1` | 키 번호 1 | 키 묶음 안에서 키를 구분하고, 키를 교체할 때 번호로 순서를 관리한다 |
| `key-string <문자열>` | 실제 비밀 문자열 | 양쪽 라우터가 같은 문자열을 가져야 서로의 광고를 받아들인다. 대소문자도 구분한다 |

**결과**
- Packet Tracer의 이 라우터에서 `key chain`, `key 1`, `key-string`이 모두 에러 없이 입력됐다. `show running-config | section key`에 `key chain RIPKEY`, `key 1`, `key-string SafecoreRip#1`이 보인다.
- 실습용 키 문자열은 `SafecoreRip#1`이다. 키 문자열은 대소문자를 구분하므로 양쪽이 정확히 같아야 한다.
- 아직 인터페이스에 적용하지 않아서 라우팅에는 영향이 없다.

**6-4. 인터페이스에 RIP 인증 적용 시도 (SC-BR-R1)**

```
configure terminal
interface GigabitEthernet0/1
ip rip authentication mode text
```

**결과 (실패)**
- `ip rip authentication mode text` 입력 시 `^` 표시가 `authentication` 위치를 가리키며 `% Invalid input detected at '^' marker.`가 나왔다.
- 원인 확인을 위해 같은 인터페이스에서 `ip rip ?`를 입력하자 `% Unrecognized command`가 나왔다. 이 인터페이스에는 `ip rip` 아래의 명령이 하나도 없다는 뜻이다.
- 해석: 이 Packet Tracer의 지사 라우터(2901)는 RIP 인증 명령(`ip rip authentication ...`)을 지원하지 않는다. key chain 자체는 만들어지지만, 인터페이스에 연결할 수단이 없어서 RIP 인증을 적용할 수 없다.
- 영향: 이 시도는 거부됐으므로 라우팅 설정은 바뀌지 않았다. 앞서 만든 key chain RIPKEY는 라우팅에 영향이 없는 채 남아 있다.
- **한계로 기록**: Packet Tracer에서는 RIP 인증(평문과 MD5)을 검증하지 못했다. 실제 장비에서 쓰는 설정은 다음과 같다(이 환경에서 검증하지 못함).

```
key chain RIPKEY
 key 1
  key-string <키>
interface <RIP이 켜진 포트>
 ip rip authentication mode md5
 ip rip authentication key-chain RIPKEY
```

- 본사 확인: SC-HQ-R1(ISR4331)의 `interface Vlan70`에서도 `ip rip ?`가 `% Unrecognized command`였다. 지사와 본사 모두 RIP 인증을 지원하지 않는 것으로 확정한다.

**6-5. 대체 통제 지원 확인 (SC-BR-R1)**

```
configure terminal
router rip
distribute-list ?
neighbor ?
end
```

| 명령어 | 뜻 | 왜 넣는가 |
|--------|-----|-----------|
| `distribute-list` | 주고받는 경로를 ACL로 거른다 | 인증이 안 되어 대신 받아들일 경로를 제한하려고 시험했다 |
| `neighbor` | RIP 광고를 지정한 이웃에게만 직접 보낸다 | 멀티캐스트 대신 유니캐스트로 보내 광고 범위를 좁히려고 시험했다 |

**결과 (둘 다 실패)**
- `distribute-list ?`: `% Unrecognized command`
- `neighbor ?`: `% Unrecognized command`
- 해석: 이 Packet Tracer의 RIP에서는 인증, 경로 필터, 유니캐스트 이웃 지정이 모두 지원되지 않는다. RIP 보안 통제로 이 환경에서 쓸 수 있는 것은 passive-interface뿐이다.

**단계 6 정리와 한계**
- 적용한 것: LAN 쪽 passive(본사 5개 포트, 지사 2개 포트)와 시리얼 passive. `show ip protocols`로 확인했다.
- 검증하지 못한 것: RIP 인증(평문, MD5), 경로 필터(distribute-list), 유니캐스트 이웃(neighbor). 모두 명령 자체가 인식되지 않아서(`% Unrecognized command` 또는 `Invalid input`) 증거 화면으로 남겼다.
- 알아 둘 점: passive는 광고를 내보내는 것만 막는다. LAN의 PC가 가짜 RIP 패킷을 보내는 것을 막으려면 LAN 쪽 포트에 ACL(UDP 520 차단)을 걸어야 하고, 이것은 ACL 단계에서 시험하는 것이 자연스럽다.
- 개념(면접용): RIP 인증은 키 묶음(key chain)을 만들고 인터페이스에서 인증 방식(평문 또는 MD5)과 키 묶음을 연결한다. 평문은 키가 패킷에 그대로 실려 도청에 약하고, MD5는 해시값만 실려서 키가 노출되지 않는다. 양쪽 키가 다르면 광고를 서로 받지 않는다.

## 4. 실제 결과와 실수

### 실수 1: 지사용 명령어를 본사 라우터에 입력
- 증상: `SC-HQ-R1(config)#no ip route 192.168.10.0 255.255.255.0 192.168.70.1` 입력 시 `%No matching route to delete`
- 원인: 192.168.10.0 경로는 지사 라우터에만 있다. 본사에는 192.168.60.0 경로 하나뿐이어서 지울 대상이 없었다. 프롬프트의 호스트네임을 보고 장비를 확인하지 않은 것이 원인이다.
- 교훈: 명령어를 입력하기 전에 프롬프트(`SC-HQ-R1`, `SC-BR-R1`)를 먼저 본다. 설정이 망가지지는 않았고 에러만 났다.

### 실수 2: network 192.168.0.0 한 줄로 RIP을 켠 줄 알았다
- 입력: 양쪽 `router rip`, `version 2`, `no auto-summary`, `network 192.168.0.0`
- 증상: 양쪽 `show ip protocols`에 `Routing for Networks: 192.168.0.0`만 있고, Interface Send/Recv 목록과 Routing Information Sources가 비어 있었다. `show ip route`에 `R` 경로가 없고 `S [250/0]` 예비 경로가 그대로였다.
- 원인: `network` 명령은 클래스 기준으로 해석되고, C클래스는 192.168.10.0, 192.168.20.0처럼 대역마다 선언해야 한다. 192.168.0.0 하나로는 우리 대역에 RIP이 켜지지 않았다. 처음 이 명령으로 안내받았다가 잘못된 것을 확인하고 정정했다.
- 함정: 이때도 지사 ping은 5/5로 성공했다(1/7/13 ms). RIP이 아니라 예비 정적 경로(시리얼) 덕분이었다. 따라서 ping 성공만으로 RIP 동작을 판단하면 안 되고, 라우팅 테이블에 `R` 경로가 있는지를 봐야 한다.

## 5. 면접 질문과 답변 요지

- 정적과 동적 라우팅의 차이: 정적은 관리자가 입력하고, 동적은 라우터끼리 교환한다. 네트워크가 늘어나는 구간에는 동적이 유리하다.
- 왜 주 회선 정적 경로를 지웠나: 남아 있으면 AD 1이 RIP의 AD 120보다 우선해서 RIP 경로가 테이블에 올라오지 못한다.
- 왜 예비 경로는 남겼나: AD 250이라 RIP(120)보다 후순위여서 RIP이 정상일 때는 영향이 없고, RIP 경로가 사라지는 최악의 경우에 마지막 수단이 된다.
- network 명령 하나로 안 켜졌던 이유: 클래스 기준이라 C클래스 대역은 대역마다 선언해야 한다. 이 문제를 `show ip protocols`의 빈 인터페이스 목록으로 찾아냈다.
- ping이 되는데 왜 RIP이 안 된다고 판단했나: 통신은 예비 정적 경로로 되고 있었다. 라우팅 테이블에 `R` 경로가 없고 이웃 경로 출처가 비어 있어서 RIP이 동작하지 않는다고 판단했다.
- RIPv2를 쓴 이유: 서브넷 마스크를 전달해서 /24와 /30이 섞인 구성에 맞고, 멀티캐스트로 광고하며 인증을 지원한다.

## 6. 한계와 더 깊게 갈 방향
- RIP은 홉 수만 보고, 수렴이 느리고(타이머 180초대), 15홉 제한이 있다. 수업 진도에 따라 OSPF로 바꿔 비교할 수 있다.
- 장애 전환 시간은 포트를 직접 내리는 방식이라 RIP 타이머가 드러나지 않았다. 중간 장비 고장처럼 회선은 살아 있는 장애, 복구 중 유실 수와 복구 시간은 측정하지 못했다.
- RIP 인증(평문과 MD5), 틀린 키 시험, 경로 수신 제한(distribute-list)은 Packet Tracer가 지원하지 않아 시험하지 못했다. LAN 쪽 ACL(UDP 520 차단)은 ACL 단계에서 시험한다.
- 정적과 RIPv2의 항목별 비교는 `라우팅_비교.md`에 정리했다.

## 7. 보안 3요소와의 연결
- 무결성: passive-interface는 LAN 쪽으로 내부 경로 정보가 새는 것과 LAN 쪽 이웃 관계 형성을 막는다. 가짜 라우터와 PC가 보낸 RIP 패킷을 거부하는 통제는 RIP 인증, 경로 필터, 또는 LAN 쪽 ACL(UDP 520 차단)인데, 이 Packet Tracer에서는 앞의 둘이 지원되지 않아 검증하지 못했다. LAN 쪽 ACL은 ACL 단계에서 시험한다.
- 가용성: 동적 라우팅과 예비 정적 경로로 주 회선 장애에도 본사와 지사 통신이 유지되게 한다.
